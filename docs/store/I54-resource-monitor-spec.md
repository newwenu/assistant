### 1.2 目标

1. 页面身份从「存储管理器」改为「资源监视器」，页面 id 保留 `storage`（§3.3）；
2. 页面内**两个 tab**：存储 + **进程树**（本文）；
3. 进程树 tab 在 v1 交付**采样缝 + 整棵子树 + 两个合计 + 口径定案**，数字只到「树级、无任务归因」的粒度（§5.2、§5.9）；
4. 进程树 tab 的**实时树与自身合计出自同一次采样**（同一 `sampledAt`）；**峰值区**只能读外部产物，且必须与实时树分块渲染（§5.5）；
5. 任何数字必须携带「采样器、口径、采样时刻、可用性状态」四件套；
6. 任何读不到的对象显示**状态与原因**，禁止显示 `0`。

### 1.3 非目标

**范围前置声明**：本规格 v1（R0–R3）**不依赖任何未立项文档**。任务级归因与停止能力都不在任何批次内（§12 推迟项），因此即使进程登记表永不立项，本 tab 仍**完整交付**树级数字，只缺一列任务名。这是范围边界，不是缺陷；相关需求清单记在附录 A，不对未立项文档下命令。

- **不做跨 tab 汇总**：文件字节与内存字节不是同一维度，相加无意义（§3.6）；
- **不引入删除 / 回收入口**：进程树 tab 只有观测者身份，不提供停止或回收（§5.4）；
- 不做进程登记表、不做任务级归因（§5.2）：本文只登记需求（附录 A），**不拥有**登记表，也不等它开工；
- **不做线程 tab、不做线程语义归属、不做线程管理**：线程只交付宿主行的一个 `threadCount` 列（§6.3）；语义归属需要全仓 spawn 命名改造，收益低，不立项；
- **不承诺 Linux 上的可求和内存合计**：Linux 无私有工作集口径，只交逐行 RSS 并标注重复计数（§5.6.4），这是平台边界不是缺陷；
- 不做「峰值」的自采样实现：峰值只能由外部留痕（§5.8 约束 2）；
- **允许新建承载「进程内采样」的 crate**：它只依赖 OS API、不读 `dirs`、路径与根 PID 由调用方注入（§5.7）；豁免边界是「不得引用应用层任何模块」，越界即否决；
- 不自持目录清单：路径只从 `AppDirs` 与可选能力模块的 getter 来（N13）；
- **不把采样器登记进 I75 的 `RESOURCES` 表**：该表是「首次 `ensure`、常驻到进程退出」的资源，采样器是**可停止资源**；I75 目前没有该类别，本文不单方面扩展它（§5.8.2）。

## 2 术语与分层

### 2.1 本 tab 的身份：只做观测者

进程树 tab 只有**观测者**一种身份：采样器**只读**系统信息，不写任何受管目录（§5.8 约束 1）；停止与回收能力不属本 tab（§5.4）。

### 2.2 行与列：对象 ≠ 方向

这是本规格最容易混淆的一处，必须先分清，否则「几个监视方向」会算错：

- **观测对象**是**行**；
- **观测方向**是**列**；
- 一个「tab」是**一组行 + 一组合法列**，不是一根方向轴。

进程树 tab 的行是**进程**，列是「角色 / CPU / 内存（带口径）/ 线程数」，没有「归属目录」这一列，也不设「存在」列（§5.1）。**禁止**为了形式统一把进程行塞进别的 tab 的行列结构。

### 2.3 一条取数缝

| 缝 | 观测对象 | 数据源 | 失败模式 |
|---|---|---|---|
| **缝 B：进程内子树采样** | 自身进程 + 由父子链推导出的全部后代 | OS 的**一次全系统进程快照**（按 `root = 自身 PID` 在内存里过滤出子树） | 采样器与被观测者同生共死；PID 复用会误归属 |

缝 B 只有**一个采样器、一个根、一次遍历**，输出**一张表**（不再切成两个投影）：

```
缝 B（进程内，root = 自身 PID）
   ├─ ① 一次全系统进程快照（单次系统调用，不是逐 PID 查询）
   ├─ ② 在内存里按 PID 建表、按 parent_pid 建父子链
   ├─ ③ 从 root 做一次 DFS → 得到整棵子树
   └─ ④ 逐进程标注 role，并按 role 汇总出两个合计（自身 / 全树）
```

**「一次遍历」的准确含义是一次全系统快照 + 内存建父子表 + 从根 DFS**（Chromium 的 `SharedSampler` 即此形态：一次 `NtQuerySystemInformation(SystemProcessInformation)` 拿全表，再在内存里过滤与分组）。

**约束（实现形态）**：

1. **禁止**「对每个后代各查一次系统接口」的逐 PID 递归查询——那是 O(N) 次系统调用，而一次快照是 O(1) 次；
2. 既然一次快照必然看到不属于本应用的进程，**过滤是采样的必需步骤而非优化**；
3. 过滤**必须按祖先链**（从 root 沿父子链可达），**镜像名只能作前置粗筛**——`msedgewebview2.exe` 是全机器共享的镜像名，只按名字过滤必然收进别的应用的进程；
4. 快照里必须**同时**取到 `parent_pid` 与 `start_time`，否则第 ② 步无法建链、§7 的 PID 复用校验也无从执行。

**为什么不再分成两个 tab**：宿主与 WebView 进程、其余子进程，本就是**同一棵树的成员**。分成两个 tab 需要「两处共用一次采样」「指标按需仲裁」「跨 tab 心算」三套额外约束来维持一致，而这三套约束没有独立价值。合并成一张表后，每个进程只出现一次、带一个 `role`，父子关系天然可解释（§5.1）。

### 2.4 可用性状态词表（封闭）

本表只定义**本文两个数据源**用到的状态：实时树采样（缝 B）与峰值区的外部诊断产物（C）。

| 状态 | 含义 | 典型来源 |
|---|---|---|
| `available` | 能出数 | 采样器成功返回；外部产物可读且未过期 |
| `unavailable` | 本次取数失败但对象存在 | 采样超时、系统接口临时失败；本平台无该口径（§5.6.4） |
| `notImplemented` | 该能力尚未落地 | 采样平台方案未定案（§10 第 1 项）；命令尚未实现 |
| `unreadable` | 结构性读不到 / 产物损坏 | 权限不足；外部产物 JSON 解析失败或被截断 |
| `noReportYet` | 外部诊断产物尚不存在 | 进程外报告从未生成过 |
| `staleReport` | 产物存在但已过期 | 报告生成时刻早于陈旧阈值 |

约束：

1. `notImplemented` 必须带原因（哪个平台能力未定案 / 哪条命令未实现），否则用户会把「未实现」误读为「系统认为没问题」；
2. 该词表是**封闭集合**，前端按枚举分支渲染，不做字符串兜底（与开放集合的处理相反）；
3. `noReportYet` 与 `staleReport` 是**外部产物类**状态，**必须**随附产物生成时刻；只有 `staleReport` 允许展示产物里的数字，且必须同时显示「生成于 X 之前」——外部产物是历史快照，不是当前值；
4. `unavailable` 与 `unreadable` 的区别：前者是「这次没取到、下次可能取到」，后者是「结构性读不到」；展示上 `unavailable` 允许「重试」，`unreadable` 不允许。

## 3 页面与 tab

### 3.1 tab 表

| tab | 取数缝 | 状态 | 不可用时的显示 |
|---|---|---|---|
| **存储** | —— | 不属本文 | —— |
| **进程树** | 缝 B（一次全系统快照 + 子树 DFS + 一张表） | 待建（§12 R1–R3） | 实时树 `notImplemented` + 原因（平台方案未定案，§10 第 1 项）；峰值区 `noReportYet` / `staleReport`（§5.5） |

**两个 tab 的数字不可互相替代**：文件字节与工作集不是同一维度；一个 tab 的失败不连坐另一个（§8.1）。

### 3.2 为什么是页内 tab，不是多个设置页

必须做成**一个设置页内的两个 tab**，而不是在 `builtinRegistry` 注册多个 page：

| 方案 | 后果 |
|---|---|
| 注册多个 page（`storage` / `process-tree`） | 左侧导航出现多项，用户需要「先选类别再选 tab」两次点击；且 `settingsSnapshot` 的 golden 投影整体改写（N8），新路由与空页面同时产生 |
| **一个 page 内两个 tab**（采用） | 左侧导航仍是「资源监视器」一项；golden 投影只需改一个 label 与 keywords；tab 之间切换不重新挂载页面壳 |

实现形态用 antd `Tabs`，仓库已有先例（`src/vault/settings/VaultSettings.tsx` 的 `activeKey` + `Tabs` 用法），不引入新组件库。

### 3.4 容器与滚动契约

引入 tab 栏后，页面原有的单 tab 滚动契约（唯一滚动容器、零内嵌滚动、表头 sticky 基准）会变，**只能由本文的容器层吸收**：

| 项 | 契约 |
|---|---|
| 滚动容器 | 页面仍是**唯一滚动容器**；tab 内容区**不引入内嵌滚动** |
| tab 栏位置 | tab 栏**吸顶**，与工具条同层，不随内容滚动 |
| sticky 表头基准 | 表头 `top` = 工具条高度 + tab 栏高度；该值由**容器统一提供**，各 tab 不各自计算 |
| 切换行为 | 切 tab **不重新挂载页面壳**（保持 `activeKey` 受控）；**滚动位置按 tab 独立记忆**，切回时恢复该 tab 上次位置，不沿用另一 tab 的偏移 |
| 高度 | 内容区高度由容器计算并下发给 tab，tab 不自己量窗口 |

**禁止**各 tab 自带 sticky 偏移常量；基准只在容器一处定义。

### 3.5 tab 与路由 / 深链

| 项 | 结论 |
|---|---|
| tab 是否进 URL | **进**：`/settings/storage?tab=<key>`，`key` 取封闭枚举（`storage` / `processTree`），非法值回落默认 |
| 默认 tab | 存储 |
| 返回行为 | 切 tab 用 `replace` 而非 `push`，避免历史里堆满 tab 切换；从其他页面返回时恢复到最近 tab |
| 是否持久化 | 进程内记忆即可，**不落盘**（设置页是导航子页，刷新后回到默认 tab 可接受） |

理由：tab 若完全不进 URL，深链无法指向进程树，也无法从其他页面跳转到指定 tab；若拆成多个路由，则与 §3.2 的「页内 tab」结论冲突。折中是**一个路由 + 查询参数**。

### 3.6 不做跨 tab 汇总（硬约束）

**禁止**在任何 tab 或页面顶部显示「本应用总占用 = 文件 + 内存」这类数字。理由有三条，任一条成立即否决：

1. **单位不同**：字节与工作集不可相加；
2. **口径不同**：文件侧是文件长度之和，内存侧是工作集或私有工作集（§5.6.2），两者都不含「将来的实际占用」；
3. **归属不同**：文件侧按目录归属，内存侧按进程树归属（§5.2），两个归属集合无交集语义。

用户要问「占了多少盘」和「占了多少内存」，是**两个问题、两个 tab、两个数字**。合并成一个数会同时错两次。

## 5 进程树 tab

### 5.1 一张表：行 = 进程，全树只出现一次

| 项 | 定义 |
|---|---|
| 行 | 整棵子树（root = 自身 PID）中的**每一个进程，只出现一次** |
| 列 | 进程（`exeName` + `pid`）/ 角色 / CPU / 内存（带口径）/ 线程数 |
| 不设「存在」列 | 快照里出现的每一行**本身就是存活的**（死进程不在快照内），该列恒为真、无信息量；「刚退出」由行消失表达，不需要一个恒真列 |
| 排序 | 后端按树序（DFS 先序）输出，前端不重建树 |
| 合计 | 头部两个：**自身**（role ∈ 宿主 + WebView）与**全树**（全部行），见 §5.3 |
| 不重叠 | 一个进程只出现在一行；不存在「同一进程在两处各计一次」 |

合并后**不再需要** `projection` 字段：`role` 直接决定该行归入「自身合计」还是「其余」。**禁止**在表里再设一列「投影」——它只是 `role` 的派生。

**两条必须写在 UI 上的边界**（否则数字会被误读）：

| 边界 | 说明 |
|---|---|
| **子树边界** | 只观测本进程的后代。主动 `detach` / `daemonize` 的子进程会脱离父子链，从而**永久不可见**——这不是采样失败，是这类进程的设计意图 |
| **无归因边界** | 同一角色的多个进程在 v1 里是**可区分但不可命名**的（按 PID 区分），用户看到的是 `msedgewebview2.exe (pid 1234)` 而不是「渲染进程 #2」 |

### 5.2 角色列与归因边界

#### 5.2.1 角色（全表可见）

**判定必须分三层，且三层的取数成本递增**。把三层压成一层（「命令行含 `--type=` 就是 WebView」）是本规格最容易犯的错：命令行不在系统快照里，逐进程读命令行会让 §2.3 的「一次快照」失效，并让「读不到命令行」变成一个**错误结论**而不是**未知**。

| 层 | 判据 | 取数 | 作用 |
|---|---|---|---|
| **① 归属** | 从 root 沿 `parent_pid` 链可达（§2.3） | 一次快照内 | 决定「在不在本应用的子树」 |
| **② 家族** | `exeName` ∈ WebView 家族（`msedgewebview2.exe` / `msedge.exe` / `chrome.exe`，按平台配置） | 一次快照内（`exeName` 随快照可取） | 决定「是不是 WebView 系」 |
| **③ 细分** | 命令行 `--type=renderer` / `gpu-process` / 其余 | **逐进程额外读取** | 决定「是 WebView 的哪一类」 |

第 ② 层用镜像名**不会**违反 §2.3 约束 3（「镜像名只能作粗筛」）：那里禁止的是用镜像名**判定归属**，而归属已由第 ① 层定死；镜像名只用来在**已确定的子树内**分家族。

| 角色 | 判据 | 归入哪个合计 |
|---|---|---|
| `host` | PID == root | 自身 |
| `webviewRenderer` | 家族命中 + 命令行含 `--type=renderer` | 自身 |
| `webviewGpu` | 家族命中 + 命令行含 `--type=gpu-process` | 自身 |
| `webviewUtility` | 家族命中 + 命令行含 `--type=` 的其余取值 | 自身 |
| `webviewBrowser` | 家族命中 + 命令行可读但无 `--type=`（WebView2 的浏览器/根进程） | 自身 |
| `webviewUnknown` | 家族命中但**命令行读不到**（权限 / 平台不支持 / 读取失败） | **自身** |
| `otherChild` | 其余全部后代 | 全树（不计入自身） |

**`webviewUnknown` 必须计入自身合计**，这是本条最要紧的约束：若把「命令行读不到」降级成 `otherChild`，一次读取失败就会把整个 WebView 子树踢出「自身」合计，而「本应用占多少」正是本 tab 要回答的核心问题——那会是一次**静默错误**，比少细分一档严重得多。读不到命令行只影响第 ③ 层，**永远不得影响第 ① ② 层**。

**DFS 必须覆盖任意深度**（不是只走一层）：WebView2 的 renderer / GPU / utility 是 `msedgewebview2.exe` **根进程**的子进程，即宿主的**孙进程**。只取直接子进程会漏掉真正吃内存的那几个。

第 ③ 层的判据照参考实现 openhuman 的 `classify_process`：先判是否等于根 PID，再看命令行 `--type=` 特征；本文在其上补了第 ② 层家族粗分与 `webviewUnknown` 兜底，因为参考实现不做「命令行不可读」这一分支。

**`host` 行的 `parentPid` 无意义**：它是宿主的父进程（如 `explorer.exe`），不在 `entries` 里。前端不得按 `parentPid` 重建树（§5.1 已规定后端出树序），因此该值只作诊断信息，**不得**用它去查父行。

**角色列为什么现在有用**：两个 tab 分开时，进程 tab 的 `role` 恒为 `otherChild`（等于没有这一列）；合并后同一列有 7 个取值，是这张表信息量最大的列之一。

#### 5.2.2 归因边界（v1 无任务名）

**本 tab 不拥有登记表，也不等它开工**。任务级归因的完整需求清单、六要素、`Task` / `TaskGroup` 拆分与防环约束，全部记在**附录 A**；主文只保留三条对本 tab 有约束力的结论：

| # | 结论 |
|---|---|
| 1 | OS 级数字（存在 / CPU / 内存 / 角色）**不依赖**登记表；只有「这个进程属于哪个任务」与「排队中」依赖。因此 v1 能出树级数字，缺的是 `Task`，不是数字 |
| 2 | **禁止**在登记表成立前显示**任务级**数字（如「MCP server foo 占 40 MB」）——没有身份代际，重启或停止一次之后归因必然错乱，错归因比没有归因更危险 |
| 3 | 本 tab 对登记表的需求只有三条：`pid + startTime` 作为 join key、`ownerTaskId → Task.title` 用于归因列、`state == queued` 用于显示无 PID 的行。其余字段（`kill` / `groupKind` / `generation`）本 tab **一律不消费** |

**归属**：登记表若立项，由 P9 ADR 定案（[I52-ext](./I52-ext-background-task.md) 的 E1 是最可能落点）。本文**不建第二套登记表**，也不对未立项文档下命令——附录 A 是**需求登记**，不是接口约定。

**停止能力与登记表无关**（易被误读，必须先说清）：停止只需要**句柄 + 统一回收抽象**，属 `assistant-tools` 的既有代码资产（Windows Job Object / Unix `pgid`，§6.4），**不需要登记表**。v1 不做停止是范围选择（§5.4），不是被登记表阻塞。

### 5.3 两个合计（自身 / 全树）

| 合计 | 成员 | 用途 |
|---|---|---|
| **自身** | `role ∈ {host, webviewRenderer, webviewGpu, webviewUtility, webviewBrowser, webviewUnknown}`（即「家族命中 + 宿主」） | 回答「本应用占多少」——最常被问的那个问题 |
| **全树** | 全部行（含 `otherChild`） | 回答「连同我启动的子进程一共多少」 |

约束：

1. 两个合计在**平台可得私有工作集时**必须用它（`memoryAdditive == true`）；若平台只有工作集（`memoryAdditive == false`），**禁止**把子项求和当总量，只能标注「各进程工作集之和（含共享页重复计数）」，或按 §5.6.4 直接隐藏合计（§5.6.2 约束 2）；
2. 两个合计是**包含关系**（自身 ⊆ 全树），必须同时显示并标注包含关系；**禁止**把二者相加（那是重复计数）；
3. 合计的数字必须与表内逐行数字出自同一 `sampledAt`（同一次采样，§5.1）。

### 5.4 停止列（行级禁用，不是 tab 级）

v1 **不交付停止能力**。这是**范围选择，不是被登记表阻塞**——停止只需要句柄（§6.4），登记表只影响「这个进程是哪个任务」，不影响「能不能停」。设计必须先把边界写死，避免将来引入停止时把「自指」放回来：

| 项 | 结论 |
|---|---|
| v1 | **无停止按钮**，该列不出现 |
| 阻塞原因 | **不阻塞**：句柄已具备（Windows Job Object / Unix `pgid` + `KillHandle`）；缺的是「MCP 纳入统一回收抽象」与「句柄暴露成标识」两处代码工作（§6.4） |
| 将来 | 停止能力**按行**决定：`role ∈ {host, webviewRenderer, webviewGpu, webviewUtility, webviewBrowser, webviewUnknown}` 的行**恒为 disabled** 并注明「停止自己 = 应用自杀」 |
| 归属 | 停止的**真实实现**复用既有回收机制（shell 的 `kill_tree` / Job Object），监视器**只能请求**，不得另建第二套回收（与 I52-ext §4 第 3 条同源） |
| 禁止 | 用「整 tab 不可停止」作为边界——那是把行级约束错写成 tab 级，一旦合并或拆分就会丢 |

**自指禁区（停止侧）**：宿主**禁止**登记进受管任务表；这条约束落在**行**上，不落在 tab 上。

### 5.5 峰值区块（外部留痕，与实时树分块）

**两个自指禁区**：

| 禁区 | 后果 | 约束 |
|---|---|---|
| **停止自指** | 宿主进程登记进受管任务表 → 停止自己 = 应用自杀 | 宿主**禁止**登记进任务表；停止列按行禁用（§5.4） |
| **峰值自指** | 采样器与被观测者同生共死 → OOM / 卡死时最后那次采样必然丢失 | **峰值禁止**由自身采样提供，只能由外部留痕 |

两条禁区同源于「观测者与被观测者是同一个东西」，但表现不同：前者是**动作**上的自指，后者是**证据**上的自指。第一条可以靠「不登记」绕开；第二条无法绕开，只能**换观测者**。

**峰值区块的形态**（两块数据性质不同，必须分开渲染）：

| 块 | 内容 | 数据来源 | 状态 |
|---|---|---|---|
| **实时树（含两个合计）** | 宿主 + WebView + 其余后代的 CPU / 内存 / 角色 | 缝 B（进程内） | `available`（平台方案定案后） |
| **峰值与热点** | 峰值内存、峰值 CPU、CPU 热点 | 外部报告（C） | `noReportYet` / `staleReport` / `available` |

**峰值区是报告阅读器，不是监视器**：它读上次诊断产物，必须显示产物生成时刻，且必须在 UI 上说明「这是 X 之前的历史快照，不是当前值」。无产物时显示 `noReportYet` 并给出「如何生成」的说明；产物过期时显示 `staleReport`，仍可看数字但必须带时间标注（§2.4 约束 4）。

**禁止**把峰值区做成「实时峰值」——那等于在进程内自采样峰值，违反 §5.5 峰值自指与 §5.8 约束 2。**禁止**让峰值区与实时树共享 `sampledAt`（两者是不同时刻的两种数据性质）。**禁止**在平台方案定案前显示任何当前值占位数字。

### 5.6 口径与单位（两件事分开定）

**5.6.1 默认口径**：「自身」合计取 `role ∈ {host, webview*}` 的全部进程，不取「仅主进程」。**不选口径就是默认选了「仅主进程」**，而它恰好是最容易被质疑的那个（用户看 200 MB、任务管理器看 900 MB）。

**5.6.2 内存单位与可加性**（本节最要紧的一条）：

可加性不是一件事，是**两件事**，必须分开判定，否则 PSS 必然错一边：

| 单位 | ① 可求和（不重复计数） | ② 等于物理占用 | 含义 |
|---|---|---|---|
| **工作集 / RSS**（resident） | **否** | **否** | 共享页（COW、共享 DLL、WebView 共享段）在每个进程里各记一次，求和必然**大于**物理占用 |
| **私有工作集**（private working set） | **是**（近似） | 近似 | Windows 任务管理器「内存」列用的就是这个 |
| **PSS**（proportional set size） | **是** | **否** | 共享页按全系统共享者数量摊 1/N，求和**不会重复计数**；但结果不等于该集合的物理占用（与树外进程共享的页只摊了 1/N） |
| 提交量 / commit | 是 | 否 | 含未驻留部分，不是「占了多少内存条」 |
| 虚拟内存 | 是 | 否 | 禁止作展示口径 |

**这两列为什么必须分开**：先前版本把「PSS 子树内不可加」写进文档，是错的——PSS 的定义就是「摊掉共享页」，**对任意集合求和都不会重复计数**，它恰恰是最标准的可求和口径；它不成立的只是「求和 = 物理占用」。用一个标志同时承载两件事，会让 PSS 的取值必然错一边。

**约束（可加性）**：

1. **可加性是「按指标」的属性，不是「按视图」的属性**：同一张表里可以同时有可求和的指标（CPU 百分比）与不可求和的指标（工作集）。因此两个标志挂在**指标**上、且**上提到快照顶层**（`memoryAdditive` / `memoryEqualsFootprint`，§8.2）——它们是 `memoryBasis` 的纯函数，放进每个 group 会出现同一响应内两份互相矛盾的标志；
2. 若展示内存合计，**必须**用可求和口径（`memoryAdditive == true`）；若用工作集，**禁止**把子项求和当作总量，只能标注「各进程工作集之和（含共享页重复计数）」；
3. **任何展示内存的列，列名必须自带口径**（「工作集」/「私有工作集」），**禁止**出现不带口径修饰的「内存」「占用」列——列名即口径，不靠脚注兜底。这条比 `memoryAdditive` 字段更能防住「后端换了口径、前端忘了分支」；
4. 单进程数字用工作集没有问题；**只有跨进程求和时**可加性才成立；
5. 若将来引入 `pss` 口径：`memoryAdditive` **为 `true`**（可求和），`memoryEqualsFootprint` **为 `false`**（不等于物理占用）——这是与先前版本相反的结论，§5.6.2 的表格是唯一出处；
6. 父项 ≠ Σ 子项的根本原因是**共享**：只要存在共享页，任何按进程求和的数字都不可直接当作「这一组占了多少物理内存」。

**5.6.3 CPU 单位**：单逻辑核百分比，**可超过 100**。禁止除以核数改成「整机占比」而不标注——用户对照任务管理器会看到不同数字。

CPU 百分比**天然可加**（各进程的 CPU 时间互相独立、无共享页问题），因此 DTO 里不为 CPU 设可加性标志；它的合计**可以直接显示**，但必须说明是「单核百分比之和，可超过 100」。

**5.6.4 平台口径可得性（必须显式降级，不得假装一致）**

「私有工作集」是 Windows 专有口径，其余平台拿不到同义指标。这不是实现缺陷，是平台事实，**必须在 UI 上按平台降级而不是三平台都显示合计**：

| 平台 | 可取口径 | `memoryAdditive` | 自身合计 |
|---|---|---|---|
| Windows | `privateWorkingSet` | `true` | **显示**（任务管理器同口径） |
| macOS | `phys_footprint`（近似私有） | `true`（近似） | 显示，标注「近似」 |
| Linux | 仅 `workingSet`（RSS） | **`false`** | **隐藏合计**，显示 `unavailable` + 原因「本平台无私有工作集口径」，只显示逐行 RSS 并标注「含共享页重复计数」 |

**结论必须写在验收里**：Linux 上 v1 **交不出**可求和的「本应用占多少」，只交逐行数字。这是目标 3 的已知平台边界（§1.2），不得用「加个估算系数」糊过去——那会把平台事实变成编造的数字。

### 5.7 三层拆分与平台方案

「监视自身」是三个可行性完全不同的问题，必须分开实现：

| 层 | 回答什么 | 数据源 | 能否进程内 | 落点 |
|---|---|---|---|---|
| **A 崩溃留痕** | 死的那一刻发生了什么 | 异常处理上下文 | **必须进程内** | `assistant-crash`（既有，N9 / N11） |
| **B 当前值采样** | 现在占多少 | OS API 读自己与子树 | **必须进程内** | 新增 crate `assistant-resource-probe` |
| **C 峰值与热点** | 峰值多少、谁在吃 CPU | 需活得比被观测者久 | **必须进程外** | `src-tauri/src/bin/resource_report.rs`（不进 bundle，N12） |

**为什么 B 要独立 crate 而不是放应用层**：它只依赖 OS API，不需要 `AppDirs`、不接触任何受管目录；独立后可在不启动 Tauri 的情况下跑单测，并把平台依赖隔离在一个 crate 内。它的缝照抄 `assistant-crash`：**不读 `dirs`、不算基根、路径与根 PID 由调用方注入**（N9）。这条豁免的边界是「不得引用应用层任何模块」（§1.3）。crate 的放置约束（叶子 crate、只依赖 OS API）见 `docs/store/crate-architecture.md`，本文不复述。

**平台方案（待定案，§10 第 1 项）**：

| 方案 | Windows | Linux | macOS | 新依赖 | 代价 |
|---|---|---|---|---|---|
| **A. `sysinfo`** | 一条覆盖 | 一条覆盖 | 一条覆盖 | **1 个**（当前为 0，N5） | 新增依赖须单独立项过审；但只污染采样 crate，不进应用层 |
| **B. 手写平台 API** | 需补 `Win32_System_ProcessStatus`（`GetProcessMemoryInfo`，N6） | `/proc` 零依赖 | 需 `libc` | 0 但三套代码 | 本形态要遍历**整棵子树**，三套「遍历 + 分类 + 读内存」成本 ×3 |

**倾向 A**：参考实现 openhuman 已用 `sysinfo` 验证该场景（含整棵子树遍历与峰值统计），且 B 的三套代码在「递归 + 角色分类」上会显著放大。但**新增依赖必须单独过审**，故列为待定而非定案。

**C 的写端必须一并定案，否则峰值区永远是 `noReportYet`**。先前版本只定义了「报告阅读器」，没有定义「谁写报告」，交付结果是**一个永远空的区块**。三件事必须写死：

| 项 | 约束 |
|---|---|
| **输入** | 宿主 PID + 宿主镜像名 + 宿主启动时刻（三者合一才能防 PID 复用，§7）。由调用方在生成报告时传入，C 不自报、不猜测 |
| **复用** | C **必须复用** `assistant-resource-probe` 的子树遍历与角色分类，**禁止**第二套采样实现——两套实现必然在角色判定与内存口径上漂移，而峰值区与实时树的数据必须可对照 |
| **触发（v1）** | 由**外部**在「诊断包生成」流程中调用，或由设置页的「生成资源报告」按钮显式调用；**禁止**由宿主自动周期触发（那等于自采样峰值，违反约束 2） |

C 与 B 的唯一差别是**谁持有句柄、活多久**：B 活在被观测进程内（同生共死），C 由外部拉起、在被观测者死后仍可读。因此 C 的产物必须自带 `generatedAt` 与 `attributionNote`，UI 必须按「历史快照」渲染（§5.5）。

### 5.8 硬约束

| # | 约束 | 依据 |
|---|---|---|
| 1 | **停止自指**：宿主不得登记进受管任务表；采样器不写任何受管目录 | §2.1、§5.4 |
| 2 | **峰值必须外部留痕**：OOM / 卡死时自采样必然失效 | 采样器与被观测者同生共死（§5.5） |
| 3 | **采样频率必须有上限**：秒级起步 + 事件驱动 + **采样失败不重试** + **不得在主线程** + **同一拍不得重入**（上一拍的异步结果未回投则本拍不发新请求）；间隔取平台最小刷新间隔的下限作常量，不得用魔法数 | 参考实现用 `max(MINIMUM_CPU_UPDATE_INTERVAL)`；Chromium 用 `waiting_for_memory_dump_` 布尔量防重入 |
| 4 | **落盘产物必须自限（只约束 C）**：外部报告产物落 `logs()` 同级，复用 `KeepSome` + 单文件上限；**禁止**写进 `crashes/`——该目录是**诊断产物专属目录**，已有 list / stat / prune 与 E13 策略，写周期性快照会污染条目统计与清理资格（N10）。**B 不落盘**：缝 B 是内存采样，只在进程内保留上一拍 CPU 缓存，本条对它不适用 | N7、N10 |
| 5 | **采样由「缓存 TTL」驱动，不做后台常驻**：后端不持有采样线程，只持有「上一拍 CPU 时间缓存」；缓存带 `idleTimeout`，过期即丢弃。**禁止**后台常驻轮询，**禁止**应用启动时预热采样 | 一个「监视自身」的功能若自身成为最大的开销来源，逻辑上自相矛盾 |

**约束 5 的准确形态：纯拉取 + 缓存 TTL**。先前版本用「消费者引用计数」描述，与 §8.1 的拉模型冲突——拉模型下后端没有「观察者对象」可引用计数，也就没有「运行 / 停止」这个状态。正确表述是：

1. 后端只维护一份**上一拍 CPU 时间缓存**（`HashMap<pid, cpuTime>`），不维护线程；
2. 每次取数读缓存、与当前值差分得出 CPU 百分比、再把当前值写回缓存；
3. 缓存超过 `idleTimeout` 未更新则**整体丢弃**（等价于「停表 + 清缓存」）；
4. 于是「无人看」的唯一后果是缓存被丢弃，**不存在泄漏的后台开销**；
5. 引用计数只在将来改为事件推送时才需要（§5.8.1 末段）。

**约束 5 的直接推论（必须同步到 §7）**：缓存过期即丢弃，因此**每次重新打开 tab（距上次取数超过 `idleTimeout`）都是新一次采样的第一帧**——CPU 为 `null` 是**每次打开都会发生的常态**，不是异常，前端不得据此进入错误态。

#### 5.8.1 拉取模型下的等价实现（空闲超时）

本项目的取数是**拉模型**（前端调命令，§8.1），后端没有「观察者对象」可以引用计数，也没有采样线程。因此「无人看即停表」的落地形态是**缓存 TTL**：

| 事件 | 后端行为 |
|---|---|
| 收到 `get_process_snapshot` | 读 CPU 缓存差分 → 写回当前值 → 刷新缓存时间戳；**不启动任何线程** |
| 距最后一次取数超过 `idleTimeout` | 缓存视为失效，**丢弃全部 `pid → cpuTime`**；本次取数按「无上一拍」处理（CPU 为 `null`） |
| 应用启动 | **不预热**；缓存为空 |

`idleTimeout` **必须**取「刷新间隔的整数倍」常量（建议 2–3 倍，与 `refreshInterval` 同源，§8.3），不得用魔法数（§10 第 2 项同源）。**禁止**用「前端主动调 stop 命令」作为唯一停表路径——前端崩溃或页面卸载漏调时缓存会滞留；TTL 是兜底且**必须**是主路径。

若将来改为事件推送（`listen` 通道），则必须换成真正的注册/注销引用计数，且**仍然保留** TTL 作兜底。

#### 5.8.2 与 I75 启动分层的边界

I75 的 `RESOURCES` 表是「首次 `ensure`、常驻到进程退出」的资源表，**没有「可停止资源」这一类别**。采样器恰恰是可停止资源（无人看即停表），因此：

| 项 | 结论 |
|---|---|
| 是否进 `RESOURCES` 表 | **不进**。进表意味着它会被 `ensure` 一次并常驻，直接违反约束 5 |
| 由谁管理生命周期 | 命令层惰性单例 + 空闲超时（§5.8.1），不依赖启动装配 |
| 是否需扩展 I75 | **否**。本文不单方面给 I75 加类别；若将来需要，应由 I75 自己定案「可停止资源」的通用语义 |

**对约束 2 的一处定稿**：先前把「Job Object 内核统计」列为可提供峰值的方案，**该条已否**——Job 峰值内存只在**持有 job 句柄期间**可读，而句柄由宿主自己持有；宿主死亡时句柄一并消失，与自采样同样失效。除非由**外部进程**持有句柄，否则它不能算「外部留痕」。Job 的 `ActiveProcesses` 只能用于「进程数归零」这类存活验收，不能用于峰值。当前唯一确定成立的外部来源是 crash dump 与 OS 侧记录。

**约束 2 与本节的固有冲突必须写明**：缝 B 在进程内，所以它**永远给不出自己的峰值**。这不是实现缺陷，是这条路径的固有边界；峰值区只能读 C 的产物（§5.5）。

### 5.9 v1 边界

v1 的进程树 tab 交付**树级数字、无任务归因**：

| 方向 | 数据 | 来源 | v1 |
|---|---|---|---|
| P1 存在与状态 | PID、存活、父子 | OS | **交付** |
| P2 CPU | 单核百分比（可超 100，§5.6.3） | OS | **交付** |
| P3 内存 | 工作集 / 私有工作集（§5.6.2） | OS | **交付** |
| P4 树归属与角色 | 谁是 WebView、谁是其他子进程 | OS 父子链 + 命令行特征 | **交付**（仅角色，不含任务名） |
| P4b 任务归因 | 这个进程属于哪个任务 | 登记表 | 推迟（§5.2.2、§13） |
| P5 回收 / 停止 | 整棵树 | Job Object（Windows）/ `kill(-pgid)`（Unix），判据见 I53（已归档） | 不做（本期无停止入口，§5.4） |

**两块结构**：实时树（含两个合计）`available`；峰值区 `noReportYet` / `staleReport` / `available`（§5.5）。

**禁止**在 v1 显示「0 个进程」「0 MB」这类占位数字：它们看起来是结论，实际是没测。**也禁止**把宿主自身单独藏起来——它现在是表里的第一行（`role = host`），不是另一个 tab 的内容。

## 6 能力边界与前置条件（进程 / 线程）

「自身占用」并入进程树 tab 的决策已收敛在 §5.1（一张表）、§5.4（行级禁用）、§5.5（峰值外部留痕）三处，此处不再复述合并前后的对照。唯一要留的一句结论：原「宿主禁止进任务表 ⇒ 必须独立 tab」是**跳步**，真正的约束落在**行**上，不落在 tab 上。

本节用途是把「要拿到某个数字，必须先满足什么条件」一次写清，避免实施时把**平台限制**误当实现缺陷，或把**拿不到**误当**为零**。

### 6.1 四个问题，前置条件完全不同

| 问题 | 前置条件核心 | 难度 | 本规格 |
|---|---|---|---|
| 拿进程信息 | 一次全系统快照 + 稳定身份 + 口径可得性 | 中 | **做**（进程树 tab，§5） |
| 拿线程信息 | 枚举与 CPU 容易；语义归属需全仓改造 | 中（采集）/ 难（语义） | 只做**线程数**一列（§6.3） |
| 管理进程（回收/停止） | 句柄所有权 + 幂等 + 不误杀 | 较易（已有基础） | v1 不做，v2 按行（§5.4） |
| 管理线程 | Rust 无法安全取消线程 | 很难 | **不做**（§6.3） |

### 6.2 进程：可达成，六条必备

| # | 必备条件 | 现状缺口 |
|---|---|---|
| 1 | **一次全系统快照能力**（Windows `NtQuerySystemInformation` / Linux 遍历 `/proc` / macOS `sysctl`，或由 `sysinfo` 统一封装） | 无采样 crate、无 `sysinfo`（N5）；`Win32_System_ProcessStatus` 未启用（N6） |
| 2 | **稳定身份**：`pid` + `start_time` 双字段，`parent_pid` 单独不可信 | 无 |
| 3 | **祖先链判定 + 创建时间单调校验**（Windows 的 `parent_pid` 在父进程死后不更新） | 无 |
| 4 | **角色三层判定**：祖先链 → `exeName` 家族 → 命令行细分；命令行读不到落 `webviewUnknown`（§5.2.1） | 无 |
| 5 | **口径可得性**：私有工作集仅 Windows/macOS 可得，Linux 只有 RSS（§5.6.4） | 无 |
| 6 | **CPU 差分缓存 + TTL**：首拍必然 `null`，缓存过期即丢（§5.8 约束 5） | 无 |

三条建议（不影响 v1 正确性）：宿主行加**线程数**一列；把 **MCP server 纳入统一回收抽象**（§6.4）；统一 **spawn 命名纪律**（为将来线程语义铺路，可分批）。

### 6.3 线程：只做数量与 CPU，不做语义，不做管理

| 层 | 能做到吗 | 说明 |
|---|---|---|
| **枚举 + CPU** | **能** | Windows `CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD)` + `GetThreadTimes`（`Win32_System_Diagnostics_ToolHelp` 未启用）；Linux `/proc/self/task/*`；macOS `task_threads` + `thread_info` |
| **线程名** | 部分 | Linux `comm` 只有 15 字节；macOS 只能进程内 `pthread_getname_np`；Windows 线程名在 TEB，跨进程读不到 |
| **语义归属**（哪个子系统 / 哪个任务） | **不能** | 系统不知道；只能靠线程名约定。现状 `std::thread::spawn` 在 31 个文件出现 55 处，**绝大多数未命名**，这是横切改造，且 WebView2 内部线程永远无名 |
| **管理线程**（停止 / 限流） | **不做** | Rust 无 `pthread_cancel` 等价物，强杀会破坏锁与不变量；只能做命名纪律与阈值告警 |

**线程数不是好指标**：线程数多通常是正常的；真正反映并发压力的是 **tokio task 数 / 阻塞池排队深度**，而 tokio 无公开 API，需另立 metrics 导出项。因此本规格**不做线程 tab**，只在宿主行给一列 `threadCount`（可 `null`）。

### 6.4 管理进程：已有约七成基础，三个缺口

已有：Windows Job Object（`AssignProcessToJobObject` / `TerminateJobObject` / `ActiveProcesses`）、Unix `setsid(2)` + `kill(-pgid)`（幂等，ESRCH 忽略）、可克隆跨线程的 `KillHandle`（§5.4、I53（已归档））。

| 缺口 | 后果 | 修法 |
|---|---|---|
| **MCP server 未纳入任何回收组**：裸 `Command::spawn` + `kill_on_drop` | `kill_on_drop` 只杀**直接子进程**，其孙进程变孤儿；同一份「子进程」存在两种回收语义 | 纳入统一回收抽象（Windows 进 Job、Unix `setsid`） |
| **PID 复用导致误杀**（若按 PID kill） | 复用后杀错进程 | 句柄化：Windows 持 Process/Job handle；Linux 用 `pidfd`；macOS 无 pidfd，只能 `kill(pgid)` + `start_time` 校验 |
| **宿主不得进回收组** | Linux 下宿主与未 `setsid` 的子进程同 pgid，`kill(-pgid)` 会**杀掉宿主自己** | 观测者不得同时是被回收者（与 §5.4 自指禁区同源） |

### 6.5 达成度总表

| 维度 | 可达成 | 难度 | 本文落点 |
|---|---|---|---|
| 进程存在 / 父子 | 是 | 中 | §5.1、§2.3 |
| 进程 CPU | 是 | 易（随采样器） | §5.6.3 |
| 进程内存（可求和） | Windows/macOS 是；Linux 否 | 中 | §5.6.2、§5.6.4 |
| 进程角色 | 是（三层判定） | 中 | §5.2.1 |
| 进程归属任务 | 否（需登记表） | 难 | §5.2.2（推迟） |
| 进程峰值 | 是（须外部留痕） | 中 | §5.5、§5.7 |
| 进程回收 | 是（补三个缺口） | 易 | §5.4、§6.4 |
| 线程数量 / CPU | 是 | 中 | §6.3（仅一列） |
| 线程语义归属 | 否（需横切改造） | 难 | §6.3（不做） |
| 线程管理 | —— | —— | §6.3（不做） |

## 7 反模式

下表只保留**跨 tab 通用**与**进程树专属**的反模式。

| 反模式 | 后果 | 替代 |
|---|---|---|
| **采样 crate 反向引用应用层** | 豁免被滥用，等于把应用层搬进 crate | crate 只依赖 OS API，路径与根 PID 由调用方注入（§5.7） |
| **把读不到显示成 `0`** | 伪精确，用户据此做出错误决策 | `unreadable` / `unavailable` / `notImplemented` / `noReportYet` 分开（§2.4） |
| **跨 tab 相加成一个「总占用」** | 单位不同、口径不同、归属不同，同时错两次 | 每 tab 独立数字（§3.6） |
| **把工作集求和当作物理占用** | 共享页被重复计数，合计必然偏高且无法解释 | 用私有工作集，或标注「含共享页重复计数」（§5.6.2） |
| **把两个合计相加** | 自身 ⊆ 全树，相加即重复计数 | 同时显示并标注包含关系（§5.3） |
| **把宿主进程登记进任务表** | 停止自己 = 应用自杀 | 宿主行停止恒 disabled（§5.4） |
| **用「整 tab 不可停止」代替行级禁用** | 把行级约束错写成 tab 级，一旦合并/拆分即丢 | 停止能力按 `role` 逐行决定（§5.4） |
| **在进程内采样自己的峰值** | OOM / 卡死时那次采样必然丢失，峰值永远是「还没崩的时候」 | 峰值由外部产物提供（§5.8 约束 2） |
| **把峰值区块混排进实时树** | 当前值与历史快照共享一屏一时刻，最易被误读 | 分块渲染 + 时间标注（§5.5） |
| **同一进程在表里出现两次** | 数字互相打架，且无法解释合计 | 一行一进程，`entries` 中 `pid` 不重复（§5.1） |
| **只取直接子进程** | WebView2 的 renderer / GPU / utility 是孙进程，全被漏掉 | 递归到任意深度（§5.2.1） |
| **对每个后代各查一次系统接口** | O(N) 次系统调用，N 随子树增长，开销随时序恶化 | 一次全系统快照 + 内存建父子表 + 从根 DFS（§2.3） |
| **按镜像名判定归属** | `msedgewebview2.exe` 是全机器共享的名字，必然收进别的应用的进程 | 按祖先链过滤，镜像名只作粗筛（§2.3 约束 3） |
| **后台常驻采样 / 启动时预热采样** | 监视自身的功能自身成为最大的开销来源，逻辑自相矛盾 | 纯拉取 + CPU 缓存 TTL，过期即丢弃（§5.8 约束 5） |
| **把采样器登记进 I75 的 `RESOURCES` 表** | 会被 `ensure` 一次并常驻，直接违反「无人看即停表」 | 不登记，只留命令层缓存（§5.8.2） |
| **把「命令行读不到」降级成 `otherChild`** | 会把整棵 WebView 子树踢出「自身」合计，静默少报最核心的数字 | 落 `webviewUnknown` 并**仍计入自身**（§5.2.1） |
| **在 Linux 上显示可求和内存合计** | 只有 RSS，求和含共享页重复计数，等于编数字 | `memoryAdditive=false` 时隐藏合计并给原因（§5.6.4） |
| **把线程列当成可管理对象** | Rust 无法安全取消线程，做了也只能是假动作 | 只给 `threadCount` 一列，不做线程 tab（§6.3） |
| **内存列不带口径修饰** | 「内存」一列必然错，用户无法判断含不含共享页 | 列名即口径（「工作集」/「私有工作集」），不靠脚注（§5.6.2 约束 3） |
| **把首帧 CPU `null` 当错误** | 每次打开 tab 都是第一帧，会把常态渲染成故障 | 显示「本拍无基准」，不进错误态（§9） |
| **沿 `parent_pid` 上溯但不校验创建时间** | PID 复用后会把无关进程认成自己的子进程，统计凭空多出一块 | 校验 `child.startTime >= parent.startTime` 且父进程确实存在（§9） |
| **在登记表成立前显示任务级归因** | 归因错乱比没有归因更危险 | 只显示树级数字，不显示任务名（§5.2.2） |
| **把周期性快照写进 `crashes/`** | 给诊断产物专属目录混入无上限的非诊断产物，污染条目统计与清理资格 | 写 `logs()` 同级并复用 `KeepSome`（§5.8 约束 4） |

## 8 契约

### 8.1 命令与模块划分

| 命令 | 职责 | 模块 |
|---|---|---|
| `get_resource_capabilities`（新增） | 只返回两个 tab 的**可用性状态与原因**，**不含任何数字** | `src-tauri/src/cmd/resource.rs`（新增） |
| `get_process_snapshot`（新增） | 缝 B 的一次采样结果：`sampledAt` + 整棵子树（两个合计 + 逐进程明细），实时树与自身合计共用 | `src-tauri/src/cmd/resource.rs` → `assistant-resource-probe` |
| `get_self_usage_report`（新增） | 只读外部诊断产物（C），返回产物内容 + 产物生成时刻 + `availability` | `src-tauri/src/cmd/resource.rs` |

**为什么能力声明要单独一条命令**：若把能力与数字塞进同一个响应，就必须有一个「跨 tab 聚合响应」，而那正是 §3.6 禁止的东西。分开后，每个 tab 各自取数、各自失败、互不影响。

**能力声明里存储 tab 只回答一个问题**：「这个 tab 存不存在」，不含任何明细。

**为什么 `get_process_snapshot` 只有一条命令**：实时树与自身合计**必须来自同一次采样**（§5.1、§5.3）。若分成两条命令，两次调用之间的时间差会让「自身 + 子进程」不可加、不可解释。响应里同时带两个合计与逐进程明细。

**这条命令同时承担「缓存心跳」**：每次调用都读 CPU 缓存差分并刷新缓存时间戳，超过 `idleTimeout` 无调用则缓存整体失效（§5.8.1）。因此**禁止**为「开始/停止采样」再增设命令——那会让停表路径依赖前端自觉，反而更易泄漏；后端也没有可停止的线程或单例。

**为什么报告要单独一条命令**：外部产物是**历史快照**，与实时采样是两种数据性质（§5.5）。混在 `get_process_snapshot` 里会让「当前值」与「峰值」共享一个 `sampledAt`，那是最容易被误读的写法。

模块归属：新增 `cmd/resource.rs` 只做能力声明与两条数据命令（`get_process_snapshot` 转发给采样 crate、`get_self_usage_report` 做本地最小解析，后者**不是转发**）。**不承载**其它 tab 的明细，也不自己实现采样。采样实现在 `assistant-resource-probe`。DTO 落 `assistant-protocol`（I62 契约域）。这符合 [CODE-SPLIT-PRINCIPLE](./../principle/CODE-SPLIT-PRINCIPLE.md) 的「按能力域拆分」，本文不复述其判据。

### 8.2 DTO 字段口径

本文只保留一条通用 DTO 约束：**任何 DTO 的 `Option` 输出字段都不加 `skip_serializing_if`**（键恒在、值 `null`），因为「缺键」与「值为空」在前端是两种完全不同的语义。

**能力声明侧**：

| 字段 | 类型 | 约束 |
|---|---|---|
| `tab` | 封闭枚举 | `storage` / `processTree` |
| `availability` | 封闭枚举 | §2.4 |
| `reason` | `String \| null` | 键恒在 |

**进程快照侧（`ProcessSnapshotDto`，一张表）**：

| 字段 | 类型 | 约束 |
|---|---|---|
| `sampledAt` | `i64` | 一次遍历一个时刻，实时树与两个合计共用 |
| `rootPid` | `u32` | 采样根，即宿主 PID |
| `memoryBasis` | 封闭枚举 | `workingSet` / `privateWorkingSet`；**口径进 DTO**，前端据此决定是否显示内存合计（§5.6.2）。`pss` 为**保留值**，本期不产出（Windows 无此口径；若将来引入，其可加性见 §5.6.2 约束 5） |
| `memoryAdditive` | `bool` | **内存**这一指标是否可加：`privateWorkingSet` 为 `true`，`workingSet` 为 `false`。标志挂在**快照顶层的指标**上，而非组/视图上（§5.6.2 约束 1）；前端据此决定能否显示内存合计 |
| `memoryEqualsFootprint` | `bool` | 内存合计是否**等于**物理占用：`privateWorkingSet` 为 `false`（近似但不等于），`workingSet` 为 `false`。与 `memoryAdditive` **相互独立**，禁止合并成一个标志（§5.6.2） |
| `cpuBasis` | 封闭枚举 | `singleCorePercent`（可超 100，§5.6.3） |
| `coverage` | 封闭枚举 | `subtreeOnly`：**明确写出「只覆盖本进程子树」**，不是采样失败 |
| `truncated` | `bool` | 遍历是否因深度/数量上限被截断；为 `true` 时**禁止**把结果当完整快照展示 |
| `selfGroup` | `ProcessGroupDto` | 自身合计（`role ∈ {host, webview*}`）的聚合 |
| `subtreeGroup` | `ProcessGroupDto` | 全树合计（全部行）的聚合 |
| `entries` | `Vec<ProcessEntryDto>` | **全部**进程逐条明细，每条带 `role`；一行一进程，`pid` 不重复 |

**`ProcessGroupDto`**：

| 字段 | 类型 | 约束 |
|---|---|---|
| `pidCount` | `u32` | 组内进程数 |
| `memoryBytes` | `u64 \| null` | 按 `memoryBasis` 求和；未声明/未取到该指标时为 `null`，**禁止填 `0`**（键恒在） |
| `cpuPercent` | `f32 \| null` | 按 `cpuBasis` 求和；**首次采样为 `null`，禁止填 `0`**（§9）；CPU 天然可加，不设标志（§5.6.3） |

可加性标志（`memoryAdditive` / `memoryEqualsFootprint`）**不在此处**，上提到 `ProcessSnapshotDto` 顶层：它们是**指标属性**，同一快照内所有组共享，放进组里会导致两个组合计口径可被独立改写（§5.6.2 约束 1）。

**`ProcessEntryDto`**：

| 字段 | 类型 | 约束 |
|---|---|---|
| `pid` / `parentPid` | `u32` | 父子链原值，前端不据此重建树（排序与分组由后端做） |
| `role` | 封闭枚举 | `host` / `webviewBrowser` / `webviewRenderer` / `webviewGpu` / `webviewUtility` / `webviewUnknown` / `otherChild`；决定该行归入哪个合计（§5.2.1）。**全表可见**，不再是「仅自身细分」。`webviewUnknown` 表示「已确认属 WebView 家族但细分读不到」，**仍计入自身合计** |
| `exeName` | `String` | 开放集合，前端兜底不窄化；**不含命令行全文**（命令行可能含凭据） |
| `cpuPercent` | `f32 \| null` | 单核百分比；首次采样或未取到时为 `null`，**禁止填 `0`** |
| `memoryBytes` | `u64 \| null` | 按 `memoryBasis`；未取到该指标时为 `null`，**禁止填 `0`**（键恒在） |
| `threadCount` | `u32 \| null` | 该进程的线程数；取不到为 `null`，**禁止填 `0`**。只交数量，不做线程语义归属（§6.3） |
| `startTime` | `i64` | 进程创建时刻；**必须**随附，用于 PID 复用的可解释性（§7）；同时也是「建父子链」的必需字段（§2.3 约束 4） |

**`SelfUsageReportDto`（外部产物，历史快照）**：

| 字段 | 类型 | 约束 |
|---|---|---|
| `availability` | 封闭枚举 | 只允许 `available` / `staleReport` / `noReportYet` / `unreadable` |
| `generatedAt` | `i64 \| null` | 产物生成时刻；**键恒在、值可为 `null`**（`noReportYet` 时为 `null`） |
| `staleAfterSeconds` | `u64` | 陈旧阈值，与后端判定同源，前端不自己算 |
| `peakMemoryBytes` | `u64 \| null` | 峰值；`null` 表示产物存在但未记录该指标，**不得填 `0`** |
| `peakCpuPercent` | `f32 \| null` | 同上 |
| `sampleCount` | `u32 \| null` | 产物覆盖的采样次数；`null` 表示未记录 |
| `attributionNote` | `String` | 必须非空：说明「这是生成于 X 之前的历史快照，不是当前值」 |

**约束**：`ProcessSnapshotDto` **不含任何任务名、任务状态、停止入口**字段（§5.2.2 收窄后的边界）。`SelfUsageReportDto` **不含任何当前值字段**——当前值只能来自 `get_process_snapshot`（§5.5 两块分离）。

**生成与校验**：改 DTO 后必须跑 `npm run contract:gen` 并提交 `src/types/protocol.contract.ts`；禁止手改生成类型；禁止用 `Record<string, unknown>` 传部分字段。封闭集合用 `enum`，开放集合（如 `exeName`）保留 `String` 且前端兜底不窄化。

### 8.3 前端落点

| 项 | 变更 |

## 9 失败模式

本文只保留跨 tab 的通用条与进程树专属的行。

| 失败模式 | 表现 | 必须的语义 |
|---|---|---|
| **任何 tab 的取数失败** | 取数抛错、命令异常 | 只降级该 tab；**禁止**让一个 tab 的失败连坐另一个 tab（§8.1） |
| 采样阻塞 UI | 全系统快照耗时 | 异步执行；前端有 loading 与上次快照时刻 |
| 能力声明读取失败 | 新命令异常 | 前端降级为「状态未知」并保留上次快照，**不得**默认判为可用 |
| **PID 复用** | 父进程死亡后 PID 被复用，而 `parent_pid` 是**创建时的快照值**、不会更新 | 校验 `child.startTime >= parent.startTime` 且父 PID 确实存活；不通过则**排除该进程并标注**，禁止静默并入子树 |
| 进程在采样中退出 | 遍历期间进程消失 | 该行跳过，不报错；`sampledAt` 后已死的进程允许出现在快照里（快照是时刻值，不是持续状态） |
| **子树遍历被截断** | 深度或数量上限触发 | `truncated: true`，UI 必须显示「本次扫描不完整」；**禁止**把截断结果当作完整快照 |
| **CPU 增量语义未满足** | 只刷新一次就取百分比 | 首次采样 CPU 输出 `null`，**禁止**输出 `0`；间隔取平台最小刷新间隔（§5.8 约束 3） |
| **把「首帧 CPU 为 `null`」当作异常** | 采样由纯拉取 + 缓存 TTL 驱动（§5.8），停表即清缓存，**每次重新打开 tab 都是新一次采样的第一帧** | CPU 为 `null` 是**常态**，UI 显示「本拍无基准，下一拍给出」，**禁止**进入错误态、**禁止**提示「数据加载失败」 |
| **新出现的行立即给出数字** | 子进程刚 spawn、或 tab 刚打开 | 新增进程在**下一个刷新周期之前没有数字**（不是 `0`）；UI 必须能渲染「待定」态 |
| 外部产物不存在 | 从未生成过报告 | `noReportYet`，`generatedAt = null`，给出「如何生成」的说明 |
| 外部产物过期 | 生成时刻早于陈旧阈值 | `staleReport`，仍可显示数字但**必须**带 `generatedAt` 标注 |
| 外部产物损坏 | JSON 解析失败 | `unreadable` + 原因；**禁止**静默退回上一次成功值（会掩盖产物已损坏这一事实） |
| 外部产物只写了一部分 | 进程被强杀，文件截断 | 按损坏处理（`unreadable`）；**禁止**按行补全解析 |

| 停止能力（行级停止按钮） | **需句柄 + 统一回收抽象**（Windows Job Object / Unix `pgid` 已有，缺「MCP 纳入统一回收抽象」与「句柄暴露成标识」，§6.4）。**不依赖登记表**，可独立推进；v1 主动不做（§5.4） | 待立项（`assistant-tools` 回收抽象；与登记表无关） |
| 全机视图（全系统进程表） | 与「子树观测」是不同产品形态，涉及隐私边界与指标按需机制 | §13 OQ5 |

## 13 开放问题

| # | 问题 | 当前倾向 |
|---|---|---|
| OQ1 | 能力声明是否需要缓存 | 不需要。它只返回状态，成本可忽略；缓存反而引入「状态陈旧」这类新问题 |
| OQ2 | 进程树 tab 是否与「工具运行面板」共享组件 | 不共享。工具运行态已在聊天卡片侧交付（I60），两者行模型不同（任务 vs 进程）；强行共用会把 `Task` 语义漏进本 tab |
| OQ3 | 采样 crate 的平台相关单测是否进 CI | 跨平台单测只覆盖「纯逻辑部分」（建父子表、DFS、role 分类、PID 复用校验）；OS 调用层用 trait 隔离，CI 跑 mock 实现 |
| OQ4 | 外部报告产物是否需要 schema 版本号 | 需要。产物由独立二进制写、由主进程读，两者版本可能不一致；无版本号时格式变更会静默解析失败 |
| OQ5 | 进程树是否将来扩展为「全机视图」 | 若扩展，必须重新引入**按需指标机制**（Chromium 的 `selection_masks` 原位掩码）与隐私边界（会看到其他应用的进程名）；本期明确不做 |
| OQ6 | 何时引入指标按需机制（原位掩码） | 只有出现**第二个消费者**（全机视图或任务级归因）时才引入；单 tab 单消费者下它只会增加复杂度（§2.3） |
| OQ7 | WebView 角色是否可用 E14 WebView profile 目录作辅助判据 | 可作辅助，但**不得**作主判据：目录归属依赖 E14 的布局，而角色分类必须自足于命令行特征（§5.2.1） |
