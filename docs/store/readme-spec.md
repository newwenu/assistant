# README 编写规范

| 项 | 值 |
|---|---|
| 状态 | 现行 |
| 日期 | 2026-11-04 |
| 适用 | 仓库根 `README.md`、crate / 子应用 README、`references/` 下自写的参考快照 README |
| 依据 | `references/` 各分组项目的根 README（ChatGPT、goose、OpenBitFun、onepoint、BongoCat、WindowPet、vaultwarden、keyring-rs、rust-keepass、memos、notes、pomatez、stretchly 等）与 `references/3-screen-capture/Cap/README.md` |

> README 是仓库**唯一面向外部读者的入口**。它只回答四件事：这是什么、能做什么、怎么跑起来、细节去哪看。内部迭代过程、决策推演、阶段门禁一律不进 README。

---

## 1 定位与边界

- **读者优先级**：第一次点进仓库的陌生开发者 > 想安装使用的用户 > 要提 issue / PR 的贡献者。三者都要在前 30 秒内找到自己要的东西。
- **信息分层**：README 只放稳定、可公开、跨版本变化慢的信息；架构、决策、迭代规格放 `docs/`，当前迭代放 `docs/store/`，README 只给链接。
- **不暴露内部编号**：I18、I38、P2/P4 等阶段编号属于内部工作流，不进 README。路线图如需展示，单独成节并标注“未发布 / 规划中”。
- **不手写易变数字**：版本号、下载量、star 数交给徽章或链接，不写死在正文里。
- **根 README 与子 README 分工**：根 README 讲产品全貌与统一入口；`src-tauri/crates/*`、子应用 README 只讲该包的能力、依赖边界与示例，不重复根 README 的产品介绍。

## 2 三条硬规则

| 规则 | 要求 | 判据 |
|---|---|---|
| **定位句** | 正文前 15 行内必须有一句（最多两句）说明“这是什么、给谁用” | 遮住标题只看首屏，仍能判断项目性质 |
| **可运行** | 所有安装 / 构建命令能在干净环境直接复制执行，并写明前置条件 | 新机器照抄能跑通，不需要读者自行推断 |
| **可导航** | 每个需要展开说明的话题都给出链接，README 本身保持一屏可扫读 | 读者不需要在 README 里读完架构细节 |

---

## 3 首屏结构（前 15 行）

固定顺序，可整段省略，不可乱序：

1. **品牌区**：居中 logo / 标题 / 一句话 tagline（BongoCat、WindowPet、Pomatez、OpenBitFun 均为此形态）
2. **定位句**：1-2 行，写“是什么 + 解决什么问题”，不写形容词堆砌
3. **关键链接行**：下载 / 文档 / Demo / 社区，用 ` · ` 分隔（memos、OpenBitFun 的做法）
4. **徽章**：平台、许可、构建状态、版本，最多两行
5. **主视觉**：截图 / GIF / 视频，一张即可，避免首屏被图片挤满

首屏之后紧跟分隔线 `---`，把“门面”和“正文”隔开。

---

## 4 正文骨架

| 节 | 要求 | 内容要求 |
|---|---|---|
| 功能 Features | 必须 | 3-7 条；短标题 + 一句解释；写用户可见能力，不写实现细节 |
| 快速开始 Quick start | 必须 | 最短可跑路径：一条安装命令或一个安装包入口 |
| 开发 Development | 桌面 / 库项目应当有 | 前置依赖 + 克隆 + 安装 + 启动 + 常用脚本 |
| 目录结构 | 应当有 | 只列 3-6 个顶层目录，每个一句话职责 |
| 文档索引 | 应当有 | 相对链接 + 一句话说明，指向 `docs/` 下的权威文档 |
| 贡献与社区 | 应当有 | 指向 `CONTRIBUTING.md`、Discussions、即时通讯群 |
| 许可 License | 必须 | 许可名称 + `LICENSE` 链接；多许可要写“任选其一” |
| 截图 / 演示 | 可以 | 放首屏或功能之后；界面用图，不用文字复述 |
| 路线图 / 已知问题 | 可以 | 必须明确“未发布 / 实验性 / 平台限制” |
| 致谢 / 赞助 | 可以 | 放正文后部，不占首屏 |

**排序原则**：

- 产品型（桌面应用）：价值 → 特性 → 安装 → 开发 → 文档 → 许可。
- 库型（crate）：这个库给谁用 → 依赖边界 → 示例 → 许可。keyring-rs 就是先讲“谁该直接依赖、谁该拆依赖”，再讲示例应用。
- 长文档（配置项极多，如 stretchly）：首屏之后立即给目录，再按平台 / 场景分节。

## 5 三种模板

### 5.1 桌面产品型

```
品牌图 / 居中标题
tagline
关键链接行
徽章
主视觉
---
定位段（2-4 行）
功能
快速开始
开发
目录 / 文档
贡献 / 社区
许可
```

适用：根 README、独立子应用。参考 OpenBitFun（能力用表格 + 大图分区）、BongoCat（首屏信息密度高、尾部放 Star history）、WindowPet（下载按平台列包格式）。

### 5.2 库 / crate 型

```
标题（H2 即可，与 crate 名一致）
构建 / 版本 / 文档徽章
定位段：能力 + 适用人群 + 不应直接依赖的场景
示例 / 子模块分节
贡献入口
许可（含贡献授权声明）
```

适用：`src-tauri/crates/*`。参考 keyring-rs（先讲依赖边界，再列示例应用）、rust-keepass（极简下限：标题 + 徽章 + Usage + License）。

### 5.3 参考快照型

本仓库 `references/` 下的自写 README 不是上游 README，必须包含：

| 字段 | 要求 |
|---|---|
| 上游地址 | 原始仓库 URL |
| 快照信息 | 提交哈希 + 日期 + 分支 |
| 许可证 | 上游许可，并注明“仅作阅读参考，不复制代码” |
| 为什么选它 | 用表格把“本项目关心的问题 → 对应上游文件”对齐 |
| 对本项目的结论 | 采纳 / 不采纳的具体理由与替代方案 |

参考 [Cap 参考快照](../../references/3-screen-capture/Cap/README.md)。

## 6 逐节写法细则

### 6.1 标题与定位句

- 标题只写项目名，不加副标题、不加版本号。
- tagline 不超过一行，动词开头或名词短语，例如 “Stay Focused. Take a Break.”。
- 定位句回答“是什么 + 给谁 + 解决什么”，不写“业界领先”“革命性”这类无法验证的词。

### 6.2 功能

- 每条一个能力，格式统一：**能力名**：一句用户收益。
- 不把同一能力的多个子项拆成多条；子项缩进一级（Pomatez 的通知类型、WindowPet 的设置窗口）。
- 不写未发布能力；实验性能力必须带“实验性”标记。
- 功能数量控制在 3-7 条，更多能力交给截图或文档索引。

### 6.3 快速开始 / 安装

- 先给最短路径（安装包或一条命令），再给备选方式（包管理器、容器、源码）。
- 命令块只放命令，输出另起一块；需要持久化目录、端口、环境变量时在同一段说明。
- 平台差异用子标题或表格（memos 的容器命令、WindowPet 的安装包后缀、notes 的数据库路径表）。

### 6.4 开发

- 必须写前置：运行时版本、工具链、平台依赖。
- 命令按“安装依赖 → 启动 → 构建 → 测试 / 检查”顺序排列。
- 常用脚本用单行注释说明用途，注释与脚本同块，便于整段复制。
- 指向更细的构建文档（如 `docs/` 下的构建说明），不在 README 重复。

### 6.5 目录与文档

- 目录树只列顶层，行尾用一句话职责，不列文件清单。
- 文档索引每条：相对链接 + 一句话说明；链接文案用文档名，不用“点击这里”。
- README 中出现的仓库内路径一律为相对路径；禁止本机绝对路径、盘符与 `file://`。

### 6.6 贡献与社区

- 必须指向仓库内的 `CONTRIBUTING.md`；没有该文件就写清 issue / PR 流程。
- 即时通讯群、论坛、Discussions 放在同一节，不散落在各段落。
- 赞助 / 捐赠入口放本节或正文末尾，并注明“自愿”。

### 6.7 许可

- 写许可全名并链接 `LICENSE`；多许可写“任选其一”，并保留贡献授权声明（keyring-rs 的写法）。
- 第三方资源（字体、图标、模型）单独列出来源与许可，不混在项目许可里。

---

## 7 语言与双语

- 根 README 默认中文；技术名词保留原文（Tauri、Rust、SSE）。
- 双语版本文件名固定为 `README.md` + `README.zh-CN.md`（或 `README-CN.md`），首行互相链接。
- 两版**结构一一对应**：节数、顺序、命令一致；只允许语言差异。
- 不能同步维护时删掉另一版，不留半成品；禁止只翻译首屏。
- 同一段落不中英混排；标点跟随所在语言。

---

## 8 排版与链接

| 项 | 规则 |
|---|---|
| 图片 | 必须写 `alt`；本地图放仓库内相对路径，外链图用稳定地址 |
| 徽章 | 必须可点击且指向有效地址；失效徽章直接删除，不保留装饰性徽章 |
| 表格 | 只用于对比（模式、平台、路径、能力矩阵），不用于段落排版 |
| 折叠 | 长列表、FAQ、配置明细用 `<details>`；首屏与核心步骤不折叠 |
| 目录 | 正文超过 5 节时给目录或锚点导航（stretchly 的 Table of contents、Pomatez 的顶部锚点） |
| 代码块 | 标注语言；命令用 `bash` / `shell`，配置用对应格式 |
| 分隔 | 门面与正文之间用 `---`；章节内不滥用分隔线 |
| 强调 | 关键前提用 `> [!IMPORTANT]` / `> [!TIP]`（vaultwarden 的写法），一段最多一个 |

---

## 9 禁止事项

| 反例 | 改法 |
|---|---|
| “业界领先 / 极致体验 / 革命性” | 换成可验证的能力描述 |
| 未实现功能写进“功能” | 移入“路线图”，并标注未发布 |
| 只写 `yarn && yarn start` | 补前置版本、安装、启动三步 |
| 截图无 `alt` | 补上界面用途描述 |
| 死链、失效徽章、指向已删除文档 | 同 PR 内修复或删除 |
| 暴露内部迭代编号与阶段状态 | 删除，或改写为面向用户的能力 |
| 本机绝对路径、`file://` 链接 | 改为仓库内相对路径 |
| 一段里塞多个主题 | 拆成小节或表格 |
| 下载量 / 版本号写死在正文 | 改用徽章或链接 |
| README 复制架构文档内容 | 保留摘要 + 链接到 `docs/` |

---

## 10 维护规则

- 新增或删除用户可见功能时，同 PR 更新“功能”节。
- 新增 npm 脚本、构建命令、平台依赖时，同 PR 更新“常用脚本”与“开发”。
- 文档改名、移动、删除时，同 PR 更新 README 内所有链接。
- 发版前按 §11 自检；不通过不发版说明。
- README 的改动不涉及代码契约，不需要 `npm run contract:gen`。
