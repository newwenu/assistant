## 0 一个 token 数必须回答四个问题

任意一个「token 数」只有在四个维度都固定时才有唯一含义，缺任一个就会产生歧义。这是本仓库所有 token 混乱的总根源。

| 维度 | 取值 | 缺失时的后果 |
| --- | --- | --- |
| **范围** | 单次请求 / 一轮 / 整个会话 | 分不清 7k 与 120k 描述的是同一段对话 |
| **方向** | 输入 / 输出 / 合计 | 把生成的 completion 计入「还能装多少」 |
| **可信度** | provider 上报 / 本地估算 | 精确值与估算值被同一个 `SUM` 相加 |
| **用途** | 容量（还能装多少）/ 账单（花了多少）/ 构成（花在哪） | 用累计值填占用位，进度条瞬间打满 |

本仓库的 9 个量，就是这四维上的 9 个坐标点。下文每个量都标注这四个坐标。

## 1 九个量的坐标与定义

前 6 个是彼此独立的口径，后 3 个是「已包含在别的量里」的子集量，**不可与前者相加**。

| 符号 | 四维坐标（范围·方向·可信度·用途） | 计算式 | 定义域 |
| --- | --- | --- | --- |
| `W` 上下文窗口 | 会话级·输入+输出·常量·容量 | 模型配置 `models_json.contextWindow` | > 0；未知时为 `NULL` |
| `O` 上下文占用 | 请求级·输入·上报·容量 | `P(n)`，见 §3.1 | ≥ 0 |
| `P` 单次输入 | 请求级·输入·上报·构成 | provider 上报的 `prompt_tokens` | ≥ 0 |
| `C` 单次输出 | 请求级·输出·上报·构成 | provider 上报的 `completion_tokens` | ≥ 0 |
| `A` 会话累计 | 会话级·合计·上报+估算混合·账单 | `Σ(P + C)`，见 §3.3 | ≥ 0 |
| `r` 占比 | 请求级·比值·派生·容量 | `O / W` | `[0, 1]`，clamp |
| `CR` 缓存命中 | 请求级·输入子集·上报·构成 | provider 上报，各系字段不同 | ⊆ `P` |
| `CW` 缓存写入 | 请求级·输入子集·上报·构成 | 仅 Anthropic 系 | ⊆ `P` |
| `RT` 推理 | 请求级·输出子集·上报·构成 | Gemini 上报；其余未解析 | ⊆ `C` |

### 1.1 每个量「不是什么」

定义的价值一半在于排除。下表逐项给出反义，用于代码评审与文案审核：

| 量 | 它**不是**什么 | 为什么容易误认 |
| --- | --- | --- |
| `W` | 不是「已用量」，不是「剩余量」，不是「花费」 | 中文「上下文窗口总 token 花费」把三个量拼成一个短语 |
| `O` | 不是累计值，不是本地求和结果 | 二者在单轮会话中数值相同，n 轮后差 n/2 倍（§3.2） |
| `P` | 不含 `C`；`CR`/`CW` 已含在其中，不能相加 | provider 各系对 `prompt` 是否含缓存的处理不同（§4） |
| `C` | 不是「占用的增量」；Gemini 的 `C` 已含 `RT` | 窗口同时约束输入与输出，但输出不预占下一次输入 |
| `A` | 不是「当前占了多少」，不能进进度条 | 它是账单，与 `W` 无因果关系 |
| `r` | 不是「剩余比例」，不是「消耗进度」 | codex 报的是 *remaining*，本仓库报的是 *used*（§5） |
| `CR` | 不是「省下的 token」，不是「免费部分」 | 它已计入 `P`，只是计价更低 |
| `CW` | 与 `CR` 不是同一件事，不能合并成「缓存总量」 | 写缓存通常比读缓存更贵 |
| `RT` | 不能与 `C` 相加 | 已含在 `C` 内 |

### 1.2 中文短语的三重歧义

「上下文窗口总 token 花费」这句话在中文里被用来指三件事，必须按语境拆分：

| 想表达 | 实际指向 | 判据 | 数量级（128k 窗口、10 轮） |
| --- | --- | --- | --- |
| 这个模型能装多少 | `W` | 与内容无关，只查模型配置 | 128,000 |
| 现在装了多少 | `O` | 与轮次**线性**相关 | ≈ 20,000 |
| 一共花了多少 | `A` | 与轮次**平方**相关 | ≈ 120,000 |

三者相差一个数量级。同一句话里出现「窗口」与「花费」，字面自相矛盾——窗口是容器，花费是流量。文案应改用「窗口占用」或「累计消耗」。

### 1.3 未知窗口的三种错误表达

`W` 未知是合法状态：模型配置没填、provider 未声明、会话尚未发过请求。它必须保持「未知」，三种常见替代写法都会产出一个**看起来合理但错误**的分母：

| 错误写法 | 表现 | 后果 | 参考项目中的实例 |
| --- | --- | --- | --- |
| 用 `0` 冒充未知 | 字段为 `0` | `O / 0` 必须特判；特判成 0% 等于「窗口无限」，特判成 100% 等于「已满」 | openhuman 后端 `context_window: 0`，前端再兜底 200k |
| 用旧值粘住未知 | 沿用上一次已知窗口 | 切模型后仍按旧窗口算分母，进度条长期错误 | openhuman 前端仅在 `ctxWindow > 0` 时覆盖 |
| 用硬编码兜底 | 缺省填 128k | 未知模型永远显示 128k，压缩阈值与 offload 预算也按 128k 算 | OpenBitFun 转换期 `unwrap_or(128_128)` |

正确写法：`W` 未知 → `NULL` / `undefined`，派生量 `r` 返回 `None`，UI 退化为显示绝对 token 数（§5.1）。

「用旧值粘住」与「用 `0` 冒充」是同一类错误的两个方向：前者让未知被**旧的已知值**掩盖，后者让未知被**合法数字**掩盖。两者都违反同一条不变量——**未知必须能覆盖已知**。

## 2 恒等式

### 2.1 provider 层（跨 provider 恒成立）

```
(1) CR ⊆ P
(2) CW ⊆ P            （仅 Anthropic 系有值，其余未上报）
(3) RT ⊆ C            （Gemini 归一化后；其余 provider 未解析）
(4) uncached = max(P - CR - CW, 0)
(5) requestTotal = P + C
```

注意 (1) 与 (4) 的关系：`CR` 是 `P` 的子集而非附加项，所以 `uncached` 必须**相减**得到，不能把 `CR` 当成额外消耗。不同 provider 对 `P` 是否含缓存的处理不一致，归一化职责就在这一层（§4）。

### 2.2 派生量

| 派生量 | 计算式 | 边界处理 |
| --- | --- | --- |
| `uncached` | `max(P - CR - CW, 0)` | 下限 0，防止 provider 上报矛盾时出现负数 |
| `requestTotal` | `P + C` | 优先用 provider 的 `total_tokens`，缺失时才相加 |
| `r` | `clamp(O / W, 0, 1)` | `W` 未知时返回 `None`，不返回 0 |
| `cacheHitRatio` | `ΣCR / ΣP`，**仅统计已上报缓存的请求** | 分母为 0 返回 `None`，不返回 0 |
| `A` | `Σ(P + C)`，含重试与压缩请求 | 无记录返回 `None`，不返回 0 |

`cacheHitRatio` 的分母必须只含「provider 明确上报过缓存字段」的请求，否则不支持缓存的 provider 会把命中率稀释成 0。判断「是否上报」用**任一缓存字段非空**，而不是只看 `CR`——只报写缓存的 provider 会被错误排除。

## 3 计算式与推导

### 3.1 上下文占用的定义式

```
O(n) = P(n)
     = tokens(system prompt)
     + Σ tokens(活跃分支消息，排除 compact_summary)
     + Σ tokens(附件投影：图片块 / 文件块 / 占位文本)
     + provider 自身框架开销（role 包装、分隔符，无法本地计算）
```

「上一次请求的 `P`」是 `O` 的唯一可信来源，因为服务端每次都会把整段历史重新计一遍——`P(n)` 本身就等于「下一次请求要发送的历史」。本地无法复现分词，因此任何本地求和都只是近似。

### 3.2 为什么累计值不能当占用：`A / O ≈ n / 2`

设：

- `S` = 首轮请求的固定部分（system prompt + 首条用户消息）
- `d` = 每轮新增**输入**（用户消息 + 工具结果，不含模型输出）
- `c` = 每轮**输出** token

每轮历史净增长是 `d + c`，因此第 k 轮请求的输入：

```
P(k) = S + (k-1)·(d + c)
```

于是：

```
O(n) = P(n) = S + (n-1)·(d + c)                ← 线性
A(n) = Σ_{k=1..n} P(k) + n·c
     = n·S + (d+c)·n(n-1)/2 + n·c              ← 平方项
```

n 较大时主导项之比：

```
A(n) / O(n) → [(d+c)·n(n-1)/2] / [(n-1)·(d+c)] = n/2
```

**结论**：`A / O ≈ n/2`。轮次越多，两者差得越远，且差距是**平方级**而非固定倍数。

具体到 128k 窗口、`S = 2k`、`d = 1k`、`c = 1k`（即每轮净增 2k）：

| n | `O(n)` | `A(n)` | `O/W` | `A/W`（错误用法） | `A/O` |
| --- | --- | --- | --- | --- | --- |
| 1 | 2,000 | 3,000 | 1.6% | 2.3% | 1.5 |
| 5 | 10,000 | 35,000 | 7.8% | 27.3% | 3.5 |
| 10 | 20,000 | 120,000 | 15.6% | **93.8%** | 6.0 |
| 20 | 40,000 | 440,000 | 31.3% | **343.8%** | 11.0 |

第 10 轮时真实占用只有 15.6%，而 `A/W` 已经 93.8%——这正是「切换会话后进度条瞬间打满」的算术原因。注意最后一列 `A/O` 趋近 `n/2`，与推导一致。

> `A/W` 这一列是**错误用法**的演示，不是任何合法口径。`A` 与 `W` 之间不存在可解释的比值。

### 3.3 累计式的正确写法

```
A = Σ_{所有请求} (P + C)
```

「所有请求」必须包含三类常被漏掉的：

1. **失败重试**的 attempt（每次带 usage 的请求都算真实消耗）
2. **压缩请求**本身（一次压缩可能吃掉整个窗口的输入）
3. **子代理**请求（若未来引入；当前无此概念）

### 3.4 本仓库现有的三个估算式

| # | 位置 | 公式 | 单位 | 作用对象 |
| --- | --- | --- | --- | --- |
| E1 | `assistant-agent/src/chat_runtime.rs` `estimate_tokens` | `ceil(len/4) + 4` | 字节 | 无 usage 时的消息 `tokens` 回退 |
| E2 | `assistant-agent/src/request_projection.rs` | 文本 `len/4`；图片固定 `765`；文件已缓存 `len/4`；文件未缓存 `20` | 字节 / 固定值 | offload 预算判定 |
| E3 | `assistant-storage/src/agent_modes.rs` | `COALESCE(tokens, ceil(len/4) + 4)` 后求和 | 字节 | 会话占用聚合（错误用法） |

E1 与 E3 的公式相同（E3 的 SQL 版就是 E1），所以「同一段文本在落库时估算一次、在聚合时再估算一次」，两条路径的数值一致但含义不同：前者是「这条消息的估算」，后者被当成「会话占用」。

### 3.5 估算误差的方向与量级

`len / 4` 隐含「4 字节 ≈ 1 token」。这个假设对不同字符集的偏差是**单向**的：

| 内容 | 实际密度 | `len/4` 估算 | 偏差 |
| --- | --- | --- | --- |
| 英文散文 | ≈ 4 字符/token ≈ 4 字节/token | 1 token / 4 字节 | 基本准确 |
| 中文 | 1~1.5 token/字，1 字 = 3 字节 | 0.75 token/字 | **低估 25% ~ 50%** |
| JSON / 代码 | 标点与括号各占独立 token，约 2~3 字节/token | 1 token / 4 字节 | **低估 25% ~ 50%** |
| Emoji | 4 字节，常占 2~4 token | 1 token | 低估 |

偏差方向恒定偏低估，因此不同用途的后果各不相同：

| 使用点 | 低估的后果 |
| --- | --- |
| offload 预算（E2） | 该降级时不降级，请求可能被 provider 以超长拒绝 |
| 无 usage 的 `tokens` 回退（E1） | 该条消息在账单里偏小 |
| 会话聚合（E3） | 分子偏小，百分比偏低，压缩判定偏晚 |
| 压缩触发 | **不受影响**——它用 provider 上报的 `P`，不用估算 |

图片的固定 `765` 是**每张图的固定价**，与实际像素无关：10 张图恒为 7,650，无论分辨率高低。真实成本由 provider 的 tile 切分规则决定（本仓库未建模），因此高分辨率图片会被系统性低估。

各参考项目的估算约定不同，差异不在系数大小，而在**分母单位**——按字节还是按字符：

| 实现 | 分母单位 | ASCII 密度 | 非 ASCII 密度 | 结构开销 |
| --- | --- | --- | --- | --- |
| 本仓库 E1/E3 | 字节 | 1 token / 4 字节 | 中文 0.75 token/字 | 每条消息 +4 |
| OpenBitFun `TokenCounter` | 字符 | 0.3 token/字符 | 0.6 token/字符 | 每条消息 +4 |
| deepseek-harness-orb `estimate.ts` | 字符（JS `length`，UTF-16 码元） | `CHARS_PER_TOKEN = 4` | 中文 0.25 token/字 | 每 block +4，每消息 +4 |
| openhuman `prompt_size.rs` | 字节 | `EST_BYTES_PER_TOKEN = 4` | 未区分 | 无（仅展示用，源码注释明确声明「是除数，不是分词器」） |
| codex | 不做字符估算 | — | — | 改用 `BASELINE_TOKENS = 12_000` 直接修正窗口 |

按字符计价对 CJK 的偏差比按字节更极端：orb 用 JS `length`，一个中文字符只算 0.25 token，是真实密度（1~1.5）的四分之一到六分之一；本仓库按字节算 0.75，仍是低估但幅度小些。这说明**只要用字符/字节估算，CJK 一定被低估**，差别只在于低估多少。openhuman 的处理最保守：它把字节作为记账单位，估算值只用于人类阅读，明确拒绝把估算当账。

四种处理里只有 openhuman 的做法可以直接采纳为规则：**估算值不参与任何需要精确的判定**。本仓库当前违反这条——`offload` 预算与 `SUM` 聚合都在用估算值做判定（见上表）。各项目的修正 / 规避策略对比见 `token-usage-analysis.md` §6。

### 3.6 复合计算的误差传播

估算误差在复合式中不是可加的，而是**混合**的：

```
A = Σ(有 usage 的请求 → 精确 P+C)
  + Σ(无 usage 的请求 → 估算)
```

聚合结果既不是精确值，也不是一致低估，而是「一部分精确、一部分低估」的混合量纲。这正是 `SUM` 口径无法自洽的根本原因：它不是「算错了」，而是**分子里混了两种可信度**。

## 4 Provider 归一化对计算的影响

`P` 的构成随 provider 变化，因此所有基于 `P` 的派生量都必须先归一化再计算。

| Provider | `P` 是否含缓存 | 缓存字段 | `C` 是否含推理 | 推理是否单列 | `requestTotal` 来源 |
| --- | --- | --- | --- | --- | --- |
| Anthropic | 是（本地求和 `input + cache_read + cache_creation`） | `cache_read_input_tokens` / `cache_creation_input_tokens` | 是（thinking 计入 `output_tokens`） | 未上报 | 本地求和 |
| OpenAI Chat Completions | 是（`prompt_tokens` 含 `cached_tokens`） | `prompt_tokens_details.cached_tokens`、`prompt_cache_hit_tokens` | 否（details 未建模） | 未解析 | 优先 provider `total_tokens` |
| OpenAI Responses | 是 | `input_tokens_details.cached_tokens` / `cache_write_tokens` | 未单列 | 未提取 | provider |
| Gemini | 是（`prompt_token_count` 含 `cached_content_token_count`） | `cached_content_token_count`（`CW` 无写入路径，恒未上报） | 是（`thoughts_token_count` 已并入 `candidates_token_count`） | 上报 | provider |

归一化后 §2.1 的五个恒等式才成立。当前运行时的 `StreamAccumulator` 自行计算 `total = P + C` 并丢弃 provider 的 `total_tokens`，因此 (5) 在本仓库是「本地定义」而非「provider 事实」——与官方账单可能存在小数级差异。

## 5 阈值计算：分子、分母、方向都不能混用

「什么时候该压缩」取决于 `O` 与 `W` 的关系，但四个项目各自扣减了不同东西，导致同一窗口下的实际阈值差别很大。

| 项目 | 分子 | 分母 | 触发条件 | 128k 窗口下的实际阈值 |
| --- | --- | --- | --- | --- |
| 本仓库 | `P`（上报） | `W`（完整窗口） | `P >= W * 80%` | 102,400 |
| OpenBitFun | `total_tokens`（占用投影） | `input_limit = W - output_reserve - 10_000` | `>= input_limit`，并在 `input_limit - 10_000` 起预取 | 约 86,000（`max_tokens` 未设时预留 32k）；`W` 由 `unwrap_or(128_128)` 填充，未知即按 128k 算 |
| codex | `last_token_usage.total_tokens`（**含输出**） | `effective_window = W - 12_000` | 展示 *remaining* 百分比，非触发 | 116,000 |
| openhuman | `last_turn_input_tokens`（**仅输入**） | `W`，`0` 表示未知，前端再兜底 `200_000` | 未在已核对模块中涉及 | 兜底值参与分母（§5.1） |
| deepseek-harness-orb | `pressureTokens = inputTokens + CR + CW`（**仅输入**） | `contextWindow` | `token-meter` 只产出投影，不含阈值 | — |

orb 的 `inputTokens` 是**未缓存输入**，缓存量另行相加，所以 `pressureTokens` 与本仓库的 `P` 等价——两个项目的 `P` 定义不同（本仓库 `P` 已含缓存），横向比较时不能直接对同名符号套用同一公式。

三条可直接吸收的计算含义：

1. **分子是否含输出，是两种合法但不可混用的口径。**
   - 输入口径（openhuman / orb / 本仓库）：回答「下一次请求要发送多少」
   - 含输出口径（codex）：回答「上一次请求一共占了多少」

   两者在同一轮内相差一个 `C`。文档与实现必须择一并声明，不能在定义处用输入口径、在画进度条时用含输出口径。

2. **分母必须扣掉输出预留。** 窗口同时约束输入与输出，若不扣 `max_tokens`，阈值会偏乐观约 `max_tokens + 安全裕度`。OpenBitFun 用 `W - output_reserve - 10k`，codex 用 `W - 12k`，本仓库用完整 `W`——这是本仓库阈值偏晚的直接原因。

3. **百分比的方向要写清。** codex 展示 *remaining*（剩余），本仓库展示 *used*（已用）。两者互补，`used + remaining = 1`，混用会让「越大越危险」与「越大越安全」同时成立。

### 5.1 窗口未知时的分母处置

`W` 未知时四家分成两派，取舍与代价如下（错误写法的分类见 §1.3）：

| 项目 | 未知的表达 | 未知时的行为 | 硬编码兜底 | 副作用 |
| --- | --- | --- | --- | --- |
| codex | `Option<i64>`，线上为 `null` | 不显示百分比，改显示绝对 token 数；**百分比与绝对数互斥** | 无 | 状态栏另走一条路，未知时按「剩余 100%」显示，与 composer 口径不一致 |
| deepseek-harness-orb | 字段整体**省略**（不写 `null` 也不写 `0`） | 新事件不带窗口时**主动删除旧值**，只留绝对量 | 无 | 无，四者中最一致 |
| openhuman | `0` 哨兵 | 后端跳过预算裁剪；前端粘住旧值，最终兜底 200k | **有**（`200_000`） | 后端注释写明「未知不要猜」，但 DTO 边界把它压成 `0`，猜的责任转嫁给 UI |
| OpenBitFun | `Option<u32>`，配置里的 `0` 归一化为 `None` | `ratio = 0`，不触发压缩 | **有**（`128_128`） | 转换期 `unwrap_or` 填死后，运行时 `context_window == 0` 分支成为死代码 |

本仓库采纳 codex 与 orb 的路线：`W` 未知 → 不画进度条、只显示绝对 token 数（`token-usage-ui-spec.md` §4.4）。三条理由：

1. **分母未知时，任何比例都是伪精度。** 百分比的可信度完全由分母决定，分母是猜的，分子再准也说明不了「还能装多少」。
2. **未知必须能覆盖已知。** orb 的 fold 逻辑证明这不是理论问题：换模型后新路由不声明容量时，旧容量必须被删除，否则进度条按旧分母长期算错。本仓库的 A8（切会话先写 128k 再覆盖）是同类错误的反面样本。
3. **兜底常量会把错误从展示扩散到行为。** `W` 不只用于展示，还用于压缩阈值与 offload 预算（上文第 2 条）。一个假的 128k 同时污染三处判定，而不只是多画一根条。

## 6 误算清单

与 `token-usage-analysis.md` 的 A1–A13（现象）和 `token-usage-ui-spec.md` 的 P/W/Q/F（代码事实）互补：本节只记**计算层的错误算法**。

| 编号 | 错误算法 | 会算出什么 | 错在哪 | 正确算法 |
| --- | --- | --- | --- | --- |
| M1 | `O = Σ(messages.tokens)` | 第 10 轮得 120k（93.8%） | 用 `A` 冒充 `O` | `O = 最新请求的 P` |
| M2 | `r = (P + C) / W` 但定义为输入口径 | 比真实多一个 `C` | 分子分母口径不一致 | 分子与分母选同一口径并声明 |
| M3 | 估算值覆盖上报值，或估算值未标记就进 `O` | 分子偏小 25%~50%，且无法与精确值区分 | 混入第二种可信度 | `O` 优先用上报值；仅在整条链路无上报时以估算兜底，且必须置 `estimated` 标记 |
| M4 | 用 `0` 表达「未上报」 | 命中率被稀释、`W` 显示 128k | 零是合法取值，与未知混淆 | 用 `NULL` / `undefined` |
| M5 | 命中率分母 = 全部请求的 `P` | 未支持缓存的 provider 拉低命中率 | 分母未筛选 | 分母只含「任一缓存字段非 `NULL`」的请求（只判 `CR` 会漏掉仅报写缓存的 provider） |
| M6 | 压缩后沿用压缩前的 `O`，不重新取锚点 | 若压缩确实改写了出站，占用会长期虚高 | 锚点未跟随出站构成变化 | 压缩请求自身的 `P` 即新锚点。**本仓库压缩不缩减出站**（摘要被过滤，见 `token-usage-analysis.md` §3.4），故 `O` 确实不变；此条对「压缩真能缩短历史」的实现才成立 |
| M7 | 重试 attempt 覆盖而非替换 | 重复消耗从 `A` 中消失 | 混淆「快照」与「增量」 | `A` 累加，`O` 取最新 |
| M8 | 阈值不扣输出预留 | 阈值偏晚约 `max_tokens` | 分母用了完整窗口 | `W - output_reserve - 安全裕度` |
| M9 | `r` 不 clamp | 出现 343% 这类值 | 分母口径错误时未兜底 | `clamp(O/W, 0, 1)`，`W` 未知返回 `None` |
| M10 | 压缩请求的 usage 丢弃 | `A` 少一整轮输入 | 压缩也是真实请求 | 落一条 `kind = compaction` 记录，只进 `A` |
| M11 | 窗口未知时沿用上一次已知的 `W` | 切模型后按旧分母算比例，长期错误且无任何提示 | 未知被旧值掩盖（§1.3） | 未知必须能覆盖已知：新上下文未声明窗口即清空为 `NULL`，不回退到旧值 |

## 7 术语禁令

| 禁用写法 | 冲突原因 | 应改为 |
| --- | --- | --- |
| `totalTokens` 单独出现 | 既可指本请求 total，也可指会话累计 | `requestTotalTokens` / `cumulativeTokens` |
| `usedTokens` 指累计值 | 与「占用」语义冲突 | `cumulativeTokens` |
| 「上下文窗口总 token 花费」 | 窗口与花费是两个量，字面矛盾 | 「窗口占用」或「累计消耗」 |
| 裸 `tokens` 指整轮 `P + C` | 易被读成「这条消息自己的 token」 | `requestTotalTokens`，并标注为整轮口径 |
| 「缓存节省了 N token」 | `CR` 已含在 `P` 内，不是额外节省 | 「其中 N token 命中缓存」 |
| 「压缩释放了上下文」 | 压缩不缩减出站构成 | 「已存档」 |
| 「剩余 93%」与「已用 93%」混用 | 方向相反 | 明确 `used` / `remaining` |
| 窗口未知时显示「剩余 100%」「已用 0%」 | 把未知当成「一点没用」，与真实状态无关 | 显示绝对 token 数，不显示比例（§5.1） |
