# 代码审查原则

> 性质：**工程原则**｜适用范围：前端、后端、脚本、构建与配置
> 本文件自足：术语、维度、依据、要求、违例形态全部在此陈述，不依赖也不引用其它规则文档；审查流程、证据格式、严重性分级、报告模板、验证命令与具体文件落点不属于原则，不在本文件出现。

---

## 1 术语与使用约定

### 1.1 术语

| 术语 | 含义 |
|---|---|
| 命令层 | 前端可调用的 Tauri 命令薄壳：解包、校验、调用、错误映射、发事件；不含业务编排。 |
| 编排层 | 组织多步领域调用、流消费与状态推进的层；不直接暴露给前端。 |
| 状态层 | 前端唯一可信的会话、设置与流状态，以及其写入入口。 |
| 跨进程调用 | 前端经 Tauri `invoke` 进入 Rust 命令层的调用及其返回。 |
| 流事件身份 | 后端为一次流式响应生成的标识，用于归属增量、终止与取消事件。 |
| 持久化身份 | 消息、会话等落库后的稳定标识；不得用作流事件归属键。 |
| 契约 | 跨进程 DTO、生成类型与事件载荷的唯一来源。 |
| 活跃文档 / 归档文档 | 活跃文档指 `docs/store/`、`docs/analysis/` 等仍在维护的文档；归档文档指 `docs/archived/` 等冻结文档。 |

### 1.2 使用约定

1. 维度编号稳定，不得复用或重排；新增维度一律追加为 D16、D17…，归入最贴切的分组，分组不再维护连续区间，既有引用不失效，并同步更新 §2 索引与 §8.3 速查表。
2. 每个维度先给**依据条目**（标注强/中/弱），再给要求与违例形态：要求用「必须 / 不得 / 禁止」陈述，能给出可观察违例的追加「即为缺陷」。
3. 依据必须能在第 8 章找到对应条目及其成立前提；第 8 章未收录的依据不得使用。正文只引用条目名称；第 8 章的速查表是派生索引，不作为判定来源。
4. 本文件只回答「审什么」；具体缺陷清单、实施步骤与排期不属于本文件。

## 2 维度分组与索引

- **A 正确性与契约（D1–D3）**：主路径之外会不会错、跨层语义是否一致、失败是否可判定。
- **B 结构与演进（D4–D6、D16）**：职责归属是否清晰、改动是否收敛、文档是否仍兑现、变更集是否干净。
- **C 运行时可靠性（D7–D10）**：时序、生命周期、持久化、资源占用。
- **D 风险与保障（D11–D15）**：安全边界、供应链、测试可信度、门禁、平台与国际化。

分组区间只描述当前编号；新增维度按 §1.2 追加，不要求维持区间连续。

| 维度 | 名称 | 一句话判据 |
|---|---|---|
| D1 | 功能正确性与边界条件 | 异常输入、非法状态、重放、取消与边界计算是否都有确定行为。 |
| D2 | 类型与契约 | 契约是否单一来源、两端策略是否一致、调用是否类型化。 |
| D3 | 错误处理与可观测性 | 失败是否可分类、可感知、可追踪，敏感信息是否外泄。 |
| D4 | 架构与职责边界 | 依赖是否单向、命令层是否薄壳、是否存在双实现与环。 |
| D5 | 一致性与可读性 | 命名、常量、重复块、注释是否收敛到单点。 |
| D6 | 文档与代码一致性 | 活跃文档、规格状态、示例是否仍与代码一致。 |
| D7 | 并发 / 异步 / 时序 | 取消、归属、锁、超时、订阅清理是否有界且成对。 |
| D8 | 状态与资源生命周期 | 状态写入是否唯一、重置是否完整、资源是否对称释放。 |
| D9 | 数据持久化与迁移 | 迁移是否幂等、写入是否原子、单位是否统一。 |
| D10 | 性能与资源占用 | 列表、高频更新、主线程、内存峰值与 N+1 是否受控。 |
| D11 | 安全与隐私 | 信任边界、明文暴露、注入、CSP 与最小权限是否守住。 |
| D12 | 依赖与供应链 | 依赖必要性、版本收敛、许可、锁文件与特性隔离是否成立。 |
| D13 | 测试策略 | 关键链路、层级分工、可重复性与回归测试是否可信。 |
| D14 | 构建与质量门禁 | 零告警、契约校验、可重复构建与本地流水线是否一致。 |
| D15 | 平台兼容与国际化 | 平台差异、路径、文案、缩放、可访问性与时区格式是否统一抽象。 |
| D16 | 变更卫生 | 变更集是否只含目标相关改动、是否可独立回滚与独立验证。 |

## 3 A 正确性与契约

### D1 功能正确性与边界条件

依据：ISO/IEC 25010 质量模型的「功能适合性」（中）；OWASP ASVS 与风险清单的 V5 输入校验（中）。

- 空值、超长、并发、重复提交、部分失败必须各有确定行为；只处理主路径、分支为空或静默返回即为缺陷。
- 非法状态转移必须在状态层拒绝；靠 UI 隐藏入口、或用多个布尔量组合出互相矛盾的状态即为缺陷。
- 重放路径（重试、事件重投、重复点击）必须幂等或显式阻断；产生重复副作用即为缺陷。
- 长任务（流式输出、迁移、导出）必须有取消与超时，取消后必须回到一致态；取消信号无人检查、超时缺失即为缺陷。
- 跨层语义必须一致且可判定；单位、时区、编码、默认值只靠字段名约定，或用默认值兜底到无法区分「无数据」与「失败」，即为缺陷。
- 边界计算（分页、截断、预算、序号）必须有边界用例；依赖隐式假设、出现差一或溢出即为缺陷。

### D2 类型与契约

依据：消费者驱动契约测试（中）；模式生成链（强）；序列化属性与严格模式（强）；Rust API Guidelines 与 Clippy 分组的 C-CONV（强）。

- 契约必须单一生成来源，生成物禁止手改；提交内容与生成结果不一致即为缺陷。
- 可选字段、未知字段、封闭集合与开放集合必须有明确策略且两端一致；输入含未知字段必须拒绝、输出可选键被序列化省略导致前端缺键即为缺陷。
- 跨进程调用必须使用类型化返回（如 `invoke<T>`）；新增强制断言、双重断言、以宽泛字典类型传递部分字段即为缺陷；既有例外必须逐条登记并写明理由。
- 传输类型不得承载本地 UI 状态，本地扩展必须用交叉类型叠加；UI 标志混入传输结构即为缺陷。
- 事件载荷必须是结构化且可校验的类型；两端各写一遍结构、或枚举字面量双份维护即为缺陷。
- 同一字段不得在不同层有双重解释；出现即为缺陷。

### D3 错误处理与可观测性

依据：OWASP ASVS 与风险清单的 V7 日志与监控（中）；Rust API Guidelines 与 Clippy 分组的 C-GOOD-ERR（强）；12-Factor 的「日志作为事件流」（中）。

- 失败分支必须归入四类之一：可恢复（自动重试或降级）、需用户决策（给出具体动作）、应上报（保留上下文）、可降级（明确降级语义）；分类重叠时按用户可执行的动作优先归类。空捕获、只写调试级别日志、吞掉有意义的返回结果即为缺陷。
- 失败必须用户可感知并给出与类别匹配的动作；在必然失败的类别上提供「重试」即为缺陷。
- 日志必须带上下文与关联标识；无法串起一次链路即为缺陷。
- 敏感信息禁止进入日志、错误消息、事件载荷与崩溃转储；出现令牌、密码、完整敏感路径即为缺陷。
- 错误边界必须覆盖懒加载与路由级组件；缺失即为缺陷。
- 后端错误映射必须保留可判定信息；统一成泛化文案、丢失原始上下文即为缺陷。

## 4 B 结构与演进

### D4 架构与职责边界

依据：Clean Architecture 依赖规则与稳定依赖原则（中）；Tauri 安全模型的命令暴露面最小化（中）；Rust API Guidelines 与 Clippy 分组的 C-VIEW 与 unsafe 文档条目（强）；设计哲学类著作与重构经验模式（弱，仅用于提问，不作判定）。

- 依赖必须单向；出现反向语义边或跨层直达调用即为缺陷。
- 命令层必须是薄壳：解包、校验、调用、映射错误、发事件；出现提示词构建、流消费、落库即为缺陷。
- 状态层必须保持纯状态；在状态动作内串联多步跨域调用即为缺陷。
- 多实现模块必须遵循「核心封闭 / 实现自治 / 编排半封闭」，扩展只改注册表；新增同类能力复制旧实现即为缺陷。
- 同一能力不得存在两套并行实现（双封装、双驱动、双解析）；出现即为缺陷。
- 不得存在只写不读字段、无消费方的重复副本、已下线但仍被引用的路径；存在即为缺陷。
- 模块之间不得成环；为打通环把函数塞回上层聚合文件、使其反而成为最大文件即为缺陷。
- 平台层 `unsafe` 必须集中并带 `SAFETY` 注释说明不变量；散落到业务层、或无注释即为缺陷。
- 对外可见面必须收敛到最小：跨 crate 使用才允许 `pub`，同 crate 内优先 `pub(crate)` / `pub(super)`；无消费者的 `pub`、仅为测试放开可见性即为缺陷。

### D5 一致性与可读性

依据：Rust API Guidelines 与 Clippy 分组的 C-NAME、style、complexity（强）；零告警门禁与格式化工具（强）；Google 代码审查实践指南（中）；设计哲学类著作与重构经验模式（弱，仅用于提问）。

- 命名必须对齐同目录既有先例；同义异名即为缺陷。
- 常量与字面量必须单点定义；目录名字面量、协议字符串、尺寸常量散落即为缺陷。
- 近似重复块必须收敛差异点为参数；但变化原因不同的相似代码不得合并（合并会制造耦合），无条件合并即为缺陷。
- 函数与组件必须按步骤组织；超深嵌套、提前返回缺失即为缺陷。
- 注释必须解释「为什么」；复述「做了什么」、与代码行为不一致、无主 TODO 即为缺陷。
- 风格争议必须交给格式化与静态检查；人工争论风格即为流程缺陷。
- 调试残留不得进入主干：`dbg!`、`println!`、`console.log`、被注释掉的代码块、临时开关与临时放宽规则即为缺陷。

### D6 文档与代码一致性

依据：12-Factor 的 Factor III 配置外置（中）；模式生成链的生成 + 校验漂移检测（强）。

- 活跃文档（不含 `docs/archived/` 等归档）声明的模块职责、链路、配置项必须与代码一致；声明已实现而代码不存在、或代码新增未进活跃文档即为缺陷。
- 规格标注的状态（进行中 / 已归档）必须与实现相符；声明「已实现」而代码缺失、已下线路径仍被引用即为缺陷。进行中的规格不要求代码已存在，但实现漂移必须显式记录。
- 新增的模块、命令、配置项、事件必须补进对应活跃文档；删除项必须反向清理；缺失即为缺陷。
- 同一规则不得在多份活跃文档重复陈述；各写一遍即为缺陷。
- 示例、字段名、默认值必须与代码实际值一致；不一致即为缺陷。
- 文档写作质量与排版规范不属代码审查结论。

## 5 C 运行时可靠性

### D7 并发 / 异步 / 时序

依据：Rust 异步运行时的取消安全说明（中）；`std::sync::Mutex` 不得跨 await 持有、`tokio::sync::Mutex` 可跨 await 但持锁期间不得做长 IO（中）；结构化并发（中）。

- 取消必须贯穿「前端状态 → 跨进程调用 → 后端任务 → 流读取」全链路；取消信号无人检查即为缺陷。
- 不得存在「先清状态再启动新任务」的时序窗口；窗口内事件无归属即为缺陷。
- 流事件身份必须由后端生成并全程携带；用持久化标识充当归属键、前端自造标识即为缺陷。
- 同步锁不得跨 await 持有；异步锁持锁期间不得执行长时间 IO 或阻塞操作；锁顺序必须一致；违反即为缺陷。
- 阻塞调用不得运行在异步执行器或主线程上；出现即为缺陷。
- 超时、重试、退避、并发上限必须全部有界；无界队列、无上限重试、无退避即为缺陷。
- 订阅与清理必须成对；热路径重复注册、卸载不释放即为缺陷。
- `select!` 与取消路径必须定义未选中分支的落盘语义：已产生部分结果时，要么提交完整单元、要么整体丢弃，不得留下半成品；未定义即为缺陷。

### D8 状态与资源生命周期

依据：React 官方规则的钩子与依赖数组不变量（强）；单向数据流惯例（弱）。

- 共享状态必须有唯一写入路径；绕过统一入口直接写共享状态即为缺陷。局部状态允许就近写入，但不得出现双向同步。
- 派生状态不得重复存储；必须存储时必须有同步机制，无同步机制即为缺陷。
- 重置必须覆盖全部字段；遗漏流式、推理、工具标志即为缺陷。
- 卸载、关窗、切换会话必须对称释放监听器、定时器、订阅、动画、缓存；缺失即为缺陷。
- 全局状态必须集中管理并安全封装；散落可变静态、出现双向引用即为缺陷。
- 缓存必须有失效策略与上限；缺失即为缺陷。

### D9 数据持久化与迁移

依据：SQLite 部署建议的 WAL、事务与迁移（中）；原子替换（强）。

- 结构变更必须通过迁移完成，且迁移幂等、可重入，并有失败恢复或前向修复路径；确实不可回滚的迁移必须显式说明。直接改结构、或迁移假设「只跑一次」即为缺陷。
- 跨表写入必须有事务边界；部分成功即返回成功即为缺陷。
- 写入必须原子；崩溃后留下半成品或损坏文件即为缺陷。
- 单位与时区必须统一且可判定；秒、毫秒、纳秒混用且无类型约束即为缺陷。
- 级联删除与孤儿数据必须有清理路径；删除主记录不清理附件与索引即为缺陷。
- 连接参数（日志模式、忙等待、外键约束）必须符合预期；预写日志用于网络文件系统即为缺陷。
- 数据库与文件系统之间不存在共同事务，必须显式定义提交顺序与补偿路径；一侧已提交、另一侧缺失且无补偿即为缺陷。
- 派生文件与侧车必须可由主文件重建，不得成为唯一真相；只能从侧车恢复的数据即为缺陷。
- 配置 schema 变更必须同时具备「新增字段有默认值」与「旧版本读到新配置的降级行为」；只覆盖单向兼容即为缺陷。

### D10 性能与资源占用

依据：React 官方规则的渲染性能部分（中）；SQLite 部署建议的索引建议（中）；列表虚拟化（中）；性能预算与资源上限（中）。

- 可能无界增长或超过既定阈值的大列表必须虚拟化；无稳定键、全量重渲染即为缺陷。
- 高频事件必须合并或节流，跨进程调用频率必须有上限；每个流式增量一次状态更新或一次调用即为缺陷。
- 主线程不得存在同步 IO、大对象序列化、重计算；出现即为缺陷。
- 启动初始化必须可并行、可延迟；阻塞首屏的串行链即为缺陷。
- 长会话、长历史、大附件下的内存峰值必须可控；无上限缓存、无分页累积即为缺陷。
- 循环内逐条查询（N+1）即为缺陷。
- 磁盘侧产物必须有轮转与总量上限：日志、崩溃转储、工具结果、临时文件只增不减即为缺陷。
- 子进程输出必须有截断上限；无界缓冲读取即为缺陷。
- 启动关键路径必须有可测量的预算与回归阈值；无预算记录或持续超标且无处理即为缺陷。

## 6 D 风险与保障

### D11 安全与隐私

依据：OWASP ASVS 与风险清单的 V2、V5、V6、V7 与 A01、A03（中）；Tauri 安全模型的 v2 能力模型（中）。

- 信任边界必须明确，跨边界输入必须重新校验；只在前端校验即为缺陷。
- 跨进程暴露面必须最小，前端不得接触明文密钥；前端缓存明文密钥即为缺陷。
- 密钥与明文必须可零化、禁止克隆与调试输出，失败路径同样清理；错误消息带密钥片段即为缺陷。
- 外部输入进入文件系统、命令、SQL、URL 时必须有等价校验；字符串拼接进入危险操作即为缺陷。
- 日志、错误、崩溃转储、事件载荷不得携带敏感数据；出现即为缺陷。
- 能力声明与资源协议作用域必须按最小权限配置，且与实际读写目录一致；覆盖不必要目录、或未覆盖实际使用路径即为缺陷。
- WebView 必须配置 CSP 与外部导航白名单；在应用内加载任意远程内容、未限制新窗口或外链跳转即为缺陷。
- 平台原生接口调用必须集中，并检查返回值与句柄生命周期；缺失检查即为缺陷。
- 符号链接、硬链接与目录联接必须解析到真实目标后校验；只校验字面路径即为缺陷。
- 校验与使用之间不得存在可替换窗口：校验对象必须就是随后打开的对象，先校验路径再重新拼接打开即为缺陷。
- 临时文件与缓存必须排他创建（存在即失败）；先探测再写入、或写入可预测固定名即为缺陷。
- 子进程必须显式约束环境变量、工作目录与参数形态；继承全量环境、经 shell 拼接参数即为缺陷。
- Web 形态条目（跨站请求伪造、同源策略、会话 Cookie）在本地应用中无对应攻击面，不得作为判定依据；本地攻击面按本节条目自行覆盖。

### D12 依赖与供应链

依据：供应链规范（SPDX、cargo-deny、SLSA）（中）；锁文件随构建生效（强）。

- 新依赖必须论证必要性，优先复用现有依赖或标准库；无必要性论证即为缺陷。
- 同一能力不得引入多个库；多版本共存、功能重叠的双实现即为缺陷。
- 版本必须集中在工作区或根配置；各子包各自声明并漂移即为缺陷。
- 许可证必须与项目一致；资产与数据文件必须有来源与许可说明，无记录即为缺陷。
- 锁文件必须提交并在构建中生效；缺失或未生效即为缺陷。
- 依赖必须可审计；未使用依赖长期留存即为缺陷。
- 可选能力必须用特性开关隔离，禁止默认全量编译；违反即为缺陷。

### D13 测试策略

依据：测试金字塔与不稳定测试治理（中）；消费者驱动契约测试（中）。

- 关键链路（对话发送、流式、取消、审批、保险库、迁移）必须有可信测试；只测纯函数、编排与跨层无测试即为缺陷。
- 层级必须分工明确：纯函数单测、模块集成、契约、快照；混层即为缺陷。
- 必须验证行为而非实现细节；替身覆盖到被测逻辑本身、断言实现细节即为缺陷。
- 必须可重复；依赖真实网络、真实时钟、未固定随机种子即为缺陷。
- 每个已修复缺陷必须有回归测试；缺失即为缺陷。
- 测试放置必须符合仓库约定：前端测试放 `__tests__` 目录，Rust 集成测试放 crate 的 `tests/`，内联单测按语言惯例保留；与约定不符即为缺陷。
- 不得存在不稳定测试；固定等待、时序假设、共享状态即为缺陷。
- 测试之间必须隔离：共享数据库、共享临时目录、共享端口、依赖执行顺序即为缺陷。
- 跳过或忽略测试必须带理由与追踪编号，并注明恢复条件；无理由 `ignore` / `skip` / 注释掉断言即为缺陷。

### D14 构建与质量门禁

依据：零告警门禁与格式化工具（强）；模式生成链的契约生成与漂移校验（强）。

- 格式、静态检查、类型检查必须零告警执行；无理由、无复查条件的告警上限放宽或跳过路径即为缺陷。
- 契约生成与漂移校验必须纳入门禁；缺失即为缺陷。
- 后端必须执行格式检查与静态检查，警告必须视为失败；放宽即为缺陷。
- 构建必须可重复，脚本必须幂等；脚本有副作用、跨平台失败静默即为缺陷。
- 本地门禁与自动化流水线必须使用同一组检查；两边结果不一致即为缺陷。
- 生成物、锁文件、快照的更新流程必须明确且可校验；缺失即为缺陷。
- 构建产物与编译时间必须有记录的上限与回归阈值；持续超标且无处理即为缺陷。

### D15 平台兼容与国际化

依据：WCAG 2.2 成功准则的可判定部分（强）；CLDR 与 Unicode 规范（强）。

- 平台差异必须集中在按平台分文件的模块；主逻辑散落平台分支即为缺陷。
- 路径分隔符、大小写敏感性、长路径、编码转换必须统一处理；硬编码分隔符、假设文件系统大小写不敏感即为缺陷。
- 前后端文案必须外置，语言包必须同步且键齐全；只改一侧、键缺失回退到键名即为缺陷。
- 快捷键、缩放比、窗口坐标、系统主题必须统一抽象；固定像素未乘缩放因子、物理与逻辑坐标混用即为缺陷。
- 时区、日期格式、数字格式不得依赖本地环境假设；依赖即为缺陷。
- 新增平台相关能力必须列出未支持平台的降级行为；无降级说明或直接崩溃即为缺陷。
- 键盘可达与焦点顺序必须完整：核心操作不得只能鼠标完成，焦点被遮挡或丢失即为缺陷。
- 自绘交互必须提供可访问名称与角色；`div` 拼接可点击元素、图标按钮无标签即为缺陷。
- 文本与关键控件必须满足对比度下限，且不得仅靠颜色区分状态；违反即为缺陷。

### D16 变更卫生

依据：Google 代码审查实践指南（中）。

- 变更集必须只包含与目标相关的改动；顺带重构、全文件格式化、无关依赖升级混入即为缺陷。
- 一个变更必须可独立回滚并可独立验证；把互不相关的修复捆绑成不可分单元即为缺陷。

## 7 跨层链路要求

单维度看「局部对不对」，链路看「跨层合起来对不对」。每条链路按「入口 → 每层职责 → 出口」逐段检查。

### 7.1 对话发送链路

`UI 输入 → 状态层 → 编排层 → 跨进程调用 → 命令层 → 模型与代理 → 流事件 → 状态层 → UI`

- 身份：持久化身份与流事件身份必须分离，身份由后端生成并全程携带。
- 时序：启动新流与清理旧流之间禁止存在事件窗口；存在时必须显式归属或丢弃。
- 取消：取消必须到达后端任务与流读取，取消后前端状态必须一致。
- 错误：错误类别必须传递到 UI 并映射到匹配动作，重试必须精确关联出错消息。
- 落库：流结束、部分输出、失败三种终态必须都有持久化路径。
- 一致性：同一消息在状态层、后端存储、UI 三处禁止分叉。

### 7.2 设置变更链路

`设置 UI → 调度层 → 跨进程调用 → 状态刷新 → 跨窗口事件 → 消费端`

- 原子性：一次变更涉及多个字段时禁止部分生效。
- 失败：写入失败必须回滚乐观更新，用户必须可见。
- 同步：其它窗口与悬浮入口必须收到事件并更新，禁止只轮询不监听的消费端。
- 副作用：副作用必须由注册表驱动，禁止硬编码比较前后值。
- 兼容：旧配置缺字段必须有默认值，未知字段必须安全处理。

### 7.3 数据与事件链路

`后端操作 → 广播或定向事件 → 前端监听 → 状态更新`

- 分类：数据变更用广播、窗口控制用定向、高频独占流用定向。
- 结构：载荷必须结构化且可校验，前端必须有对应类型。
- 覆盖：所有改变数据的操作必须发出通知，批量操作必须携带受影响集合。
- 幂等：重复投递、乱序投递禁止造成重复数据或错误状态。
- 清理：监听方卸载必须取消订阅，禁止泄漏或重复处理。

### 7.4 安全边界链路

`UI → 跨进程调用 → 命令层 → 安全与保险库 → 存储`

- 暴露面：明文只在后端短暂存在，前端只拿结果或密文。
- 生命周期：密钥与明文在成功、失败、取消三条路径上必须都被清理。
- 校验：跨边界输入必须在后端重新校验，禁止信任前端。
- 审计：敏感操作必须有审计记录，审计失败禁止被静默吞掉。
- 对称：锁定与解锁、加密与解密、授权与撤销必须成对实现，禁止单边残留。

### 7.5 工具执行链路

`审批卡片 → 管线 → 工具实现 → 结果落盘 → 前端气泡`

- 参数一致性：审批展示的参数必须就是实际执行的参数；审批后重新解释、重新拼装即为缺陷。
- 校验位置：路径与命令参数必须在命令层与工具层各自成立，以「前端已校验」为由跳过即为缺陷。
- 取消：取消必须到达工具执行体，已产生的部分结果按 D7 的落盘语义处理。
- 落盘：超出阈值的结果必须写盘并保留可失效的引用；只留内存、或截断后不落盘即为缺陷。
- 失效：写入结果目录的文件必须能按组件级前缀失效；按精确字符串匹配导致路径形态漂移后失效失败即为缺陷。
- 回传：工具失败必须保留类别与可判定信息；统一成「工具执行失败」即为缺陷。

### 7.6 文件与路径链路

`用户输入 / 拖拽 / 对话框 → 校验 → 文件系统 → 事件 → 前端展示`

- 形态分离：展示形态与 IO 形态必须在单一转换点互转；每层各自把字符串重新解释为路径即为缺陷。
- 校验点唯一：外部使用路径只在一处校验，后续各层复用该结果；层层重新拼接后再各自校验即为缺陷。文件系统状态随时可变，校验只对当前时刻成立，不得表述为「已验证即可信任」。
- 作用域同源：资源协议作用域、写入目录、读取目录必须来自同一常量来源；三者不一致即为缺陷。
- 失败可判定：路径解析失败必须报错并携带原因；回退相对路径、回退默认值、回退当前目录即为缺陷。
- 编码：非 UTF-8 路径必须显式失败或按定义降级；静默换成另一条路径即为缺陷。

## 8 行业依据的认可条件

### 8.1 为什么每条依据都要标条件

规范被广泛引用，不等于在任意上下文都成立。三种典型失效：照搬条目而非内核（把服务端检查项搬到本地应用，检查了无意义的条目，同时漏掉真正的攻击面）；把清单当证明（勾选完成即视为达标）；把启发式当阈值（把「深模块」读成数值标准，为达标而拆分）。

因此本节对每条依据同时交代三件事：凭什么可信、在什么前提下成立、前提不成立时怎么用。说不出这三项的规范不构成审查依据。

认可强度分三档：**强**——违反会产生确定的运行时后果，或可被机器校验，直接作为判定依据与门禁；**中**——在明确前提下属实证有效，须先确认前提再引用；**弱**——由经验归纳，无度量无阈值，只用于提问。

### 8.2 逐条说明

**ISO/IEC 25010 质量模型**（中）。多国产业界共识，被采购与验收流程引用；价值在于把质量拆成可分别讨论的特性，使争论从「好不好」变成「哪一维、按什么标准」。其「功能适合性」子特性（完备性、正确性）可直接用于边界条件分类。它只给分类，度量与阈值须自行定义；直接当评分表会产生互相冲突的指标（可维护性与性能、兼容性与一致性往往此消彼长）。借分类，不借判定。

**Google 代码审查实践指南**（中）。结论来自超大规模审查的沉淀：审查时间应花在设计、复杂度、测试、命名与文档，机械风格问题交给工具。其审查重点可作为 D4、D6、D13、D16 的提问来源，但判定仍以对应维度的要求为准。前提是格式化、静态检查、自动化测试已先行承担机械问题；无自动化时该指南不成立，人工审查被迫检查风格，真正的设计问题反而无人处理。

**OWASP ASVS 与风险清单**（中）。条目来自真实漏洞案例，被合规与审计采纳；分级本身承认不同系统的威胁模型不同。前提是已有威胁模型并按应用形态裁剪。风险清单是意识清单而非验证清单，逐条打勾不构成安全证明；服务端特有条目在本地应用中无对应攻击面，本地攻击面（文件系统越权、进程间接口暴露、本地提权、符号链接穿越）不在其覆盖范围。只借跨形态内核：输入校验、密钥管理、日志脱敏、路径穿越。

**Rust API Guidelines 与 Clippy 分组**（强）。官方与社区共识，大部分条目可机器校验；分组本身区分缺陷与偏好，正确性与可疑类属缺陷，风格与复杂度类多属偏好。前提是 API 规范面向库的对外接口，应用内部模块与私有函数适用度低。静态检查只覆盖可模式化问题，覆盖不到职责划分与设计取舍；参数数量、类型复杂度、相似代码等规则在具体语义下是误报，应按语义判断而非一律压制或一律修复。静态检查是下限，不是标准。C-NAME、C-CONV、C-GOOD-ERR 等具体条目按出处引用，不把整组规则一概套用。C-VIEW 的公开面收敛与 `missing_safety_doc` 的 `SAFETY` 文档要求可机器校验，属可判定部分；`unsafe` 的不变量说明仍须人工确认是否与实际前提相符。

**零告警门禁与格式化工具**（强）。格式与静态检查的输出是确定的通过或失败，且不依赖人的判断，是唯一可以无条件当判据的一类规范。前提是基线已清理：存量项目一次性开启全部规则会产生大量噪音，团队随即学会绕过，门禁反而失效；应先清理再开启，并对每条豁免写明理由与复查条件。类型检查只覆盖被标注的类型边界，跨进程收到的 JSON 在编译期仍是声明值而非运行时事实，类型检查通过不等于数据合法。

**Clean Architecture 依赖规则与稳定依赖原则**（中）。依赖只能指向更稳定的方向，是把「改动传播范围」变成可检查结构关系的少数可操作判据。前提是已识别出稳定与易变部分；单体小项目分层过细会抬高跳转成本，此时按变化原因判据而非层数判据。

**设计哲学类著作（复杂度与模块深度）**（弱）。基于长期教学与代码观察归纳出「复杂度是主要成本」，并给出可操作的提问：接口是否比实现更简单、信息是否被隐藏、错误状态是否被设计掉。无度量无阈值；深模块在需要跨团队并行发现时可能抬高定位成本。用它问「接口是否比实现简单」，不用它定「多少行必须拆」。

**重构经验模式（坏味道）**（弱）。来自大量真实代码的重复观察，命名稳定，便于团队共享词汇。坏味道是症状而非诊断：两段代码因不同变化原因而相似时，强行合并会制造耦合，这与「一个文件一个变化原因」的判据正好相反。「消除重复」不是无条件正确。

**React 官方规则**（强，部分条目）。钩子调用顺序与依赖数组是框架定义的运行时不变量，违反会产生确定的错乱，且有官方静态检查可机器校验。条目随版本演进，须按当前版本核对。关于「何时不该使用副作用」的建议针对特定数据流与并发渲染模型，是建议而非不变量；列表键仅在需要身份保持或子组件持有状态时才是正确性要求。区分不变量与建议：钩子与依赖数组进判定，渲染性能与列表键建议降为中档，仅作提问。

**单向数据流惯例**（弱）。唯一写入路径让状态变化可追溯，是多框架社区长期共享的实践。它是惯例而非框架约束：小范围局部状态用多条写入路径并不产生故障，只在状态需要跨组件、跨窗口共享时才成立。用它找「同一个状态被几处修改」，不用它要求所有状态都进全局。

**Tauri 安全模型**（中）。能力声明、命令暴露面、资源协议作用域直接对应实际攻击面，且有公开漏洞案例佐证作用域过宽与命令注入的现实风险。须按当前主版本的能力模型核对，版本之间差异大。官方推荐是最小权限的下限而非上限，业务侧仍需自定义校验（路径归一化、符号链接、编码绕过、大小写与长路径）；旧版本条目可能已完全失效。

**12-Factor**（中）。来自部署与运维失败归纳，Factor III 配置外置、日志作为事件流、可观测性几条在运维侧被反复验证。前提是面向可水平扩展、无状态的服务进程；桌面单机应用天然不满足「无状态进程」「端口绑定」「进程模型」，照搬会把本地持久化误判为违规。只借配置外置、日志、可观测性三条。

**消费者驱动契约测试**（中）。契约漂移是高频真实故障，把契约变成可执行断言能在改动时立即暴露不兼容。前提是契约有单一来源且校验进入流水线；没有单一来源时，契约测试只会固化两份不一致的真相。双向验证成本较高，单体内应用用「生成 + 编译期类型检查 + 启动时校验」往往已足够。

**序列化属性与严格模式**（强）。`deny_unknown_fields`、`rename_all`、TypeScript `strict`、ESLint 禁止显式 `any` 与严格类型检查都是声明式、编译期或启动期即生效的约束，违反会在首次运行或构建时暴露。前提是约束声明在实际边界上：只在输入结构声明拒绝未知字段、只在输出结构统一命名，未声明的结构仍会静默接受并丢字段；严格模式对「从外部读到的 JSON」只做类型断言，不做运行时校验。

**Rust 异步运行时的取消安全说明**（中）。各方法的 cancel-safe 标注是官方逐方法给出的可核对结论，`select!` 语义与锁的取舍也有明确文档。前提是按当前版本核对具体方法；未标注 cancel-safe 的操作在取消后可能丢失数据，这一结论不适用于同步代码路径。`tokio::sync::Mutex` 是允许跨 await 的异步锁，`std::sync::Mutex` 才是不应跨 await 持有的同步锁。

**结构化并发**（中）。把并发任务的存活范围绑定到明确的作用域，取消与清理由结构而非约定保证，这一模型在主流运行时与语言里都已被实现验证。前提是任务确实纳入作用域：游离的任务不继承取消与超时，作用域之外的清理责任仍落在调用方。

**SQLite 部署建议**（中）。日志模式、事务、迁移、索引建议来自大量生产部署，官方同时明确适用边界：单写者、不适合高并发写。预写日志在网络文件系统上不可靠；「单连接」假设在多窗口并发写入下会被破坏；迁移必须幂等、可重入，这一要求来自「用户可能随时中断」的桌面现实，而非数据库本身的要求。

**原子替换**（强）。写临时文件、落盘、再重命名替换，是文件系统层面有明确语义的写入方式，崩溃时旧内容完好或新内容完整，不会出现半成品。前提是同目录同文件系统且按目标平台语义使用：跨卷重命名不保证原子，部分平台替换已存在文件需专门接口并处理占用与共享冲突；未落盘的重命名在断电后可能丢失。

**列表虚拟化**（中）。只渲染可视区域在大量数据的列表上被反复验证为数量级的改善，且与框架无关。前提是行高可预测或可测量：可变高度、嵌套滚动、需要全文搜索的列表收益下降或需要额外测量策略；虚拟化后仍需稳定键，否则复用的行会串内容。

**性能预算与资源上限**（中）。启动时间、内存峰值、磁盘占用与子进程输出都可由剖析工具与构建记录给出确定数值，使「变慢」「变大」从主观感受变成可比较的数值；预算与回归阈值一旦确定，超标即可判定。前提是项目已定义预算与测量口径，且测量环境稳定；未定义预算时只能提问「有没有上限」，不能判缺陷。测量口径不一致（不同机器、不同构建配置）时结论失效，需先统一口径再引用。

**模式生成链**（强）。由结构定义生成校验器、类型、文档与快照，使契约与文档只有一个来源，漂移在生成或校验时立即暴露。前提是生成源本身唯一且生成物禁止手改；一旦有人手工修补生成物，生成链就退化为第二份真相。

**供应链规范（SPDX、cargo-deny、SLSA）**（中）。许可标识可机器校验，漏洞与许可检查有成熟工具；SLSA 把供应链保障分级，承认不同项目所需强度不同。前提是工具进入门禁；未进门禁的检查只提供一次性快照，不构成持续保障。

**锁文件随构建生效**（强）。锁文件提交并在构建中生效，使依赖图可复现且可机器校验；缺失或未生效即失去供应链基线。前提是锁文件与构建工具链匹配，且构建路径不绕过锁文件；仅提交锁文件而不在构建中强制使用，只提供记录，不提供保障。

**测试金字塔与不稳定测试治理**（中）。金字塔结论来自测试成本与反馈速度的长期权衡；不稳定测试治理建议强调隔离与量化，而非反复重跑掩盖。前提是测试本身可重复；若环境不可控，金字塔比例无意义。

**WCAG 2.2 成功准则**（强，可判定部分）。成功准则可判定通过或失败，且被多国法规引用，是少数能客观核验的体验类规范。须按等级（A、AA、AAA）与目标用户群裁剪。部分条目针对网页结构与浏览器交互，对桌面原生控件无直接对应；自定义绘制界面（动画、可视化、装饰性元素）难以完全满足；成本与收益须按实际用户群评估，不应一律取最高等级。

**CLDR 与 Unicode 规范**（强）。时区、日期、数字格式的权威数据源，大小写折叠与归一化有明确算法定义。前提是按目标区域加载对应数据；只支持单区域时不必引入完整数据，但不得用本地环境默认值代替显式声明。

### 8.4 引用前的三问

1. **它针对哪类故障**：可复现的运行时错误、概率性风险、长期维护成本。前两类可定级，第三类只能提要求。
2. **它的前提在本上下文成立吗**：应用形态（服务端或桌面端）、并发模型、团队规模、工具链完备度。前提不成立时结论直接失效，不是打折扣。
3. **违反它是否产生可观测后果**：能复现或能机器校验的按强档判定；只能推测的降为中档并先验前提；纯经验偏好的降为提问。

结论：强档进门禁与判定，中档先验前提再引用，弱档只做提问。

## 9 禁止事项

以下为第 3–6 章禁止性要求的摘要；与正文冲突时以正文为准。

- 不用 UI 隐藏代替状态层校验。
- 不用强制断言或宽泛字典类型绕过契约；既有例外必须逐条登记。
- 不手改生成物、不手工编辑快照。
- 不在状态动作内串联多步跨域调用，不把业务编排留在命令层。
- 不在业务层散落 `unsafe`，不写无 `SAFETY` 说明的 `unsafe`。
- 不保留无消费者的 `pub`，不为测试放开可见性。
- 不让调试残留进主干：`dbg!`、`println!`、`console.log`、注释掉的代码块、临时开关。
- 不用持久化标识充当流事件归属键，不自造事件标识。
- 不持同步锁跨异步等待，不持异步锁做长 IO，不使用无界队列与无上限重试。
- 不绕过状态层直接写共享状态，不保留只写不读字段。
- 不做非原子写，不让结构变更绕过迁移，不让数据库与文件一侧提交另一侧缺失。
- 不把敏感信息写入日志、错误、事件与崩溃转储。
- 不只校验字面路径，不忽略符号链接的真实目标。
- 不先校验路径再重新拼接打开，不先探测临时文件再写入。
- 不让路径解析失败回退相对路径或默认值，不让非 UTF-8 静默换值。
- 不让日志、崩溃转储、工具结果无上限增长，不无界缓冲子进程输出。
- 不在应用内加载任意远程内容，不放开外部导航白名单。
- 不为小功能引入大依赖，不让依赖版本在各子包漂移。
- 不提交跳过门禁的改动，不让本地与流水线检查不一致。
- 不混入与目标无关的改动，不捆绑不可独立回滚的修复。
- 不无理由跳过测试，不让测试共享数据库、临时目录或执行顺序。
- 不保留无理由、无复查条件的告警豁免。
- 不让同一规则在多份文档重复陈述，每条规则只在一处承载。
- 不把行业依据当权威直接引用：说不出它针对的故障与成立前提，就不构成审查依据。
