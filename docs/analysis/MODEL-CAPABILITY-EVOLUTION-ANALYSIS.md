# 模型能力描述与演进兼容性分析

> 日期：2026-11-01
> 关联：`docs/ARCHITECTURE.md` · dto-frontend-backend-sync-audit（已归档） · I29-token-usage-analysis（已归档）
> 范围：models.dev 目录 → 能力判定 → 请求构造 → 流协议 → 持久化 → 前端投影
> 性质：**前瞻分析**。讨论能力描述的结构形态与演进兼容性，不描述修复方案，不跟踪代码进度。
> 阅读约定：结论部分（§1、§3–§8）讨论的是结构，不随代码修复失效；基线快照（§2）是某一时刻的结构证据，修复后**不再更新**，不构成待办清单。

---

## 0 结论

1. 能力描述不准的根因是三个缺失，不是字段少：**缺三态**（支持 / 不支持 / 未知）、**缺来源**（谁说的、何时说的）、**缺主体**（能力属于 `provider + 端点 + 模型 + 请求形态`，不属于 `model_id`）。
2. 演进分两类：**词汇型**（新模态、新档位、新计费项）加字段即可；**语法型**（有状态、带约束、多流并发、多层来源、时间漂移、多模型组合）击穿结构。
3. 「看起来支持、实际半路丢弃」比「完全没有」更危险——它给出错误的安全感，让排查从正确的方向偏开。
4. 取舍：**先止损、再占位（仅流协议 item 维度与能力 key），其余按需推进**。不要为了「未来可能」一次性重构协议。

## 1 核心命题：什么叫「准确描述能力」

准确描述必须同时回答四件事，缺一即失真：

| 问题 | 对应结构 | 缺失后果 |
| --- | --- | --- |
| 它是什么 | 名词：模态、限额、控制项 | 字段不够用，靠布尔硬凑 |
| 谁说的、何时说的 | `source` + `revision` + `valid_until` | 目录失真后无法纠正 |
| 信到几分 | 三态：`Supported` / `Unsupported` / `Unknown` | 「没写」被当成「不支持」 |
| 谁依赖它 | 能力与用法解耦（feature → capability 映射） | 新特性散落多处判定 |

### 1.1 三个缺失

1. **缺三态**。布尔把「明确不支持」与「目录没写」压成同一个 `false`，UI 无法表达「不确定，但你可以试」。
2. **缺来源**。能力值没有出处，因此无法回答「为什么是这个值」，也无法在目录更新后判定「哪个值该被替换」。
3. **缺主体**。能力的主体是四元组 `(provider, 端点, 模型, 请求形态)`，而非 `model_id`。同一模型在官方端点、兼容代理、云部署上能力不同；同一模型走 `chat/completions` 与 `responses` 也不同。

### 1.2 五个判断

1. 能力不是布尔，是**带条件的谓词**：「支持图片」实为「在什么请求形态下、几张、多大、哪种编码下支持」。
2. 能力的主体是**四元组**，不是模型。
3. 能力的可信度**分档且必须显式**：API 声明 > 适配器已知行为 > 内置目录 > 兜底 > 猜测。猜测必须能被标出来。
4. 能力会**漂移**：同名模型改版、目录更新、端点换协议。数据必须带来源与时效。
5. 「未知」的处理策略应**按特性分别定义**，不能全局一个 `false`——图片可放宽（允许但提示），工具宜保守（错一次代价高）。

## 2 基线快照（2026-11-01）

### 2.3 结构证据

| # | 证据 | 结构性含义 |
| --- | --- | --- |
| P1 | 不透明推理的 replay capture 类型已定义并在流解析中产出，但无落库、无回放 | 存在「看起来已支持」的假象；一旦需要回传即断 |
| P2 | 历史重建时 `tool_calls` / `tool_call_id` / `thinking_signature` 被置空，而存储侧有值 | 投影层是有损的，是回传类能力的第一个断点 |
| P3 | 推理内容的持久化开关由 UI 模式决定，而非由「Provider 是否要求回传」决定 | 两个不同性质的开关被合成了一个 |
| P4 | 内容编解码只识别文本块，其余块在搜索 / 导出 / 预览中静默丢弃 | 非文本内容在派生功能中无声消失 |
| P5 | 「内容是否为空」判定不识别非文本主体 | 纯附件 / 纯产物型消息被判非法，属语义层阻塞 |
| P6 | 流协议的工具调用字段为单槽位，无 index 维度，而累加器内部已有索引 | 并发 / 托管工具无法在对外协议上表达 |
| P7 | 附件限额为硬编码常量，不来自能力数据 | 能力与交互约束之间无连接，失败发生在请求之后 |
| P8 | 模型列表持久化三重脆弱：严格拒绝未知字段 + 解析失败静默降级为空 + 前端 round-trip 丢未知字段 | 加字段 / 旧前端 / 版本回退都可能让列表变空 |
| P9 | 预算降级只覆盖一种模态，token 用固定常数估算，预算口径取满上下文窗口 | 预算求解是单一规则，不是按约束求解 |

## 3 七条硬编码假设

这些假设未写在任何文档里，但结构到处依赖。演进只要碰到其中一条，就不是加字段能解决的。

| # | 假设 | 结构依据 | 击穿后改动面 |
| --- | --- | --- | --- |
| A1 | 能力是模型级、静态、无状态事实 | 目录以 `model_id` 为唯一 key，catalog 侧无 provider 维度；运行时靠 per-provider 快照部分补偿 | 全链路签名 |
| A2 | 请求选项是无状态扁平结构 | 选项结构仅含标量字段，无不透明状态位 | 请求构造 + 全部适配器 |
| A3 | 消息 = 文本主体 + 输入附件；流 = 平铺字段 | 消息主体为字符串；流为平铺标量字段，无 item 维度 | 协议 + 持久化 + 渲染 + 前端 store |
| A4 | 工具只由本地循环执行 | 工具执行在 agent 侧 | 事件模型 + 权限模型 |
| A5 | usage 是固定字段集 | 定长结构；消息侧为单整数 | 计费 + 统计 + DTO |
| A6 | 会话 = 单模型 + 单端点 | 会话绑定单值；但模式层可覆盖模型 | 会话模型 + UI + usage 归属 |
| A7 | 本地消息数组是真源 | 裁剪、压缩、fork 全在本地计算 | 一致性 + fork / 重试语义 |

**A1 的准确表述**：能力主体在**目录侧**是单维（`model_id`），在**运行时**靠 per-provider 快照部分补偿。因此不是「完全没有 provider 维度」，而是「两个来源的维度不一致，且合并策略未显式化」。

**A6 的隐蔽矛盾**：模式层带模型与采样参数，会话内模型可按模式切换，但能力仍按 `model_id` 全局取值——**能力与实调模型可能不一致**。

## 4 演进分类

### 4.1 判据

**新增一项时，改的是「数据」还是「结构」。**

- 改数据 → 词汇型，无需预留
- 改结构 → 语法型，必须预留

### 4.2 词汇型

新输入 / 输出模态、新推理档位、新计费字段、新元信息。

**前提条件**（不满足时词汇型会退化成语法型）：

1. 去掉枚举白名单过滤——否则新值被静默吞掉
2. 去掉严格拒绝未知字段——否则加字段即解析失败
3. 投影 / 转换层存在对应的**通用分支**，而非「每加一个模态就加一个布尔 + 一个 if」

第 3 条是易被忽略的：即便能力数据是开放列表，若消费侧仍是逐布尔分支，新增模态依然要改代码。**开放的是数据，闭合的是消费方式**，这仍属语法型。

### 4.3 语法型

| # | 演进 | 击穿 | 为何加字段救不了 | 返工面 |
| --- | --- | --- | --- | --- |
| E1 | 有状态推理（不透明块须原样回传） | A3 / A7 | 需「不可变保护」语义：裁剪 / 压缩 / fork / 去重任一处改动即失效，而投影层已有损（P2） | 存储 + 投影 + 裁剪 + 压缩 + fork |
| E2 | 服务端工具 / 托管 Agent（item 生命周期、并发多流） | A3 / A4 | 流协议无 item 维度，单槽位工具字段（P6）无法表达并发 | 协议 + 全部流解析 + 前端消费 + 持久化 |
| E3 | 远端会话状态（response_id / 服务端压缩 / 服务端记忆） | A7 | messages 由「输入」变「引用」；fork 与重试语义须重定义 | 请求构造 + fork + 压缩 + 重试 |
| E4 | 约束型能力（图 ≤ N 张、单张 ≤ X、PDF ≤ Y 页、输入预算） | A2 | 布尔装不下参数；限额与能力数据无连接（P7） | 类型形态 + 前端交互 + 投影 |
| E5 | 能力协商（错误驱动降级、运行时修正能力缓存） | A1 | 需错误粒度到「哪个参数被拒」，当前为兜底错误桶 | 错误分类 + 能力缓存 |
| E6 | 多模型组合（fallback / router / planner+executor） | A6 | 能力由单点事实变组合运算（交集 / 并集） | 会话模型 + UI + usage 归属 |
| E7 | 策略层覆盖（组织策略、数据驻留、零保留、tier） | A1 | 优先级由两层变多层偏序，且可远端下发、有时效 | 判定链 + 配置来源 |
| E8 | 运行时探测（自托管模型目录失效） | A1 | 需第三类来源 + TTL + 失效 | 能力来源 + 缓存 |
| E9 | 输出产物（图像生成 / 语音 / 执行产物） | A3 | 输出非文本增量，需「产物 → 落地 → 引用 → 预览 → 计费」；空内容判定会直接判非法（P5） | 存储 + 渲染 + usage |
| E10 | 时间漂移（同名模型改版 / 下线 / 灰度） | A1 | 需 revision + 有效期；当前快照冻结且无版本，**不可纠正** | 能力投影 + 缓存失效 |

### 4.4 预留成本

| 等级 | 项 | 不预留的返工 | 现在预留 |
| --- | --- | --- | --- |
| S | E2 流模型 item 化 | 协议级重写 | 中（加三个可选字段，旧路径不变） |
| S | E1 不透明内容保护 | 已落库会话难救 | 低（加语义标记 + 投影不丢） |
| S | A1 能力主体加维度 | 全链路签名 | 低（改 key + 显式合并策略） |
| A | E4 / E9 / E5 | 类型形态迁移 / 存储渲染 / 错误重构 | 低（各加一个变体或细分） |
| B | E3 / E6 | fork 重定义 / 会话 UI usage | 中 |
| C | E7 / E8 / E10 | 判定链 / 新来源 / revision | 低（留位即可） |

## 5 六个难适配维度的本质

| 维度 | 变化 | 现有结构为何不行 |
| --- | --- | --- |
| 状态 | 能力 → 有状态的会话契约 | 请求为纯函数式构造，无不透明状态位；投影有损 |
| 约束 | 「能不能」→「能多少、在什么条件下」 | 布尔 + 硬编码常量 |
| 并发 | 单流 → 多 item 生命周期 | 流协议平铺单槽位 |
| 来源 | 一个值 → 多层断言 + 可信度 | 仅两层，无策略层、无探测层 |
| 时间 | 常量 → 有时效的观测 | 快照冻结、无 revision |
| 组合 | 单点 → 运算结果 | 会话绑定单模型 |

## 6 预留形状

原则：不预测具体能力，只让未知能力有地方落。

```rust
// 形状 1：不透明状态位（E1 / E3 / E5）
pub session_state: BTreeMap<String, Value>,
pub session_ref: Option<String>,

// 形状 2：能力 = 带参数、带出处的断言（E4 / E7 / E8 / E10）
pub enum Capability { Supported { params: BTreeMap<String, Value> }, Unsupported, Unknown }
pub struct Resolved<T> { value: Capability, source: Source, revision: Option<String>, valid_until: Option<i64> }

// 形状 3：协议形态开放（E1 / E2 / E9）
ContentBlock::Opaque { provider, kind, payload, preserve }
ContentBlock::Artifact { kind, uri, meta }
ChatDelta { item_id, item_kind, item_phase }   // 旧字段保留为兼容投影

// 形状 4：能力 key = (provider_id, endpoint_shape, model_id)，合并策略显式
// 形状 5：投影不丢——存储里有，请求里就有
```

## 7 判定原则

### 7.1 优先级偏序

```
用户显式覆盖 > 组织策略 > API 声明 > 适配器已知行为 > 内置目录 > 运行时探测 > 兜底
```

### 7.2 四条规则

1. **每层可回答「为何是这个值」**（`source`）。
2. **`Unknown ≠ Unsupported`**，不得把未知压成 `false`。
3. **未知策略按特性分别定义**，不设全局默认。
4. **降级事实走结构化通道，不走文案。**

### 7.3 字符串受众（第 4 条的展开）

能力降级会产出两类字符串，受众不同，处理方式必须不同：

| 类型 | 受众 | 载体 | 处理 |
| --- | --- | --- | --- |
| 投影占位符 | **模型** | 出站 prompt | 硬编码固定语言即可，无需本地化 |
| 降级提示 | **用户** | 响应侧结构化字段 | 需本地化，且需携带原因码 |

推论：占位符的读者是模型，不是用户；它的语言选择不影响正确性，因此硬编码是**决策而非遗漏**。而「用户怎么知道图片没被模型看见」无法通过文案解决——因为文案不在用户可见链路上。**降级可观测性只能由结构化回传实现**（如响应侧附带降级列表），且这是唯一可行通道。

## 8 取舍建议

只给顺序与理由，不给实施内容（实施归 spec）。

| 顺序 | 定位 | 判据 |
| --- | --- | --- |
| 1 | **止损** | 纯防御、零功能成本；不做就会静默丢数据 |
| 2 | **占位** | 唯一「必须趁数据未固化时占位」的结构：流协议 item 维度、能力 key 维度 |
| 3 | **补全** | 能力视图完整化：三态、来源、未消费字段 |
| 4 | **求解** | 约束求解、协商回路、远端会话——依赖真实需求出现 |

理由：第 1、2 项的共同特征是**越晚做越贵**（已落库数据、已发布的协议契约）；第 3、4 项属于体验优化，可在需求明确时再做，提前做的代价是增加调试复杂度。

**反向建议**：不要为了「未来可能」一次性重构协议。语法型预留只需占住位置（可选字段、开放枚举、状态位），不需要提前实现语义。

## 9 本文档的边界与可信度

### 9.1 可信度分级

| 级别 | 内容 | 依据 |
| --- | --- | --- |
| **高** | §2 结构证据；§3 假设的结构依据 | 逐条核对代码，可用单元测试断言 |
| **中** | §4 语法型的「击穿哪条假设」与返工面；§6 预留形状 | 由现有结构推演，逻辑闭合但未验证 |
| **低** | E1–E10 中涉及的具体外部形态（如「Provider 会要求回传不透明推理」「会出现托管工具 item 流」） | 来自外部协议演进的一般认知，本仓库代码无法证实，需对照各家协议文档确认 |

### 9.2 偏向与盲区

1. **偏悲观**。把「外部可能出现的形态」一律当作「本项目会遇到」。本产品是桌面助手，E6（多模型组合）、E7（企业策略）、E8（自托管探测）大概率长期不涉及；高相关的只有 **E1、E2、E4、E9**。
2. **只算返工成本，未算预留成本**。不透明状态位会让调试与可观测性变差，这是真实代价，本文未量化。
3. **A1 的修法可能引入新失真**。`endpoint_shape` 的定义本身（协议类型？base_url 归一？）没有标准答案。
4. **未量化**。所有「改动面」均为定性描述。
5. **只谈结构与机制，未谈字符串与分支**。本文曾因此把「占位符硬编码」误判为 i18n 缺陷，故在 §7.3 补充了「字符串受众」维度。同类盲区仍可能存在：结构层能回答「要不要加变体」，回答不了「加了变体代码里有没有对应分支」。
