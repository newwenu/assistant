# 应用任务资源管理器：管理机制合理性分析

> 日期：2026-11-11｜性质：**预先分析**（只判定管理机制能否成立、成立需要哪些范式、哪些部分不可归零；不含实施步骤与排期）
> 判据来源：`docs/principle/CODE-REVIEW-PRINCIPLE.md`、`docs/principle/CODE-SPLIT-PRINCIPLE.md`
> 事实基线：仓库当前代码；`docs/store/I38e-mcp-tools-spec.md`（MCP 进程与重连规格，**未实施**）
> 范围界定：**本文的主体是「管理机制」——任务如何被登记、准入、调度、状态化、可见、治理、回收。终止只是「回收」要素的一个子项，不作为主线。**
> 范围例外：§8「自身占用监控」不属管理机制，但因与任务观测共用投影通道、且决定 DTO 字段与用户文案，需一并定案。
> 引用已归档规格时只写「文档名 +（已归档）」，不给路径。

## 0 结论速览

| # | 命题 | 判定 | 依据 |
|---|---|---|---|
| 1 | 「任务资源管理器」的难点在管理机制，不在终止 | **成立** | 仓库已有登记 / 状态 / 代际 / 并发 / 投影五套范式（§2）；终止是唯一无现成物的部分，但它是兜底路径（§3.7） |
| 2 | 管理机制可以完全复用仓库既有范式 | **不成立** | 五套范式可复用其**形状**，但键、准入判据、调度策略、状态分层、投影通道都要按任务语义重新定义（§3） |
| 3 | 任务身份必须含代际 | **成立且必要** | `TurnTasks` 的 `turn_id = conversation_id:counter` 已证明：无代际则旧任务回调会覆盖新任务状态（§3.1） |
| 4 | 登记必须先于启动 | **成立且必要** | 否则存在「已启动但无人知晓」的窗口，停止与回收都无从下手（§3.2） |
| 5 | 并发上限应由任务自报，而非全局数字 | **成立** | `partition_tool_batches` 的声明驱动 + fail-closed 是既有判据（§3.3） |
| 6 | 准入判定即可覆盖调度 | **不成立** | 准入只回答「能不能启动」，顺序 / 抢占 / 背压 / 优先级另属调度；仓库有四个调度原语却无一被当作调度判定（§2.8、§3.4） |
| 7 | 抢占需要显式判定，不能靠默认行为 | **成立** | `OnBusy::Reject` / `Replace` 已证明双策略可行；任务层若不定，被抢占会被误记为失败（§3.4） |
| 8 | 状态机应分两层（通用态 + 领域态） | **成立，且是唯一可行形态** | MCP 的 `Ready` 与 `shell` 的退出码语义不可合并；合表会让枚举随消费方线性增长（§3.5） |
| 9 | 可见性需要 snapshot + delta 双通道 | **成立** | 项目要求 DTO 契约化（`contract:gen`），纯事件流会让前端无法冷启动对齐（§3.6） |
| 10 | 「回收」是唯一真缺口 | **成立** | 跨平台树杀、Unix 退出回收、统一退出收口三者均无现成物（§3.7） |
| 11 | 任务管理器可以绕过审批网关启动进程 | **不成立** | 会形成权限旁路；必须区分「配置面启动」与「调用面执行」两条治理路径（§3.8） |
| 12 | 应建一个统一全局 `TaskManager` | **不成立** | 唯一消费者（MCP server）尚未落地；契约会被它绑架（§4.2、§9） |
| 13 | 资源观测属于管理机制 | **不成立** | 观测是度量，不是管理；且标准库不提供（§1.4、§6） |
| 14 | 自身占用监控属于管理机制 | **不成立** | 观测对象是宿主而非受管任务；且「登记自己 → 停止自己」是自指，不可行（§8.1） |
| 15 | 「本应用占用」有唯一自然口径 | **不成立** | 仅主进程 / 含 WebView 进程 / 再含受管子进程，三种口径数量级不同，必须显式选（§8.2） |
| 16 | 自身占用可零依赖实现 | **部分成立** | Linux 可读 `/proc/self`；Windows / macOS 需平台特性或新增依赖（§8.3） |
| 17 | 六项机制形状应立即定型 | **成立** | 代际键、登记顺序、状态分层、双通道契约、抢占语义、自身占用口径六者一旦写错，第二个消费者必然要求重构（§9.2） |

一句话：**管理机制的骨架在仓库里已经长过五遍（注册表、状态机、代际、并发批次、事件投影），另外还躺着四个没被当作调度的调度原语；本议题的正确做法是复用这些形状，补齐「回收」这一缺失要素，并把「调度」与「自身占用」两处未判定项显式定案——否则会得到一个只有兜底路径、没有管理语义的组件。**

## 1 管理机制的边界

### 1.1 四类被管理的对象

「任务资源管理器」这个词同时指向四类对象，它们的管理手段不同。前三类属本文主线，第四类属 §8：

| 对象 | 例子 | 管理手段 | 是否属本文主线 |
|---|---|---|---|
| **受管进程** | MCP server、`git`、`ssh-add`、将来的 `shell` | OS 级约束 + 应用级登记 | **是** |
| **逻辑任务** | 一次工具调用、一轮 turn、一个后台子代理 | 取消树 + 状态投影 | **是**（复用现有内核） |
| **受管任务度量** | 子进程的 CPU、内存、进程树 | 采样与展示 | **否**（度量不是管理，见 §1.4） |
| **自身占用度量** | 宿主进程、WebView 进程、自身派生的子进程合计 | 采样与展示 | **否，但需独立定案**（§8） |

**为什么第四类不能与第三类合并**：两者的数据源、生命周期、失败模式、目的全都不同，而最关键的差异是**自指**——自身占用一旦并入受管任务表，就出现「把自己登记为任务 → 停止自己 = 应用自杀」；且 OOM / 主线程卡死时，采样器与被观测者同生共死。合并成一行会同时丢掉这两个约束。

### 1.2 管理机制的八个要素

把「管理」拆成要素，才能分别判定。八要素中六项有范式可继承，调度有原语但无判定，回收完全缺位，治理部分成立：

| 要素 | 要回答的问题 | 缺了会怎样 | 仓库现状 |
|---|---|---|---|
| **身份** | 任务的键是什么，可不可变 | 同一任务出现两个 id，停止打到错的目标 | 有范式（§2.1） |
| **登记** | 谁在何时把任务写进表 | 「启动了但没人知道」，无法停止 | 有范式（§2.6） |
| **准入** | 允不允许启动、允许多少个 | 无限拉起，或第二个消费者被第一个饿死 | 有范式（§2.2、§2.4） |
| **调度** | 谁先跑、能否抢占、满了怎么办 | 长驻进程与一次性进程抢同一队列；被抢占记成失败；队列无限等待 | **有原语无判定**（§2.8、§3.4） |
| **状态** | 任务当前处于哪个阶段 | UI 显示与事实不符，重启判定错误 | 有范式（§2.2） |
| **可见** | 用户与其它模块如何得知 | 只能靠日志，无法做面板与诊断 | 有范式（§2.5） |
| **回收** | 任务怎么结束、谁来收尾 | 进程残留、端口占用、文件锁 | **无**（§3.7） |
| **治理** | 谁有权启动、是否留痕 | 权限旁路与不可审计 | 部分（§3.8） |

### 1.3 为什么终止不是主线

终止在八个要素里只对应「回收」的一个分支，却被直觉当成全部，原因有三：

1. **它是唯一 Rust 不提供跨平台语义的部分**（单层 `kill` 与树杀之差），因此最扎眼；
2. **它的失败最容易被观察到**（进程残留、端口占用），而管理机制的失败只表现为「状态不对」；
3. **它看起来可以独立完成**，而登记、准入、调度、投影都必须与消费方语义绑定。

判定：**终止是兜底路径，不是管理机制。** 只做终止会得到一个「能杀进程但没有任务概念」的组件——它能杀，但不知道杀什么、该不该杀、杀完谁负责更新状态。

同理，**调度也不是终止**：调度决定「什么时候启动、启动几个、谁让路」，它发生在启动之前与并发之中，与「怎么杀」没有因果关系。把调度并入终止讨论，会得到「先拉起、出问题再杀」的伪策略。

### 1.4 成本口径

| 记号 | 定义 | 现状 |
|---|---|---|
| **G 机制成本** | 身份 / 登记 / 准入 / 调度 / 状态 / 可见 / 治理 的定义与实现 | 主要成本；可复用范式与原语，但要重新定义语义 |
| **R 回收成本** | 树杀、退出收口、幂等停止 | 唯一真缺口，含平台差异 |
| **O 受管任务观测成本** | 子进程 CPU / 内存 / 树形采样 | 不在本文范围；需新依赖且边界未定 |
| **S 自身占用监控成本** | 宿主与 WebView 的 CPU / 内存采样、口径定义、峰值留痕 | 不在本文范围，但**口径与约束需定案**（§8） |

判定：**G 是主体，R 是必要条件，O 可整体不做，S 的口径不可推迟。** 把 O 误当管理机制的一部分，会得出「必须先引入 `sysinfo` 才能做任务管理」的错误前置；把 S 的「口径」也一并推迟，则后续所有 DTO 字段与用户文案都要重写。

## 2 代码事实基线：仓库已有的管理范式

仓库里已经存在五套管理范式、一套装配范式，以及四个未被当作调度的调度原语。它们不是巧合，而是同一类问题（「多实例 + 生命周期 + 准入 + 可见」）在不同领域的解法。本议题的价值在于识别它们并复用其形状。

### 2.1 注册表范式：`ToolRegistry`

`src-tauri/crates/assistant-tools/src/registry.rs` 的双表结构：

| 结构 | 作用 |
|---|---|
| `tools: DashMap<String, RegisteredTool>` | 内部 id → 实例（管理与诊断走这条路径） |
| `names: DashMap<String, String>` | 模型可见名 → 内部 id（别名解析） |

已确立的四条语义：

- **注册即登记**：`register` 同时写入两张表，不存在「只在一个表里」的中间态；
- **重复注册覆盖并清别名**：`names.retain(|_, mapped| mapped != id)`，避免留下悬空别名；
- **名称冲突告警而非静默**：同名不同 id 时 `log::warn` 并重指向；
- **身份由实现自声明**：`tool.id()` / `tool.name()` 由工具自己给出，注册处只登记不覆盖。

判定：**任务管理器可以直接沿用「id 为主键 + 别名解析 + 冲突告警」三件套**，但必须补一项 `ToolRegistry` 没有的东西——**代际**（§3.1）。

### 2.2 状态机范式：`SessionStates`

`src-tauri/crates/assistant-agent/src/kernel/state.rs`：

| 机制 | 细节 |
|---|---|
| 存储 | `Arc<Mutex<HashMap<conversation_id, SessionState>>>` |
| 缺省语义 | 未记录视为 `Idle`；`ensure_idle` **只写 Idle，不覆盖已有 `Processing` / `Error`** |
| 准入判据 | `can_start_new_turn`：`Idle` / 可恢复 `Error` 允许，`Processing` 拒绝 |
| 显式枚举 | `Idle` / `Processing` / `Error { recoverable }` |

已确立的两条语义最值得移植：

- **「未记录」有明确语义**，不是 `None` 挂空，而是领域内的 `Idle`；
- **准入判据是行为，不是状态名**：`Error` 是否可恢复决定能否启动，而不是「Error 一律拒绝」。

判定：**任务的「准入」应沿用同一形状**——判据写成「当前状态 + 可恢复性」的函数，而不是一串 `if state == ...`。

### 2.3 代际范式：`TurnTasks`

`src-tauri/crates/assistant-agent/src/kernel/tasks.rs`：

| 机制 | 细节 |
|---|---|
| 代际构成 | `turn_id = format!("{}:{}", conversation_id, counter)`，counter 单调递增 |
| 迟到防护 | `finish(conversation_id, turn_id)` **校验代际**，非当前代际直接忽略并记 debug |
| 取消语义 | `cancel` 只置位令牌，**不 `abort`** |
| 子令牌 | `child_token()` 供模型流 / 工具执行 / 审批等待，父取消则子失效 |

**这是本议题最重要的一条可移植结论**：任务管理同样会遭遇「旧任务迟到回调」问题——重启后的新进程状态，可能被旧进程的退出事件覆盖；用户点停止后，旧任务迟到的 `Exited` 可能被当成新任务的退出。`TurnTasks` 给出的解法是**把代际写进身份本身**，而不是在回调里加时间戳比较。

### 2.4 并发策略范式：`ToolPipeline::partition_tool_batches`

`src-tauri/crates/assistant-tools/src/pipeline.rs`：

| 机制 | 细节 |
|---|---|
| 切分依据 | `tool.is_concurrency_safe(arguments)` **自报** |
| 合并规则 | 连续可并发者合为一组，其余各自单独成组 |
| fail-closed | 未注册的工具按**不可并发**处理 |

判定：**任务的并发上限应由任务自报（§3.3、§3.4）**，而不是全局常量。MCP server 单实例、`shell` 可多开、`git` 同仓库需串行——三者的并发语义无法用一个数字表达。

### 2.5 投影范式：`protocol/events.rs`

| 机制 | 细节 |
|---|---|
| 事件名 | 集中在 `event_name` 常量模块，禁止散落字符串 |
| 广播 | `emit_broadcast(app, event, payload)` 统一封装与错误日志 |
| 定向 | `emit_orb_only` 按窗口定向 |

判定：**任务事件必须进 `event_name` 常量表**，否则前端订阅与后端发射会各自硬编码字符串，改名即断。

### 2.6 装配与清扫范式：`setup.rs`

`src-tauri/src/setup.rs` 已确立两条与任务管理直接相关的做法：

| 做法 | 代码事实 | 对本议题的含义 |
|---|---|---|
| 状态统一注入 | `handle.manage(...)` 依次注入 `DbState` / `TurnTasks` / `SessionStates` / `ClockRuntime` | 任务表应是**受管状态**，在 `setup` 中注入而非懒初始化 |
| **启动清扫** | `mark_streaming_messages_interrupted(&conn)`：把上次未完成的流式消息标记为中断 | 任务表同样需要「启动时把上次残留标记为中断」，否则 UI 会显示幽灵任务 |

判定：**「启动清扫」是管理机制的必备要素，且仓库已有先例**。它不是终止问题，而是状态对齐问题——上次应用被杀，任务表里必然留着 `Running` 的假记录。

### 2.7 缺位：没有「回收」要素

| 事实 | 证据 |
|---|---|
| 退出钩子只调一个特性专属函数 | `src-tauri/src/lifecycle.rs` 的 `RunEvent::Exit` 仅 `vault_cleanup_on_exit`，且关闭态是空桩 |
| 名为「终止」的函数不终止 | `assistant-sync` 的 `kill_ssh_sessions()` 只 `log::debug`，非 Unix 直接空函数，且**无调用点** |
| 无统一进程表 | 全仓无 PID 登记、无 `JoinSet`、无进程组 |

判定：**回收是八要素中唯一没有范式可继承的一项**。这也解释了为什么「杀」在直觉里显得像全部——因为它是唯一需要从零设计的部分。

### 2.8 四个调度原语与两处自身监控现状

**调度并非空白，而是原语散落、未被当作调度看待。** 四处代码事实：

| 原语 | 代码事实 | 实际调度语义 |
|---|---|---|
| **拒绝 / 顶替双策略** | `TurnTasks::begin` 的 `OnBusy`：`Reject` 返回 `Busy` 且旧令牌原样继续；`Replace` 取消旧令牌并递增 counter（旧代际已取消时按 `Replace` 顶替） | **这是抢占**：`Replace` = 新任务抢占旧任务，`Reject` = 不抢占、拒绝新任务 |
| **声明式并发分组** | `partition_tool_batches`：`is_concurrency_safe` 自报 + 连续合并 + 未注册按不可并发（fail-closed） | **这是分组**：串行 / 并行由任务自报，不由机制层指定 |
| **限速闸** | `src-tauri/src/cmd/vault/audit.rs`：`HIBP_CONCURRENCY = 2`、`HIBP_MIN_INTERVAL_MS = 1500`、`Semaphore::new(1)` | **这是速率调度**（不是并发调度）：许可证 + 最小间隔 |
| **消费方专属退避** | `docs/store/I38e-mcp-tools-spec.md` §4.2：指数退避 1s / 2s / 4s / 8s 上限 60s、最多 5 次；握手超时 30s；调用超时 30s 且受 turn 剩余预算约束 | **这是重试调度**：但只写在 MCP 规格里，机制层未定「重试归谁」 |

另有一处**被写成调度、但没被识别**的决策：I38e §4.2 第 1 条「从 `mcp_servers` 读取 `enabled = 1` 的 server 并全部启动，失败只记日志、不阻塞启动」——这是「启动即全启、非懒启动、失败不阻塞」的调度选择，但规格里没有作为调度判定出现。

**自身监控现状**（详见 §8）：

| 项 | 状态 | 证据 |
|---|---|---|
| 自身 CPU / 内存采样 | **完全没有** | 全仓无 `sysinfo`、无 `GetProcessMemoryInfo`、无 `/proc/self` 读取 |
| 周期性采样的先例 | **有，但形态偏旧** | `setup.rs` 的 `spawn_screen_inspection`：`std::thread::spawn` + `sleep(固定间隔)` + `should_exit()` 退出判据 |
| 磁盘自限先例 | **有，且是唯一一个** | `plugins.rs`：`RotationStrategy::KeepSome(3)` + `max_file_size(10MB)` |
| 诊断产物目录 | **有** | `app_dirs` 的 `logs()` / `crashes()` 同落 local 根，不进漫游 |
| 启动预算记录 | **无** | 只有零散的 `Instant::now()`，无统一预算与回归阈值 |

判定：**磁盘维度的自限已做，内存 / CPU 维度空白**。这个不对称本身就是结论——自监控在仓库里只被当作「日志轮转」处理过，没被当作一类能力。

## 3 逐要素判定

### 3.1 身份：键、不可变性与代际

| 子问题 | 判定 | 依据 |
|---|---|---|
| 主键是什么 | **内部 id 为主键，展示名为别名** | `ToolRegistry` 双表已验证该形状（§2.1） |
| id 可不可变 | **不可变**；改名只改别名 | 与 `mcp_servers.id` 的既定约定一致（I38e §3.1） |
| 是否需要代际 | **需要，且必须写进身份** | `TurnTasks` 的 `conversation_id:counter`（§2.3） |

**代际的必要性论证**：

任务的生命周期包含「停止 → 重启」。若 id 只是 `server_id`，重启后的新实例与旧实例同 id，会出现三类错误：

1. 旧实例的退出回调把新实例标记为 `Exited`；
2. 用户点「停止」时打到新实例，而用户想停的是旧实例；
3. 事件流里两次 `Started` 无法区分，前端状态覆盖顺序错乱。

三条的共同解法是**让 id 本身随代际变化**（`{id}:{gen}`），并在所有写入点校验代际——与 `TurnTasks::finish` 完全同构。

判定：**成立，且不可省略**。省略后的补救（时间戳比较、状态内嵌 PID 比较）都会引入新的不确定性。

### 3.2 登记：先登记后启动

| 顺序 | 后果 |
|---|---|
| 先启动 → 后登记 | 启动与登记之间存在窗口；此刻用户点停止、应用退出、或启动失败，表里都没有记录，无从处理 |
| **先登记 → 后启动** | 表里先有一条 `Starting` 记录；启动失败则转 `Failed`，成功则转 `Running` |

判定：**先登记后启动是硬约束，不是优化**。它把「启动失败」从「异常路径」变成「状态转移」，这正是管理机制存在的意义——把一切异常都收敛为状态。

补充：登记必须在**受管状态**内（`setup` 注入），不能懒初始化，否则「应用启动后、首次使用前」的任务表不存在，等于放弃这段时间的管理。

### 3.3 准入：闸与配额

| 子问题 | 判定 | 依据 |
|---|---|---|
| 是否需要准入闸 | **需要** | `SessionStates::can_start_new_turn` 已验证（§2.2） |
| 闸的判据形态 | **「状态 + 可恢复性」的函数** | 同上；不得写成状态名相等判断 |
| 并发上限来源 | **任务自报，非全局常量** | `partition_tool_batches` 的声明驱动 + fail-closed（§2.4） |
| 是否需要队列 | **需要，但只对「同 id 串行」生效** | 见下 |

**配额判定细节**：

- MCP server 是**单实例资源**（一个 server 只能有一个进程），第二个启动请求必须被拒绝或排队，不能并行；
- `shell` 类任务**可以多开**，但应有总量上限，否则模型可以一次拉起几十个进程；
- `git` 类任务在**同一仓库**上必须串行（否则索引锁冲突）。

三者对应三种不同的准入语义，因此上限必须由任务自报（「我这类最多 N 个」+「我是否独占某资源」），而不是一个全局 `max_tasks`。

判定：**闸成立，配额半成立**——机制可以统一，数值必须分散。

**准入与调度的分界**：本节只回答「此刻允不允许启动」。一旦允许，接下来「谁先跑、跑几个、有人要位置怎么办」全部属于 §3.4。两者共用同一个判据入口（准入闸是调度的前置），但**不能共用同一张判定表**——准入随状态变化，调度随策略变化。

### 3.4 调度：粒度、分组、抢占、背压

**这是八要素中唯一「有原语、无判定」的一项。**

#### 3.4.1 调度要素判定

| 子问题 | 判定 | 依据 |
|---|---|---|
| 调度对象是进程还是任务 | **两者都有，但必须按「长驻 / 一次性」分治** | 见 3.4.2 |
| 并发分组由谁决定 | **任务自报 + fail-closed**（复用 `partition_tool_batches`） | §2.4、§2.8 |
| 是否允许抢占 | **允许，但必须按「触发者 + 归属」分策略**（复用 `OnBusy` 双策略） | 见 3.4.3 |
| 优先级 | **不做**；同 id 内 FIFO | 见 3.4.4 |
| 背压（队列满） | **拒绝，不无限等待** | 见 3.4.4 |
| 重试归属 | **归消费方，机制层不提供通用重试** | I38e §4.2 已把退避写在消费方 |
| 速率限制 | **复用「许可证 + 最小间隔」形态** | `audit.rs` 的 `Semaphore::new(1)` + `HIBP_MIN_INTERVAL_MS`（§2.8） |
| 启动时机 | **配置面全启，非懒启动，失败不阻塞** | I38e §4.2 第 1 条（§2.8） |

#### 3.4.2 调度粒度：长驻不排队，一次性才排队

| 类别 | 例子 | 是否排队 | 理由 |
|---|---|---|---|
| **长驻进程** | MCP server | **不排队**；启动即占位，后续请求被 `Reject` 或复用 | 单实例资源，排队没有意义——队列里等的是「同一进程」，不是「新进程」 |
| **一次性进程** | `shell`、`git`、`ssh-add` | **排队**；按归属分组、按自报上限准入 | 每次调用都是新进程，需要总量约束与顺序 |

判定：**把两类放进同一条队列不成立**。长驻进程排队会造成「第二个请求等第一个进程退出」的语义错误；一次性进程不排队则失去总量约束。

#### 3.4.3 抢占：必须有显式语义，且要与失败区分

仓库已在 turn 层选择**双策略**（§2.8）：`chat` 走 `Replace`（静默顶替旧 turn）、`agent` 走 `Reject`（返回 `Busy`，旧 turn 继续）。任务层必须给出同类判定，而不是继承默认行为：

| 归属 | 建议策略 | 理由 |
|---|---|---|
| 用户显式动作（设置页重启 server） | **Replace** | 用户意图就是「换掉旧的」；返回 `Busy` 会让开关失效 |
| 模型自动发起（重连、重新拉起） | **Reject** | 自动路径不得顶掉用户正在使用的实例 |
| 后台派生（将来的子代理、后台任务） | **Reject** | 与 `agent` 一致，避免后台把前台挤掉 |

**被抢占任务的退出语义（必须显式定义）**：

| 处理方式 | 后果 | 判定 |
|---|---|---|
| 记为 `Failed` | 面板出现假故障；告警与重试被误触发 | **不合理** |
| 记为 `Exited` 且原因 = 被抢占 | 状态诚实，不触发故障统计 | **合理** |
| 静默删除记录 | 用户看不到「我重启过它」，无法解释端口释放延迟 | **不合理** |

判定：**抢占必须在状态机里有一等表示**（`Stopping` → `Exited`，附带「被抢占」原因），不能借用失败路径。这条判定直接约束 §3.5 的状态字段与 §3.6 的投影字段。

#### 3.4.4 优先级与背压

| 子问题 | 判定 | 理由 |
|---|---|---|
| 是否引入优先级 | **不引入**；同 id FIFO | 引入优先级必须同时定义「谁可以设、能否被用户改、饥饿怎么防」；当前唯一消费者（MCP server）是单实例、无竞争，引入即为过度设计 |
| 队列满时 | **拒绝**（返回 `Busy` 类错误），不排队等待 | 与 `OnBusy::Reject` 同构；无限等待会让模型侧超时被误判成「任务卡住」，且失去背压 |
| 队列上限 | **由任务自报**（§3.3），机制层只校验 | 与并发上限同源 |
| 是否允许「丢弃最旧」 | **不允许** | 丢弃最旧等于静默抢占，与 §3.4.3 的显式抢占冲突 |

判定：**「不做优先级 + 拒绝式背压」是当前唯一自洽的组合**——它使调度退化为「准入闸 + 队列长度检查」，与仓库既有范式同构，且不引入饥饿问题。

#### 3.4.5 调度与取消的关系

| 命题 | 判定 |
|---|---|
| 取消令牌是调度手段 | **不成立**。取消令牌表达「不要了」，调度表达「等一等」；用取消代替排队会让状态机无法区分「用户停止」与「还没轮到」 |
| 抢占可以复用取消令牌 | **成立**。`Replace` 的实现就是「取消旧令牌 + 递增代际」（§2.8），无需新增机制 |
| 排队任务被取消 | **必须支持**。排队中的任务同样持有令牌，取消即从队列移除并转 `Exited`（原因 = 取消），不留幽灵条目 |

### 3.5 状态：两层状态机

**这是本议题最容易被做错的一处。**

| 形态 | 后果 | 判定 |
|---|---|---|
| 单一枚举，把 `Ready` / `Error` 等 MCP 语义并入顶层 | 每新增一类任务就要加枚举分支，`CODE-SPLIT-PRINCIPLE` 意义上的「一个文件多个变化原因」 | **不合理** |
| 两层：通用态 + 领域态 payload | 通用态固定，领域态由消费方定义 | **合理** |
| 不做状态机，只用 `running: bool` | 无法表达 `Stopping`，停止与已退出不可区分，UI 无法显示正确进度 | **不合理** |

**建议的两层形态**（判定合理，非实施要求）：

| 层 | 内容 | 谁定义 |
|---|---|---|
| 通用态 | `Registered` / `Queued` / `Starting` / `Running` / `Stopping` / `Exited` / `Failed` | 机制层固定，不随消费方增长 |
| 领域态 | 例如 MCP 的 `Ready` / `Error`、`shell` 的退出码与信号 | 消费方，作为通用态的附加字段 |

判定依据：通用态回答「进程还活着吗、正在被停吗」，领域态回答「业务上能不能用」。两者的变化原因不同，必须分开。

**`Stopping` 不可省略**：停止是异步的（发出信号 → 等待退出 → 超时强杀），没有 `Stopping` 就无法表达「已请求停止但尚未结束」，UI 只能显示一个错误的 `Running` 或提前显示 `Exited`。

**`Queued` 由 §3.4 引入**：既然一次性进程要排队（§3.4.2），就必须有「已登记、未启动」的显式状态，否则排队中的任务会显示成 `Starting`，与「正在拉起进程」混淆。

**`Exited` 的终止原因必须带分类**：正常退出 / 被用户停止 / 被抢占 / 超时强杀 / 启动失败。缺了分类，§3.4.3 的「抢占不记失败」就无法落地。

### 3.6 可见：snapshot + delta 双通道

| 通道 | 作用 | 缺了会怎样 |
|---|---|---|
| **snapshot**（命令拉取全量） | 冷启动、窗口重建、诊断 | 只有事件流时，前端打开面板看不到历史任务 |
| **delta**（事件推送增量） | 实时更新 | 只轮询时，状态变化有延迟且浪费 IPC |

判定：**双通道成立**，且必须遵守项目既有的 DTO 约束：

- 任务快照必须走 `src-tauri/src/protocol/dto/` + `ts-rs` 生成的契约，跑 `npm run contract:gen`；
- 禁止用 `Record<string, unknown>` 传部分字段（项目规则明令禁止）；
- 事件名必须进 `event_name` 常量表（§2.5）；
- 输出 DTO 的 `Option` 键恒在、值 `null`（项目规则）。

**投影的最小字段集**（判定必要，超出即为无谓扩张）：

| 字段 | 为什么必要 |
|---|---|
| id（含代际） | 唯一标识，停止与对齐都靠它 |
| 通用态 + 领域态 | UI 显示的唯一依据 |
| 终止原因分类（正常 / 停止 / 抢占 / 超时 / 失败） | §3.4.3、§3.5 的判定要求 |
| 排队位次（仅 `Queued`） | 有队列就必须能解释「为什么还没跑」（§3.4.4） |
| 启动时间 / 结束时间 | 判断「卡住」与「刚退出」 |
| 退出码 / 失败原因 | 诊断与重试决策 |
| 所属归属（会话 / 特性 / server） | 按归属过滤与批量停止；也是抢占分策略的键（§3.4.3） |
| 输出尾部 N 行（有界） | 面板可用性；**必须有上限**（`CODE-REVIEW-PRINCIPLE` 硬要求） |

**不应进投影的字段**：完整 stdout/stderr、环境变量值、命令行明文（含凭据）。这三者属于「日志与诊断」，不属于「面板展示」，混入会同时违反凭据约束与输出预算。

### 3.7 回收：唯一真缺口

回收包含四个子项，只有第一项是「杀」：

| 子项 | 判定 | 说明 |
|---|---|---|
| **终止语义** | 成立但零依赖不成立 | 单层 `kill` 只杀一层；树杀需 Windows Job Object（`windows` crate 需加 `Win32_System_JobObjects` + `Win32_System_Threading`）与 Unix `process_group(0)` + 组杀（需 `libc` / `nix`） |
| **幂等停止** | 成立且必要 | 对已退出任务调用停止必须成功返回；应返回三态（已退出 / 已停止 / 超时），而不是 `Result<(), Error>`，否则 UI 停止按钮会报错 |
| **退出收口** | 不成立（缺位） | 现状只有 `lifecycle` 调 vault 清理；任务表需要「退出时遍历全部任务并回收」的统一入口 |
| **启动清扫** | 成立（有范式） | 上次异常退出后表里残留的 `Running` 必须在启动时改判（§2.6） |

**退出收口的形态判定**：不应再新增一条 `crate::mcp::shutdown()` 这类**调名边**。理由与 `docs/analysis/FEATURE-ZERO-COST-MOUNT-ANALYSIS.md` §4.2 一致——core 调名会让「关闭态仍需空桩」的负担回来。任务表本身就是一个天然的清理聚合点：**退出时遍历表即可，无需知道谁是谁**。

**回收的平台事实**（只需知道结论，不展开）：

| 平台 | 树杀 | 退出即回收 |
|---|---|---|
| Windows | Job Object `TerminateJobObject` | `KILL_ON_JOB_CLOSE`（内核保证） |
| macOS | `kill(-pgid)`（需 `libc`） | 无对等机制 |
| Linux | `kill(-pgid)`（需 `libc`） | `PR_SET_PDEATHSIG`（Linux 专有） |

**挂载竞态**（必须记录）：`AssignProcessToJobObject` 在 `spawn()` 之后调用时，子进程可能在挂载前就派生后代，导致后代逃出 Job Object。消除方式是 `CREATE_SUSPENDED` → 挂载 → `ResumeThread`，代价是启动路径复杂度上升。这是回收成本的隐藏项。

### 3.8 治理：权限与审计

| 子问题 | 判定 | 依据 |
|---|---|---|
| 任务管理器可否绕过审批网关启动进程 | **不可** | 网关（`ToolGateway`）是权限唯一入口；绕过即形成旁路 |
| 「配置面启动」与「调用面执行」是否同一路径 | **不是，必须分开** | 见下 |
| 是否留痕 | **需要，但复用现有审计存储** | `PermissionAuditStore` 已在用，不新建表 |

**两条治理路径的区分**（本要素的核心判定）：

| 路径 | 触发者 | 是否走审批 | 理由 |
|---|---|---|---|
| **配置面启动**（MCP server 启动） | 用户在设置页显式 `enabled` | **不走审批** | 这是配置动作，用户已通过开关表达意图；每次启动都弹审批会把「开开关」变成「无限弹窗」 |
| **调用面执行**（模型调工具） | 模型发起工具调用 | **走审批** | 这是 `ToolGateway` 的既有职责，不得因「进程已启动」而放行 |

判定：**治理成立的前提是这两条路径不共用同一个审批键**。若共用，会出现两种错误：要么配置面启动被反复审批，要么调用面执行因「server 已就绪」被隐式放行。

**与调度的交叉**：§3.4.3 的「用户显式动作走 `Replace`」意味着**治理路径决定调度策略**——同一任务由用户重启与由模型重连，抢占行为必须不同。因此调度策略不能只看任务类型，必须带「触发者」维度。

## 4 机制形态判定

### 4.1 三种候选形态

| 形态 | 内容 | 判定 |
|---|---|---|
| A 统一全局 `TaskManager` | 一张表管所有任务，含状态机、配额、调度、重试、观测 | **不合理**：契约被唯一消费者绑架；状态机会被 MCP 语义污染；调度策略会被单实例场景固化成「不排队」 |
| B 完全分散 | 每个消费方自建进程表与状态机 | **不合理**：代际、登记顺序、调度判定、退出收口四件重复实现，且必然分叉 |
| C **分层：机制层 + 消费方** | 机制层提供身份 / 登记 / 准入闸 / 调度骨架 / 通用态 / 投影 / 回收；消费方提供领域态、自报配额、抢占策略 | **合理** |

### 4.2 判定依据

| 判据 | 说明 |
|---|---|
| 变化原因分离 | 机制层随「管理语义」变化，消费方随「业务语义」变化——符合 `CODE-SPLIT-PRINCIPLE` |
| 与既有范式同构 | 机制层的形状与 `ToolRegistry` + `SessionStates` + `TurnTasks` + `partition_tool_batches` 一致，不引入新范式 |
| 消费方数量 | 当前唯一明确消费者是 MCP server；机制层只做「任何消费方都需要」的部分，避免过度设计 |

判定：**C 成立**。但机制层的落点由消费者数量决定（§9）。

### 4.3 调度与观测的归属

| 项 | 归属 | 理由 |
|---|---|---|
| 调度骨架（队列、准入闸调用、抢占原语） | **机制层** | 任何消费方都需要，且形状已由 `OnBusy` / `partition_tool_batches` 定死 |
| 调度策略（谁可抢占、上限多少、是否排队） | **消费方自报** | 与 §3.3 配额同源；机制层只校验不决定 |
| 受管任务观测 | **不做** | 与 §3.4 调度无因果；独立成特性（§9.3） |
| 自身占用监控 | **独立于任务表** | 自指禁区（§8.1）；只能与投影通道共用，不能与任务表共用 |

## 5 与既有机制的冲突矩阵

| 既有机制 | 与本议题的关系 | 必须遵守的边界 |
|---|---|---|
| `TurnTasks`（取消树） | **复用** | 任务接受外部传入的 `CancellationToken`；**不得另建取消总线**；不得把取消当排队（§3.4.5） |
| `OnBusy`（拒绝 / 顶替） | **复用形状** | 抢占判定沿用双策略，但策略值由触发者与归属决定（§3.4.3）；不得把被抢占记为 `Failed` |
| `SessionStates`（会话状态） | **复用形状，不共用表** | 会话态回答「这轮对话在跑吗」，任务态回答「这个进程活着吗」；合并会让两者互相污染 |
| `ToolRegistry`（工具注册表） | **复用形状** | 工具 id 与任务 id 是两套身份；MCP 工具名派生自 server id，但任务 id 含代际，二者不可混用 |
| `partition_tool_batches`（并发分组） | **复用** | 任务自报并发安全 + fail-closed；不得在机制层另设并发白名单 |
| `Semaphore` + 最小间隔（`audit.rs`） | **复用形态** | 速率调度用「许可证 + 最小间隔」；不得用 sleep 轮询替代 |
| `ToolGateway`（审批网关） | **不得绕过** | 配置面与调用面分路径（§3.8） |
| `exec::invoke`（工具超时） | **口径分离** | 该 deadline 只在 `await` 点抢占，**不得**作为进程超时的实现；进程层超时必须先触发并完成回收 |
| `lifecycle`（退出钩子） | **改形态** | 从「调名」改为「遍历任务表」，否则新增一条 core 调名边 |
| `protocol/events`（事件） | **接入** | 事件名进 `event_name` 常量表；调度状态变化（入队 / 出队 / 被抢占）同样要发事件 |
| `app_dirs`（受管目录） | **接入** | 任务日志与落盘输出走受管目录，不落 cwd；自监控快照同样落 `logs()` 同级 |
| `spawn_screen_inspection`（周期线程） | **参照，不复用** | 自监控可参照其「固定间隔 + `should_exit()`」形态，但必须改为可配置间隔与失败不重试（§8.4） |
| `plugins.rs` 日志轮转 | **复用形态** | 自监控落盘同样需要 `KeepSome` + 单文件上限（D10 硬要求） |

## 6 缺口清单

| # | 缺口 | 归属 | 是否阻塞「管理机制成立」 |
|---|---|---|---|
| G1 | 无代际键 | G | **是**（迟到回调会污染状态） |
| G2 | 无「先登记后启动」的顺序约束 | G | **是**（存在管理盲区） |
| G3 | 通用态 / 领域态未分层 | G | **是**（枚举会随消费方膨胀） |
| G4 | 无 snapshot 通道与 DTO | G | **是**（面板无法冷启动对齐） |
| G5 | 无准入闸与自报配额 | G | 否（可先做单消费者约束） |
| G6 | 无启动清扫 | G | **是**（幽灵 `Running` 记录） |
| G7 | 无统一退出收口 | R | **是**（退出即残留） |
| G8 | 无跨平台树杀 | R | 否（可先单层 + 文档声明边界） |
| G9 | Unix 无退出即回收 | R | 否（可先声明为已知边界） |
| G10 | 无受管任务观测（CPU / 内存） | O | 否（**不在管理机制范围**） |
| G11 | 14 处 `std::process` 未迁移 | G/R | 否（存量债，非新机制阻塞项） |
| G12 | 无调度判定：抢占语义、背压、粒度分治均未定 | G | **是**（决定状态机字段与事件语义，事后改要动所有消费方） |
| G13 | 无 `Queued` 态 | G | **是**（排队任务会被显示成 `Starting`） |
| G14 | 终止原因无分类 | G | **是**（抢占与失败无法区分） |
| S1 | 「本应用占用」口径未定义 | S | 否（不阻塞管理机制，但阻塞 DTO 字段定稿） |
| S2 | 无自身占用采样 | S | 否 |
| S3 | 峰值无外部留痕 | S | 否（但必须承认「峰值不可自测」） |
| S4 | 采样频率与失败策略未定 | S | 否（不定则违反 D10 节流要求） |

判定：**阻塞项全部属于 G 与 R，且 G 占 7 项**——这直接印证「管理机制是主体、终止是子项、调度是被遗漏的一项」。

## 7 反例

| 反例 | 破坏点 |
|---|---|
| 用 `running: bool` 代替状态机 | 无法表达 `Stopping`，停止与已退出不可区分 |
| 任务 id 不含代际 | 旧实例退出回调覆盖新实例状态（§3.1） |
| 先 `spawn` 后登记 | 启动窗口内无法停止、无法回收（§3.2） |
| 把 MCP 的 `Ready` / `Error` 并入通用枚举顶层 | 每新增消费方就加枚举分支（§3.5） |
| 只发事件、不做 snapshot | 面板冷启动为空；窗口重建后状态丢失（§3.6） |
| 快照里带完整 stdout 或命令行明文 | 违反输出预算与凭据约束（§3.6） |
| 另建全局取消总线 | 与 `TurnTasks` 形成两个真源 |
| 任务管理器直接 `Command::new` 启动并宣称「已管理」 | 绕过准入闸与登记，等于无管理 |
| 配置面启动也走工具审批 | 开开关变无限弹窗（§3.8） |
| 因「server 已就绪」而放行工具调用 | 权限旁路（§3.8） |
| 用 `tokio::time::timeout` 包子进程冒充进程超时 | 只放弃 `await`，进程继续跑（I31 工具框架规格（已归档）§4.3） |
| 用 `Child::kill()` 冒充树杀 | 只杀一层，`git` / `cmd /c` / MCP server 后代成孤儿 |
| 在 core 里写 `crate::mcp::shutdown()` | 新增 core 调名边，零成本挂载失效（§3.7） |
| 把任务表做成无归属维度的全局单例 | 「停止」退化为「停全部」，且与会话级绑定口径冲突 |
| 宣称任务可跨重启存活 | 进程已随应用退出而死；「恢复」只能是重新启动（I36 design（已归档）D13，I38e §1.2 非目标） |
| **长驻 server 与一次性 `shell` 共用一条队列** | 第二个请求会等第一个进程退出；语义错误（§3.4.2） |
| **被抢占的任务记为 `Failed`** | 面板出现假故障，告警与重试被误触发（§3.4.3） |
| **队列满时无限等待** | 失去背压；模型侧超时被误判为「任务卡住」（§3.4.4） |
| **引入优先级但不定义饥饿防护** | 低优先任务永不执行，且无判据可查（§3.4.4） |
| **机制层自带通用重试** | 与 I38e 的退避叠加成双退避，重连次数翻倍（§3.4.1） |
| **用取消令牌代替排队** | 无法区分「用户停止」与「还没轮到」（§3.4.5） |
| **把宿主自身登记进受管任务表** | 自指：停止自己 = 应用自杀（§8.1） |
| **在主线程高频采样自身内存** | 违反 D10「主线程不得同步 IO / 高频事件必须节流」（§8.4） |
| **声称可观测自身内存峰值** | OOM / 卡死时采样器与被观测者同生共死（§8.4） |
| **混用 RSS / 工作集 / 私有工作集口径** | 同一状态两个数字，用户会当成泄漏（§8.2） |

最值得注意的五条：**`running: bool`**、**无代际**、**先启动后登记**、**长驻与一次性共用队列**、**被抢占记为失败**。前三条不会在功能演示时暴露，只在「重启一次」「停止一次」「启动失败一次」之后以状态错乱的形式浮现；后两条只在「第二个消费者出现」或「用户重启一次 server」之后暴露——而它们恰好都是管理机制的定义性内容。

## 8 自身占用监控（范围外但需定案）

**为什么单列一节**：它不属八要素，却与任务观测共用投影通道，并且决定 DTO 字段与用户文案。把它并入 §1.4 的「O」里，会同时丢掉「自指禁区」与「口径必须显式选」这两个约束。

### 8.1 与受管任务观测的差异

| 维度 | 受管任务观测 | 本应用自身观测 |
|---|---|---|
| 观测对象 | 子进程（MCP server、`git`、`shell`） | 宿主进程 + WebView 进程 + 自身派生的子进程 |
| 采样时机 | 任务存在时 | 全程，且需覆盖启动期 |
| 失败模式 | 采样失败只影响该任务显示 | **采样器与被观测者同进程**：OOM / 主线程卡死时，采样器自身也失效 |
| 目的 | 面板展示、停止决策 | 泄漏检测、启动预算回归、崩溃现场留存、用户可见健康度 |
| 可否进任务表 | 可以 | **不可以**（自指：登记自己 → 停止自己 = 应用自杀） |
| 依据 | 产品功能 | `CODE-REVIEW-PRINCIPLE` D10 是**硬要求** |

判定：**两者只能共用「投影通道 + DTO 约束」，不能共用任务表，也不能共用停止语义。**

### 8.2 三种「本应用占用」口径

Tauri 应用是「主进程 + 若干 WebView2 子进程」。任务管理器里看到的是多个进程，因此「本应用占多少」必须先选口径：

| 口径 | 含什么 | 适用场景 | 风险 |
|---|---|---|---|
| **仅主进程** | 宿主 Rust 进程 | 诊断内存泄漏（定位到自己的堆） | 用户看到 200MB，任务管理器看到 900MB，被判为「数据造假」 |
| **主进程 + WebView 进程** | 含 `msedgewebview2.exe` 若干 | **面向用户的「这个应用占多少」** | 需按进程树归属判定，跨平台识别方式不同 |
| **上述 + 受管子进程** | 再含 MCP server 等 | 容量规划、卸载前的残留检查 | 与「任务面板」数字重叠，容易被误读成任务占用 |

判定：**必须显式选一种作为默认展示口径**，其余作为二级明细。**不选口径就是默认选了「仅主进程」**——而它恰好是最容易被用户质疑的那个。

**单位口径同样必须固定**：RSS / 工作集 / 私有工作集 / 虚拟内存四者不同，Windows 任务管理器显示的是工作集。前端文案必须写明是哪一种，否则「内存 300MB」会被当成泄漏。

### 8.3 平台能力矩阵

| 平台 | 自身内存 | 自身 CPU | 零依赖 |
|---|---|---|---|
| Linux | `/proc/self/statm`、`/proc/self/status`（`VmRSS` / `VmHWM`） | `/proc/self/stat` | **成立** |
| Windows | `GetProcessMemoryInfo` | `GetProcessTimes` | 不成立（需 `windows` 特性） |
| macOS | `task_info` / `libproc` | 同左 | 不成立（需 `libc` 或第三方） |
| 跨平台统一 | `sysinfo`（含 `self()`） | 同左 | 不成立（需新增依赖） |

判定：**「跨平台零依赖」不成立，Linux 单独成立**。这与 §3.7 回收成本的结构完全同构——平台差异集中在两处，且都需要特性开关或新依赖。`windows` crate 已启用 18 个特性但不含进程状态相关项，与 Job Object 的特性缺口是同一类问题。

### 8.4 四条硬约束

| # | 约束 | 依据 |
|---|---|---|
| 1 | **自指禁区**：宿主不得登记进受管任务表 | 停止语义冲突（§8.1） |
| 2 | **峰值必须外部留痕**：OOM / 卡死时自采样必然失效，峰值只能由 crash dump、OS 记录或「宿主挂进 Job Object 后的内核统计」提供 | 采样器与被观测者同生共死 |
| 3 | **采样频率必须有上限**：低频（秒级起步）+ 事件驱动 + **采样失败不重试** + 不得在主线程 | D10「高频事件必须合并或节流」「主线程不得同步 IO」 |
| 4 | **落盘产物必须自限**：自监控快照落 `logs()` 同级，复用 `KeepSome` + 单文件上限 | D10「磁盘侧产物必须有轮转与总量上限」 |

### 8.5 与 D10 的对应关系

| D10 条目 | 现状 |
|---|---|
| 磁盘侧产物必须有轮转与总量上限 | **部分满足**：日志侧已满足（`plugins.rs`）；崩溃转储与工具结果未统一 |
| 子进程输出必须有截断上限 | **未满足**（本议题 §3.6 已定） |
| 启动关键路径必须有可测量的预算与回归阈值 | **空白**：只有零散 `Instant::now()`，无统一预算记录 |
| 高频事件必须合并或节流 | 对**子进程**有约束，对**自身采样**无约束 |

判定：**D10 在「磁盘」维度已被处理过，在「内存 / CPU 维度」完全空白**——这正是自监控应当独立定案的原因：它不是新功能，而是既有硬要求的一条未完成项。

### 8.6 本节判定汇总

| 命题 | 判定 |
|---|---|
| 自身占用属任务管理器的管理机制 | **不成立** |
| 自身占用需独立定案 | **成立**（口径与四条约束不可推迟） |
| 跨平台零依赖 | **不成立**；Linux 成立 |
| 峰值可自测 | **不成立**（必须外部留痕） |
| 可与受管任务观测共用投影通道 | **成立** |
| 可与受管任务共用任务表 | **不成立**（自指） |
| 与 D10 的关系 | 是 D10 的未完成项，不是新增功能 |

## 9 落点与时机

### 9.1 机制层的落点选项

| 选项 | 判定 |
|---|---|
| 新建 crate `assistant-process` | 分层最干净；但当前只有一个消费者，新建 crate 的维护成本大于收益 |
| 放进 `assistant-tools/src/process/` | 零新增 crate；但「工具」与「任务管理」语义混住 |
| **写在首个消费者内（`src-tauri/src/mcp/`）并保持可搬走** | **当前阶段合理**：`src-tauri/src/` 下尚无 `mcp/` 目录，消费者未落地 |

判定：**机制层的形状现在就定，位置等消费者落地再定**。区分「形状」与「位置」是本议题唯一能提前做的事。

### 9.2 现在必须定型的六项（写错就要重构）

| # | 内容 | 为什么不能推迟 |
|---|---|---|
| 1 | 身份含代际（`{id}:{gen}`） | 后续所有停止、对齐、事件去重都依赖它 |
| 2 | 先登记后启动 | 影响调用顺序，事后无法通过加代码补回 |
| 3 | 通用态 / 领域态分层（含 `Queued` 与终止原因分类） | 影响枚举形状，事后拆分要改所有消费方 |
| 4 | snapshot + delta 双通道 + DTO 契约 | 影响 wire 契约，事后改需 `contract:gen` 重跑与前端适配 |
| 5 | **抢占语义**（策略值由触发者 + 归属决定；被抢占记 `Exited` 不记 `Failed`） | 决定状态字段与事件语义，事后改要动所有消费方（§3.4.3） |
| 6 | **自身占用口径**（默认展示哪一种、单位是哪一种） | 决定 DTO 字段名与用户文案，事后改要重写前端（§8.2） |

### 9.3 现在可以推迟的四项

| # | 内容 | 推迟理由 |
|---|---|---|
| 1 | 自报配额的具体数值与队列长度上限 | 单消费者下用「单实例约束」即可覆盖；**但背压形态（拒绝而非等待）不可推迟**（§3.4.4） |
| 2 | 跨平台树杀 | 可先单层 + 显式声明边界；但**必须在文档写清**，否则会被当成已支持 |
| 3 | 受管任务观测与自身占用采样本身 | 需新依赖，且功能边界未定；**但口径与四条约束不可推迟**（§8.4） |
| 4 | 优先级与公平性 | 当前无竞争消费者，引入即过度设计；**但「不做优先级」这一判定必须写进文档**，否则会被实现成隐式策略 |

### 9.4 时机判定

| 阶段 | 形态 |
|---|---|
| **现在** | 在 MCP 落点内按 §9.2 的六项定型机制层；`spawn/stop` 走统一封装，不直接 `Command::new`；调度按 §3.4 的「长驻不排队 / 一次性排队 + 拒绝式背压 + 触发者决定抢占」落地 |
| **第二个消费者出现时** | 把机制层搬为独立模块或 crate；此时抽象有依据，契约不被单一消费者绑架 |
| **始终不做** | 通用任务编排 UI、跨重启存活、CPU 配额调度、优先级与公平性、把观测当作管理机制的前置 |

## 10 结论

| 命题 | 判定 |
|---|---|
| 本议题的主体是管理机制 | **成立**；八要素中六项属机制与治理，一项（回收）属平台适配，一项（调度）属被遗漏的判定 |
| 管理机制可复用既有范式 | **形状可复用**（注册表 / 状态机 / 代际 / 并发批次 / 事件 / 装配清扫 / `OnBusy` / `Semaphore`），**语义必须重定义** |
| 唯一真缺口 | **回收**（跨平台树杀、Unix 退出回收、统一退出收口） |
| 被遗漏的判定 | **调度**（粒度分治、抢占语义、背压形态、重试归属、优先级不做） |
| 最易被做错的三处 | `running: bool` 代替状态机、身份不含代际、先启动后登记 |
| 最易被高估的部分 | 终止（它是兜底路径，不是管理机制） |
| 最易被误纳入的部分 | 受管任务观测（度量不是管理，且标准库不提供） |
| 最易被混淆的部分 | 自身占用监控（观测对象是宿主，且自指不可入任务表） |
| 与既有架构的关系 | 取消树复用、`OnBusy` 复用形状、会话态不共用、并发分组复用、审批不旁路、超时口径分离、退出钩子改遍历 |
| 当前应做 | 定型六项机制形状（代际键 / 登记顺序 / 状态分层 / 双通道契约 / 抢占语义 / 自身占用口径），回收做成可搬走的封装 |
| 当前不应做 | 统一全局 `TaskManager`、受管任务观测、自身占用采样实现、跨重启存活、CPU 配额、优先级与公平性 |

最终判定：**管理机制成立，且主体成本在「身份、登记、准入、调度、状态、可见」六件事上，不在「怎么杀」。** 正确的落点是「在首个消费者内部按既有范式定型机制形状，把调度从隐式行为提升为显式判定，并把回收做成唯一一处可替换的平台适配」，而不是「先建一个以终止为核心的进程管理组件」。
