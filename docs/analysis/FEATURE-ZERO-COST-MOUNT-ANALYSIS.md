# 可选特性零成本挂载：设计思路合理性分析

> 性质：分析。只判定"零成本挂载"这一目标本身能否成立、成立需要什么样的设计前提、哪些部分注定不可归零。不含实施步骤与排期。
> 前置分析：`docs/analysis/FEATURE-OPTIONAL-BINARY-ANALYSIS.md`（引入方式的合理性，D1/D2/D3 三自由度）
> 事实基线：仓库当前代码；`docs/store/vault-optional-build.md`（L1 已实施，L2~L5 未实施）
> 拆分判据一律引用 `docs/principle/CODE-SPLIT-PRINCIPLE.md`，本文不复述。

---

## 0 结论速览

| # | 命题 | 判定 | 依据 |
|---|---|---|---|
| 1 | "零成本"以"装配点个数"计量是伪命题 | **不成立**，必须先拆分成本口径 | 8 个装配点里混着"声明存在"与"接入运行期"两类语义 |
| 2 | 声明成本可归零 | **不成立** | `Cargo.toml` 的 `[features]` 与 `dep:` 门控是 cargo 语义要求；清单条目是特性存在的定义 |
| 3 | 挂载成本可归零 | **成立** | 6 个挂载点中 5 个可在构建期从清单派生，1 个（capabilities）可降级为特性本体文件 |
| 4 | 前端"零手写 + 真删除 + 入库"三者可同时满足 | **成立，但只有一种形态** | 生成物内容只依赖清单、开关仍以字面量参与条件判断（§5） |
| 5 | 零成本的核心前提是"core 只遍历、不调名" | **成立，且是必要条件** | 空桩手法的唯一存在理由就是 core 直接调名（§4） |
| 6 | 零成本的代价是门禁从"存在性断言"退化为"派生一致性断言" | **成立** | 存在性断言正是"每特性手改 8 处"的固化形式（§7） |
| 7 | 全部装配点都能归零 | **不成立** | `tauri.conf.json` 的 `windows` 数组、capabilities 的 `windows` 列表无法从清单派生（§6） |

一句话：**"零成本挂载"在把成本拆成 D（声明）/ M（挂载）/ B（本体）之后是可达的，目标形态是 M=0、D 恒为 2 项、B 不设上限**。它不是一个"更省事"的改动，而是一次**计量口径的更换**：从"数特性必须碰几个文件"换成"数 core 里还剩几处特性字面量"。

## 1 成本计量模型

### 1.1 为什么现有 8 个装配点不是正确的计量单位

`src/features/__tests__/coreBoundary.test.ts` 的 `ASSEMBLY_POINTS` 列了 8 条，语义是"新增一个特性必须触碰的 core 文件"。但这 8 条并不是同一种成本：

- `config/features.json` 的一条条目、`src-tauri/Cargo.toml` 的 `[features]` 声明——这是**让系统知道"存在这个特性"**，任何编译期特性机制都无法免除；
- `registry.ts` 的 `if` 分支、`plugins.rs` 的 `.plugin(...)`、`build.rs` 的 `plugin("vault", ...)`、`capabilities/default.json` 的一行授权——这是**让这个特性在运行期生效**，是真正可以消除的部分。

两类混在一起计，只能得出"零成本不可能"；分开计，才能给出可达目标。

### 1.2 三个成本项

| 记号 | 定义 | 是否可归零 |
|---|---|---|
| **D 声明成本** | 让系统"知道存在这个特性"的最小改动 | 不可归零，恒为固定项 |
| **M 挂载成本** | 让特性"在运行期真正生效"的 core 改动 | **目标归零** |
| **B 本体成本** | 特性自身边界内的文件：`src/features/<id>/**`、`src-tauri/src/<id>_plugin.rs`、`capabilities/<id>.json` | 不设上限，计入特性自身 |

"零成本挂载"的准确含义是 **M = 0**：新增特性只需写 D 的两项 + 自己目录内的 B，不必再编辑任何其它 core 文件。

### 1.3 现状计数

| 装配点 | 归类 | 现状形态 | 证据 |
|---|---|---|---|
| `config/features.json` | D | 1 条目 | 当前仅 `vault` 一项 |
| `src-tauri/Cargo.toml` `[features]` + `default` | D | 2 行 | `vault = [...]` 与 `default = ["vault"]` |
| `src/vite-env.d.ts` | M | 每特性 1 行 `declare const __X__` | 断言要求逐条存在 |
| `src/features/registry.ts` | M | 每特性 3 行 `if / import / push` | `loadFeatures()` 内 |
| `src-tauri/build.rs` | M | 每特性 1 处 `plugin("<id>", InlinedPlugin)` | `PLUGIN_SOURCE` / `COMMAND_PREFIX` 均写死 vault |
| `src-tauri/src/lib.rs` | M | 每特性 1 行 `mod <id>_plugin;` | 模块树静态声明 |
| `src-tauri/src/plugins.rs` | M | 每特性 1 行 `.plugin(<id>_plugin::init())` | `attach()` 链尾 |
| `src-tauri/capabilities/default.json` | M | 每特性 1 行 `"<id>:default"` | ACL 授权 |

**M = 6**。此外还有 3 处不在 `ASSEMBLY_POINTS` 内、但同样属于 M 的成本（在足迹 allowlist 里体现）：`cmd/mod.rs` 的 3 行 vault cfg 与空桩、`lifecycle.rs` 对 `cmd::vault_cleanup_on_exit` 的直接调用、`cmd/config.rs` 的 `apply_vault_side_effects` 调用。

## 2 可归零的三条必要条件

任何"派生式挂载"方案必须同时满足以下三条，缺一条就不成立。

| 判据 | 含义 | 违反后果 |
|---|---|---|
| **R1 构建期可枚举** | 派生源能在构建期被读取，且是唯一真源 | 派生源与清单不一致，产生第二个真源 |
| **R2 派生结果 cfg-free** | 派生出的装配代码不得引入特性 `cfg` | `cfg` 出现在 A2 白名单之外，装配契约直接失败 |
| **R3 不破坏真删除** | 前端开关仍须以字面量参与条件判断 | 关闭态仍产出 chunk，产物探针失败 |

R2 是最容易被忽略的一条。派生代码如果写成 `#[cfg(feature = "vault")] fn mount() {...}`，即便它位于生成文件里，也违反了"特性 cfg 只允许出现在 `cmd/mod.rs` 与 `<name>_plugin.rs`"的约束——`cfg` 的**位置**是契约，与文件是否生成无关。

## 3 逐点判定

| 装配点 | 派生方式 | 可归零 | 代价与风险 |
|---|---|---|---|
| `vite-env.d.ts` | 由清单生成 `declare` 块 | **可** | 生成物入库，需漂移断言 |
| `registry.ts` | 由清单生成 mount 表，条目内保留 `if (__<ENV>__)` 字面量开关 | **可** | 见 §5，形态唯一 |
| `build.rs` | 遍历清单，`plugin(name, prefix)` 参数化 | **可** | 顺带修复"单插件写死"（前置分析 E5） |
| `plugins.rs` | 遍历 `mounts()` 表 | **可** | 需 trait/表结构（§4） |
| `lib.rs` | 生成 `feature_mounts.rs` 后，`lib.rs` 只留 1 行静态 `mod feature_mounts;` | **可** | 该行一次性引入，不随特性增长 |
| `capabilities/default.json` | 无法从清单派生（tauri 读静态文件） | **不可** | 降级为 B：`capabilities/<id>.json`，同时解决窗口作用域问题（§6） |

结论：M 由 6 降到 **0**（capabilities 一项从 core 装配点转入 B），D 恒为 2 项。

## 4 核心手法：从"core 调名"到"core 遍历"

### 4.1 现状的四条"调名边"

| 边 | 位置 | 形态 |
|---|---|---|
| 插件注册 | `src-tauri/src/plugins.rs` | `.plugin(crate::vault_plugin::init())` |
| 退出清理 | `src-tauri/src/lifecycle.rs` | `crate::cmd::vault_cleanup_on_exit(app_handle)` |
| 模块与重导出 | `src-tauri/src/cmd/mod.rs` | `#[cfg(feature = "vault")] mod vault;` + `pub use` + `#[cfg(not(...))]` 空桩 |
| 配置副作用 | `src-tauri/src/cmd/config.rs` | 直接调用 `apply_vault_side_effects` |

四条边的共同点是：**core 知道特性叫什么名字**。这就是 `cmd/mod.rs` 里那 3 行 `cfg` 与空桩函数存在的全部理由——core 要调用一个名字固定的函数，关闭态下这个名字必须仍然存在，于是只能造一个空桩。

### 4.2 遍历化之后空桩退役

把四条边都改成"遍历一个由特性提供的表"：

- 关闭态的表是空切片，core 遍历 0 次，行为等价于"这个特性不存在"；
- 开启态的表含一条，core 遍历 1 次；
- **core 代码里不再出现任何特性名字**，因此不需要 `cfg`，也不需要空桩。

这不是风格偏好，而是逻辑必然：**空桩是"core 调名"的伴生品**。任何保留 core 调名的"零成本"方案，都必然保留空桩，也就必然保留 `cfg` 配额压力。

### 4.3 由此带来的两个连带收益

| 原本独立的问题 | 现状 | 遍历化后 |
|---|---|---|
| E4 `cfg` 配额（`VAULT_CFG_LIMIT = 6`） | 5 行（插件文件 2 + `cmd/mod.rs` 3） | 降到 2 行，全部在插件文件内，配额不再有压力 |
| P7 足迹冻结（allowlist 7 个 core 文件） | vault 占用 7 个历史文件 | 目标降为 **0**：core 文件不出现特性字面量 |

这两个问题此前被当作两条独立的技术债，遍历化让它们同时消失。这是判定"零成本挂载"**合理而非仅仅省事**的核心论据：它把"配额管理"和"足迹豁免"这两类维护成本整体消除，而不是把成本挪到别处。

### 4.4 契约形状的判定

需要的不是"每特性写一套装配代码"，而是**一个统一的挂载表**，其条目在两种模式下都存在、方法体由特性自己实现：

- 关闭态实现返回空切片 / 空表；
- 开启态实现返回真实内容；
- 表本身**零 cfg**（R2），`cfg` 只在特性本体文件内。

判定：**合理**。它与前端 `FeatureModule`（一个特性 = 一份声明，聚合器是唯一构造点）在语义上对称，形成"前端一个模块、后端一个挂载表"的对应关系，符合 `CODE-SPLIT-PRINCIPLE` 的"一个文件只对应一个变化原因"。

## 5 前端三角：三个目标不能靠同一手法满足

### 5.1 三个目标

| 目标 | 含义 |
|---|---|
| **T1 零手写** | 新增特性不改 `registry.ts` / `vite-env.d.ts` |
| **T2 真删除** | 关闭态产物中不含该特性的 chunk |
| **T3 生成物入库** | 可 code review、可断言、IDE 可导航 |

### 5.2 三种候选形态的判定

| 形态 | T1 | T2 | T3 | 判定 |
|---|---|---|---|---|
| 现状：手写 `if (__VAULT_ENABLED__) { await import(...) }` | 否 | **是** | 是 | T1 不满足，这就是 M 的来源 |
| `import.meta.glob("./*/module.ts")` 枚举 | **是** | **否** | 是 | glob 会为所有匹配产出 chunk，关闭态 chunk 仍在产物里，违反产物探针 |
| 生成器按当前 env 决定"是否写入 import 语句" | **是** | **是** | 否 | 不同特性组合产出不同文件内容，无法入库；每次构建都需重跑生成 |

三者各缺一个角，没有任何一种能单独满足 T1+T2+T3。

### 5.3 唯一可行的折中

**生成物内容只依赖清单，不依赖 env**：每个条目仍写成

```
if (__<ENV>__) { ... await import("./<id>/module") ... }
```

- 文件内容对给定清单是确定的 → **T3 成立**（可入库、可 review、可漂移断言）；
- 构建时 `define` 把 `__<ENV>__` 替换成字面量 `false` → `if (false)` → Rollup 折叠掉动态 import → **T2 成立**；
- 手写成本为 0 → **T1 成立**。

判定：**合理且是唯一形态**。其成立的关键是"开关必须是字面量"——`define` 的替换结果必须是 `true` / `false` 这种常量，Rollup 才能做死代码消除。任何把开关做成运行期查表（`flags[id]`、`Record<string, boolean>`）的写法都会退化成不可折叠，T2 随即失效（见 §8 反例）。

### 5.4 与既有生成物范式的关系

仓库已有"生成 + 入库 + 断言"的先例：`npm run contract:gen` 产出 `src/types/protocol.contract.ts`，项目规则要求提交该文件、禁止手改。前端挂载表复用同一范式，属于既有工程习惯的延伸，不引入新范式。

判定：**合理**。反过来说，如果拒绝生成物入库、改用"构建时临时生成"，就会失去"干净检出即可跑断言"的能力，与 `contract:gen` 的既定做法相冲突。

## 6 不可归零项

| 项 | 不可归零的原因 | 处置 |
|---|---|---|
| `Cargo.toml` 的 `[features]` 与 `default` | cargo 要求特性静态声明；`dep:` 门控语法只能写在这里，无任何派生机制 | 计入 **D**，固定 2 行 |
| `tauri.conf.json` 的 `windows` 数组 | tauri 在编译期读取该静态配置；它不是代码，无法参与派生；且 `main` 窗口必须静态存在 | 计入 **D/B**；独立窗口形态只能走"运行期创建"（见前置分析 §3 推论） |
| `capabilities` 的 `windows` 列表 | tauri 读取静态 capability 文件；`build.rs` 若去写该目录等于自修改源码树，构建顺序脆弱 | 降级为 **B**：`capabilities/<id>.json` |
| conf 分组播种（`app` / `orb` / `mascot` 的 applier） | A8 要求"已注册分组集合 == `*_conf` 模块集合"，播种点在 `cmd/mod.rs` 之外 | 属**特性化前置**，不是挂载成本；须先把这三组变成特性，才谈得上可选 |

### 6.1 capabilities 按特性拆文件的两重收益

把 `"<id>:default"` 从 `capabilities/default.json` 挪到 `capabilities/<id>.json`，同时解决两件事：

1. **成本归属**：从 core 装配点转为 B，M 计数中消失；
2. **窗口作用域**：前置分析 G-2 指出"capability 与窗口/特性之间没有断言守护"。`default.json` 的 `windows` 是 `["main","orb"]`，若把独立特性窗口并进去，会连带获得 `global-shortcut` / `autostart` / `always-on-top` 等与之无关的权限。按特性拆文件后，每个特性文件可以只声明自己的 `windows` 列表，作用域由文件名与内容共同界定。

判定：**合理**。代价是"新增一个文件"，但该文件属于特性本体，不构成挂载成本。

## 7 门禁改造：零成本的代价

### 7.1 现有断言正是成本的固化形式

`coreBoundary.test.ts` 的三条断言与 `assembly_contract.rs` 的 A1-A8，绝大部分是**存在性断言**：某文件里是否出现了某个字符串。

| 现有断言 | 实际证明的东西 |
|---|---|
| `lib.rs` 含 `mod vault_plugin` | 有人手写过了 |
| `plugins.rs` 含 `vault_plugin::init()` | 有人手写过了 |
| `capabilities` 含 `vault:default` | 有人手写过了 |
| `registry.ts` 含 `__VAULT_ENABLED__` | 有人手写过了 |

这些断言**只能证明"装配动作发生过"**，不能证明"特性真的被排除了"。它们与"每特性手改 8 处"互为因果：因为要求逐处手写，所以逐处断言；因为逐处断言，所以不能改成派生。

### 7.2 归零后必须替换的三类断言

| 类别 | 内容 | 替代的旧断言 |
|---|---|---|
| **派生一致性（漂移）** | 重新生成一次，与入库文件逐字节比较 | 取代 `vite-env.d.ts` / `registry.ts` 的存在性断言 |
| **反向足迹** | core 文件不得出现任何特性 id 字面量，allowlist 从 7 降为 0 | 取代 `FEATURE_FOOTPRINT_ALLOWLIST` 的豁免机制 |
| **行为断言** | `cargo tree --no-default-features -i <crate>` 依赖断开；关闭态 chunk 数 = 0 | 补上前置分析 G-1 / G-6 两处缺口 |

### 7.3 判定：净收益

存在性断言与行为断言的证明力不在同一层级：前者证明"源码里写了什么"，后者证明"产物里真的没有什么"。零成本挂载把断言从前者整体换成后者，**门禁强度上升而不是下降**——前提是漂移断言必须落地。若只删旧断言、不加新断言，门禁会退化为空转，这比现状更差。

## 8 会破坏现有契约的"零成本"写法（反例）

| 反例 | 破坏点 |
|---|---|
| `import.meta.glob("./*/module.ts")` 枚举前端模块 | 关闭态仍产出 chunk，产物探针失败（T2） |
| 把 `cfg` 写进派生出的装配代码 | `cfg` 出现在 A2 白名单外（R2）；"位置"是契约，与是否生成无关 |
| 开关做成 `Record<string, boolean>` / `flags[id]` 运行期查表 | 失去字面量常量折叠，动态 import 无法被消除（T2）；且违反类型安全规范 |
| 在 `build.rs` 里写 `src-tauri/capabilities/*.json` | 自修改源码树，构建顺序脆弱，且让"生成物"脱离 review |
| 用 `OUT_DIR` + `include!` 生成 `mod` 块 | A2 的源码扫描覆盖不到，`cfg` 逃逸门禁；IDE 不可导航 |
| 用 `linkme` / `inventory` 做链接期自注册 | 新增依赖；且 Rust 侧的"是否编译"是静态决策，链接期注册改变不了这一点 |
| 让 core 保留调名、只把调用点包成 `if feature_enabled()` | 空桩仍在、`cfg` 配额仍紧、足迹仍非零——只换了调用形式，没消除成本 |

最后一条最值得注意：它是"看起来零成本、实际成本不变"的典型。判据是 §4.2 那句话——**只要 core 还在调名，成本就没有消失**。

## 9 判定结论

| 命题 | 判定 |
|---|---|
| "零成本挂载"作为目标是可达的 | **成立**，形态为 M=0、D 恒 2、B 不设限 |
| 前提一：core 只遍历、不调名 | **必要**，否则空桩与 cfg 配额无法退役 |
| 前提二：生成物入库 + 漂移断言 | **必要**，否则失去可断言性与 IDE 导航 |
| 前提三：前端开关保持字面量 | **必要**，否则真删除失效 |
| "零声明成本" | **不成立**，cargo 与清单语义要求静态声明 |
| "零生成物" | **不成立**，模块树与 `vite-env.d.ts` 无法在无生成层的情况下派生 |
| 现有三道门禁 | **需替换而非叠加**：存在性断言退役，派生 / 足迹 / 行为断言上位 |
| 对 vault 的意义 | 把已完成的 L1 从"一个特例"提升为"一类机制"，7 个足迹文件与 5 行 cfg 的维护成本同时归零 |

最终判定：**设计思路合理，但必须按"成本口径拆分 + 遍历化 + 生成物入库 + 门禁换挡"四件事成套成立**。单独做其中任何一件，都会得到"成本被搬到别处"或"门禁变松"的结果，而不是真正的零成本。
