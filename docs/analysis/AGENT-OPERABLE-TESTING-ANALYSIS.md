## 1 口径

### 1.1 为什么「agent 可操控测试」不能作为一个词判定

它同时指向四个面。四者的驱动方式、覆盖范围、对内部支持的要求完全不同，混在一起计只能得出「做不了」或「全都能做」两种伪结论：

| 面 | 覆盖什么 | 需要什么内部支持 | 当前是否成立 |
|---|---|---|---|
| **语义面** | 命令语义、状态机、事务、加解密、同步、错误映射 | 进程内可构造的 App + 可枚举的命令 + 可判定的静默信号 | **否**（无 `tauri` test feature） |
| **装配面** | 插件挂载、feature 开关、ACL、产物隔离 | 可注入的依赖 + 产物探针 | **部分**（探针已有，注入无） |
| **渲染面** | 布局、DPI、交互反馈、动画 | 进程外驱动 + selector 约定 + 截图对比 | **否**（无驱动、无截图） |
| **观测面** | 判定「做对了没有」 | 事件外流 + 状态快照 + 日志 + 取证 | **部分**（日志有，外流无） |

关键判定：**语义面与渲染面不是同一套基础设施的两档强度，而是两套不同的驱动方式**。语义面要的是「App 作为对象」，渲染面要的是「App 作为像素」。把渲染面当作语义面用，会得到「点得动但断言不了」的测试；把语义面当作渲染面用，会得到「断言得准但看不见用户所见」的测试。

### 1.2 三个成本项

沿用可选特性分析的分项口径（`docs/analysis/FEATURE-ZERO-COST-MOUNT-ANALYSIS.md` §1.2），把「为 agent 提供支持」的改动分成三项：

| 记号 | 定义 | 是否可归零 |
|---|---|---|
| **D 声明成本** | 让系统知道「存在这个测试面」：feature 开关、DTO 契约、事件名 | 不可归零，但可固定（每项 1~2 行） |
| **M 装配成本** | 让测试面在运行期生效：依赖注入、命令注册、挂载 | **调用型部分可归零**：`feature_mounts.rs` 已证明「core 只遍历、不调名」可行 |
| **B 本体成本** | harness 自身的代码：用例、夹具、断言、取证 | 不设上限，计入测试自身 |

判定：**「给 agent 提供支持」不等于「在 core 里到处加 debug 分支」**。M 的调用型部分在本仓库已有现成范式可复用（`feature_mounts.rs` 的 `MOUNTS` 表 + `plugins.rs` / `lifecycle.rs` / `setup.rs` 三处遍历），因此这部分成本已被前序工作预支。

### 1.3 七项支持的定义

| 支持项 | 一句话定义 | 缺了会怎样 |
|---|---|---|
| **可构造** | 能在进程内起一个功能完整的 App，且不依赖真实用户目录与真实桌面会话 | agent 只能点真机，无法并行、无法重复、无法隔离 |
| **可枚举** | 能拿到命令清单与事件清单，而不是靠读源码猜 | agent 只能覆盖它恰好知道的命令，新增命令永远测不到 |
| **可注入** | 路径、时间、随机、网络、系统能力（生物识别 / 快捷键 / 托盘）都可替换 | 同一用例两次运行结论不同，断言写不出来 |
| **可判定** | 能回答「当前有没有进行中的工作」，而不是靠等 | 等待靠 sleep，失败率与用例时长正相关 |
| **可观测** | 事件能外流、状态能快照、时序有身份 | 只能断言终态，无法断言顺序与因果 |
| **可取证** | 失败时自动落盘日志、事件 trace、快照、截图 | agent 无法自我修正，只会重试 |
| **可隔离** | 测试面在 release 产物中零残留，且有探针证明 | 安全事件；vault 明文面使其后果放大 |

### 1.4 为什么「加一个 AI 入口」不是答案

本仓库的 agent 工具链（`src-tauri/src/tool_setup.rs`）是**产品功能**：它服务于用户，走审批网关、权限授予、审计链路。测试可操控性服务于开发者，需要**绕过**审批与 UI。两者方向相反：

- 产品入口必须过 `ToolGateway` / `ToolPipeline` / `ApprovalPrompter`，因此它无法用来驱动「审批弹窗本身」的测试；
- 测试面必须能直接进入命令层，因此它天然是后门，必须与 release 严格隔离。

把两者混谈，会得出「做一个 chat 命令让 agent 自己点」的伪结论——那条路径既测不了审批（它就是审批的执行者），也测不了启动流程（它运行在启动完成之后）。

### 1.5 两个口径：开发期自测，还是向 agent 开放操控

「agent 可操控测试」有两种读法。本文只取第一种，这个选择必须在文首口径里说死，否则后文所有「成本」都会被按错的口径计价：

| 口径 | 形态 | 消费者 | 产物归属 | 本文判定 |
|---|---|---|---|---|
| **A 开发期自测** | agent 在开发环境跑 harness 用例、读失败产物自我修正；操控面由 `dev-hooks` feature 承载 | 开发者与 agent（开发期） | 不进 release，且必须被探针证明不存在 | **本文口径** |
| **B 向 agent 开放操控** | 运行期把命令与事件开放给 agent，agent 驱动真实 App | 用户场景中的 agent | 进入 release，成为产品能力 | **不取**（§1.4、§5.3） |

判定 B 不成立的三条理由都是方向性冲突，不是「以后再说」：

1. **方向相反**：产品入口必须过 `ToolGateway` / `ApprovalPrompter`，测试面必须绕过它；同一个面无法同时服务两种方向（§1.4）。
2. **信任边界**：release 中的操控面即后门，ACL 一旦授权，窗口内任意前端代码可调用（§5.3）；vault 明文面使后果不可撤回。
3. **B 会取消判据**：口径 B 的操控面本就在 release 里，「零残留」无对象可断言，于是「可隔离」从「可验证」退化为「承诺」——而承诺恰好是本文拒绝的证明形态。

一处必须澄清的相邻误读：**口径 A 不等于 `debug_assertions` 口径。**debug 构建同样可能被分发（内测包、崩溃复现包），因此「测试面只存在于 debug 构建」既不能保证安全，也不能证明 release 干净。这正是 §8 形状 5 把隔离单位定为 feature 而非 `debug_assertions` 的原因：feature 让 release 构建也能生成、也能被探针断言。

由此，口径的一句话是：**操控面是开发期资产，agent 是它的消费者而不是它的产品化承载者；它成立的证据不是「debug 里有」，而是「release 里被证明没有」。**

## 2 事实基线

> 本节记录某一时刻的结构证据。**不跟踪修复进度**；代码演进后以当时代码为准。

### 2.1 可构造性

| 事实 | 证据 | 数值 |
|---|---|---|
| 构造入口唯一且无参数 | `src-tauri/src/lib.rs` 的 `run()` 固定链 `plugins::attach` → `.setup(setup::init)` → `.invoke_handler(ipc::handler())` → `build(generate_context!)` | **1 条** |
| `setup::init` 签名 | `pub fn init(app: &mut App) -> Result<(), Box<dyn Error>>` | **无依赖参数** |
| 路径解析点分散 | `AppDirs::resolve()` 生产调用点：`setup.rs` / `plugins.rs` / `main.rs` / `tool_setup.rs` / `cmd/vault/mod.rs` / `cmd/vault/recovery.rs` / `cmd/vault/lifecycle.rs` / `cmd/vault/entries.rs` / `cmd/mascot_asset.rs` / `cmd/attachment.rs` | **10 处** |
| 库层注入缝已存在 | `AppDirs::with_bases(data, local)`，注释写明「测试注入」 | 1 处 |
| `tauri` 未开 test feature | workspace 依赖 `features = ["tray-icon", "macos-private-api", "protocol-asset"]` | **0 处 test** |
| dev-dependencies 无测试装配件 | 仅 `minidump`、`tempfile` | **2 项** |
| managed state 数量 | `.manage()` 调用分布：`setup.rs` 5（`DbState` / `AttachmentStore` / `TurnTasks` / `SessionStates` / `ClockRuntime`）、`tool_setup.rs` 5（读回执 / 提问挂起 / 审批挂起 / 执行端口 / 工具注册表）、`cmd/vault/mod.rs` 7（`SecurityDbState` / `RevealGuard` / `ClipboardGuard` / `SshAgentState` / `VaultRepo` / `SyncEngine` / 屏幕锁监视） | **17 处 / 3 文件** |

判定：**可注入性在库层成立，在装配层不成立。**`with_bases` 是一条真实的缝，但生产路径上没有任何地方用它——10 个调用点全部走 `resolve()`。这与 M7.10 收口的「路径与仓库所有权分散」是同型缺陷：测试只是它的第一个受害者，真正的成本是任何一次目录语义变更都要改 10 处。

补充事实：`plugins.rs` 的 `log_plugin()` 也在 Tauri 初始化之前调用 `resolve()`（注释明确「可在 Tauri 初始化之前调用」）。这意味着**日志落点与数据落点共享同一个分散解析**，harness 若只注入数据根而不注入 local 根，日志仍会写到真实用户目录。

### 2.2 可枚举性

| 事实 | 证据 | 数值 |
|---|---|---|
| 宿主命令 | `src-tauri/src/ipc.rs` 的 `generate_handler![...]` | **85 条** |
| vault 命令 | `src-tauri/src/vault_plugin.rs` 的 `generate_handler![...]`（不含 `vault_setup` / `vault_cleanup_on_exit` 两个生命周期钩子） | **72 条** |
| 命令总数 | 上两者之和 | **157 条** |
| 事件名常量 | `src-tauri/src/protocol/events.rs` 的 `event_name` 模块 | **20 个** |
| 运行期可枚举 | `generate_handler!` 是宏展开，产物中无命令清单表 | **不可** |
| 文本解析实现 | `src-tauri/crates/assistant-vault/tests/command_gate.rs`、`src-tauri/tests/assembly_contract.rs`、`src/test-utils/rustCommands.ts` | **3 处** |

判定：**枚举能力已经存在，但以「三份独立解析同一真源」的形式存在。**`command_gate.rs` 解析 `#[command]` 与函数体做前置条件门禁；`assembly_contract.rs` 解析 `generate_handler![` 块做注册分区与 ACL 对账；`rustCommands.ts` 在测试期解析同一批块，供前端 `commandNames.test.ts` 做 invoke 字面量对账。三者各自实现了一遍「剥注释 + 找块 + 切逗号」，任何一处的解析规则落后于源码形态，都会静默漏检。

这条判定的含义：**可枚举性的缺口不是手段，是单一来源。**新增一条命令时，agent 需要的是「一张能读到的表」，而不是第四份解析器。

### 2.3 可注入性

| 依赖 | 现状 | 形态 |
|---|---|---|
| 时间 | `src-tauri/src/adapters/system_clock.rs` 实现 `Clock` trait（`now` / `now_millis`）；`src-tauri/src/clock.rs` 的 `ClockRuntime` 方法签名一律接收 `now_ms: Millis` 参数 | **已有缝**（纯函数 + 时间参数化），仅边界处 `now_ms()` 读系统时间 |
| 时间（测试替身） | `src-tauri/tests/approval_timing.rs` 用 `SlowApproval` 实现 `ApprovalPrompter` 做固定时长替身 | **已有先例**（trait 对象缝） |
| 路径 | 库层 `with_bases` 有缝；装配层 10 处 `resolve()` 无 | **缝存在但未接线** |
| 随机 | 未见注入点；ID / 盐 / nonce 由各领域自行生成 | **无** |
| 网络 | provider 基址写在配置与领域内；无 base-url 覆盖入口 | **无** |
| 系统能力 | 生物识别走 `assistant_vault::biometric`（Windows 下 `warm_up_keyring_backend`）；全局快捷键、托盘在 `setup.rs` 直接注册 | **无 stub** |

判定：**「可注入」不是从零开始**。本仓库已经在两个领域证明了 trait 缝可行（`Clock`、`ApprovalPrompter`），因此剩下的不是「要不要引入依赖注入」的架构争论，而是「把已有缝接到装配层」的接线问题。差别在于：`Clock` 缝在**领域层**，装配层是否使用它取决于调用点；`AppDirs` 缝在**库层**，装配层 10 个调用点各自绕过它。

### 2.4 可判定性

| 事实 | 证据 | 含义 |
|---|---|---|
| 会话状态容器已存在 | `setup.rs` 中 `handle.manage(Arc::new(SessionStates::new()))` | 空闲与否可由它推导 |
| 轮次任务容器已存在 | `setup.rs` 中 `handle.manage(Arc::new(TurnTasks::new()))` | 进行中的 turn 可数 |
| 两者均无对外投影 | 无对应命令、无对应事件 | agent 拿不到 |
| 同步在途无计数 | `SyncEngine` 无 in-flight 暴露 | 同步完成不可判定 |
| 审批挂起可枚举 | `PendingApprovalRegistry` / `PendingQuestionRegistry`（`tool_setup.rs` 装配） | 挂起数可推导，但未投影 |

判定：**「静默」这一信号在仓库里已经是可计算的，只是没被投出去。**`SessionStates` + `TurnTasks` + `PendingApprovalRegistry` 三者相加足以定义「无进行中工作」。这意味着可判定性是七项中成本最低的一项——它不需要新机制，只需要一个聚合读入口。

反过来说：**在没有这个入口的情况下，agent 只能等。**而「等多久」在任何有构建负载的机器上都是不可判定的（§5.2）。

### 2.5 可观测性

| 事实 | 证据 | 含义 |
|---|---|---|
| 广播出口唯一 | `protocol/events.rs` 的 `emit_broadcast(app, event, payload)` | 单点，适合加旁路 |
| 定向出口唯一 | 同文件的 `emit_orb_only` | 单点 |
| 出口只到 webview | 两者都走 `app.emit` / `win.emit` | 进程外无消费者 |
| 载荷无序号 | 无 `seq` / `correlation_id` 字段 | 无法断言顺序与因果 |
| 事件常量 20 个 | `event_name` 模块 | 覆盖面已够，缺的是外流 |

判定：**可观测性的缺口是一层抽象，不是二十处改动。**因为广播与定向各只有一个出口函数，加「旁路 sink」的改动面是 2 个函数，而不是 20 个调用点。这与 §2.2 的「三份解析」形成对照：**出口收敛的地方，改造便宜；解析分散的地方，改造昂贵。**

### 2.6 可取证性

| 事实 | 证据 | 含义 |
|---|---|---|
| 文件日志已接 | `plugins.rs` 的 `log_plugin()`，落 `local` 根，按 `debug_assertions` 分档，`KeepSome(3)` + 10 MB 轮转 | 可读，但无「按 run 归档」 |
| 崩溃转储已接 | `main.rs` 在启动前 `AppDirs::resolve()` 后装 `assistant-crash` | 有，但与测试失败无关 |
| 截图能力 | `docs/store/I35-screenshot-qa-spec.md` 为 **Draft rev4，未实施**；`xcap` 不在依赖中 | **无** |
| 图像处理依赖 | `image = { features = ["png","jpeg","bmp","tiff"] }` 已在 workspace 依赖 | 已有（供附件/图标用） |

判定：**取证链的三段里有两段已存在**（日志、崩溃转储），缺的是「按测试 run 归档 + 事件 trace + 状态快照」的组装。截图是独立一段，且它属于渲染面基础设施（§6），不应与语义面取证捆绑。

### 2.7 可隔离性

| 事实 | 证据 | 数值 |
|---|---|---|
| `debug_assertions` 使用点 | `main.rs`（`windows_subsystem`）、`plugins.rs`（日志档位）、`window.rs`（1 处 `#[cfg(not(debug_assertions))]`） | **3 处**，无一处是测试面 |
| 现有 dev-only 命令 | 无 | **0 条** |
| 装配契约探针 | `src-tauri/tests/assembly_contract.rs` 的 A1–A8 + B1–B9 | **17 条** |
| 命令门禁 | `command_gate.rs` 的 `STATE_ACCESS` 4 项、`PRECONDITIONS` 3 项 | **2 组** |
| 产物探针模式 | A1（注册文件无 cfg）、A2（特性 cfg 只在边界文件）、B1（挂载表无 cfg） | 已有范式 |

判定：**「测试面零残留」这条要求，本仓库已经有能力用机器证明，而不是靠承诺。**A2 的判据（特性 `cfg` 只允许出现在 `cmd/mod.rs` 与 `<name>_plugin.rs`）正好是新增 `dev-hooks` 时最需要的约束形态；B1（挂载表 0 处 cfg）正好约束新增的测试挂载表。

## 3 逐点判定

| 支持项 | 目标形态 | 可否 | 代价与风险 |
|---|---|---|---|
| **可构造** | 进程内 harness：`tauri::test::mock_builder()` + 注入 deps 的 `init_with(deps)`，不依赖真实桌面会话与真实用户目录 | **可**，且是唯一地基 | 需改 `setup::init` 签名 1 处、收口 10 处 `resolve()`、开 `tauri` test feature 1 行；风险是 17 个 managed state 的构造副作用（托盘、全局快捷键、窗口、巡检线程、屏幕锁监视、工具注册表）在 mock 环境下需全部降级，否则 harness 一启动就 panic |
| **可枚举** | 单一命令表（157 命令 + 20 事件），`generate_handler!` 与三处解析器都从它派生或与之对账 | **可**，但需先定真源位置 | 表必须 cfg-free（否则违反 A2）；三份现有解析器不能简单删除——它们守的是不同维度（前置条件 / 注册分区 / 前端对账），应改为「读表断言」而非「各自解析源码」 |
| **可注入** | 路径 / 时间 / 随机 / 网络 / 系统能力五类可替换 | **部分可** | 时间与审批已有 trait 缝，接线成本低；路径需先解决 10 处分散（§4 R1）；随机与网络无现成缝，需新增；生物识别 stub 是硬需求（§6） |
| **可判定** | `debug_wait_idle` 或 `app-idle` 事件，口径为「无进行中 turn + 无挂起审批 + 无在途同步」 | **可**，成本最低 | 需新增 in-flight 计数（同步侧当前无暴露）；口径必须显式，否则「无事件 N 秒」会退化成 sleep |
| **可观测** | `EventSink` 旁路 + 载荷加 `seq` / `correlation_id` | **可** | 出口只有 2 个函数，改动面小；风险是 `seq` 进入 wire 会改 DTO 契约，需明确「仅测试面可见」还是「正式契约」——前者要求 cfg 隔离，后者要求 `contract:gen` |
| **可取证** | 失败时自动落 `local/logs/<run-id>/`：日志尾 + 事件 trace + 状态快照（+ 渲染面截图） | **可**，三段已有两段 | 快照必须过明文 egress 规则，不能含 vault 明文或密钥材料；截图依赖 §6 的渲染面基础设施，不应与语义面捆绑 |
| **可隔离** | `dev-hooks` feature + 产物探针证明 release 零残留 | **可**，且必须 | 判据来源 D11 / D14；复用 A2 / B1 范式；不可谈判（§5.3） |

结论（手写阶段）：**七项中 5 项可直接成立，2 项（可构造、可注入）受阻于同一个根因——装配层未参数化。**而这个根因与 M7.10 的「路径所有权分散」同型，修它同时消灭一个架构缺陷与一个测试阻塞，属正收益。

## 4 必要条件

以下五条必须同时满足，缺一条则「agent 代劳」退化为「更快的盲目点击」。

| 判据 | 含义 | 违反后果 |
|---|---|---|
| **R1 进程内可构造** | 能在无真实桌面会话、无真实用户目录的条件下起一个完整 App | 只能驱动真机：不能并行、不能隔离、CI 上无法运行 |
| **R2 状态可枚举且单一来源** | 命令与事件的清单来自一张可读的表，而非多处源码解析 | 新增命令永远测不到；三份解析器漂移后静默漏检 |
| **R3 存在可判定的静默信号** | 「无进行中工作」是一个可查询的状态，不是一段等待时间 | 等待退化为 `sleep`，失败率与用例时长正相关 |
| **R4 失败可自证** | 失败时自动产出可读的现场，无需人工复现 | agent 无法自我修正，只能重试；重试放大 flaky |
| **R5 隔离可验证** | release 产物零残留，且由探针证明而非承诺 | 安全事件；测试面即后门 |

**R1 是地基**：R2 到 R5 都以「能起一个 App」为前提。这也是 §0 命题 17 的依据。

**R2 与 R3 是「判定」的两半**：R2 回答「能做什么」，R3 回答「做完了没有」。只有前者，agent 能发出动作但不知道何时断言；只有后者，agent 知道何时结束但不知道有哪些动作。

**R4 与 R5 互为约束**：取证要求尽可能多的现场，隔离要求尽可能少的残留。两者的调和点是「取证产物落在测试运行目录、不进入产品数据目录」，而不是「取证靠减少隔离」。

## 5 反例推演

### 5.1 直接上进程外 driver

若跳过 R1 直接引入 `tauri-driver`（Windows 走 Edge WebDriver）：

- 它需要真实桌面会话。CI 上的无头环境不可用，本地并行多个实例会争抢焦点与全局快捷键（`setup.rs` 的 `register_global_shortcuts`）；
- 它能验证「点了有反应」，但无法验证「数据库里没有脏文件」「vault 锁状态已重置」「anchor 已清空」——这些恰恰是 vault 手工验收的主体；
- 它需要为每个控件建立稳定 selector，而本仓库当前**没有 `data-testid` 约定**，投入会先花在改组件上，而不是在测行为上。

判定：**进程外 driver 是渲染面的正确工具，但不能替代语义面。**先上它会得到一个「能点但断言不了」的测试套件，覆盖率数字好看而缺陷捕获率低。

### 5.2 用 `sleep` 代替静默信号

若不做 R3，改为「动作后等 3 秒」：

- 本 workspace 有 80+ 集成测试 target，每个静态链接整条依赖图（`Cargo.toml` 的 `[profile.dev]` 注释即为证），构建与 IO 负载波动大；
- `sleep` 过短在慢盘上失败，过长在本地浪费；两者的边界随机器漂移，因此失败会被误判为产品缺陷；
- 一旦出现 flaky，团队的处理方式是「重跑」，这会掩盖真实缺陷——比没有测试更糟。

判定：**`sleep` 不是静默信号的降级方案，是它的伪替代。**R3 的成本是聚合一个读入口，远低于长期 flaky 的代价。

### 5.3 测试命令不做隔离

若 `debug_seed` / `debug_snapshot` / `debug_reset` 无条件编译进 release：

- 它们能读写 vault 目录与安全库，等价于在产品中留一个明文入口；`I9-vault-plaintext-egress-spec.md`（已归档）的全部约束在此被绕过；
- 命令一旦进入 ACL 授权，该窗口内**任意前端代码**（含被注入的第三方脚本、开发者工具控制台）即可调用，权限边界从「命令名」退化为「窗口」；
- 「先上线再删」在实践中不成立——release 产物一旦分发即不可撤回。

判定：**R5 不可谈判。**且它可被机器守住：A2 已规定特性 `cfg` 只允许出现在边界文件，B1 已规定挂载表 0 处 cfg，新增 `dev-hooks` 沿用同构约束即可，不需要新判据。

### 5.4 把命令表写成 cfg 分支

若命令表按「开 / 关」两态各写一份：

- 违反 A2：特性 `cfg` 出现在边界文件之外，装配契约直接失败；
- 若为规避 A2 而把表放在 `<name>_plugin.rs` 内，则表与插件名绑定，宿主 85 条命令无处安放；
- 表的两种形态会让「表 ↔ `generate_handler!`」对账在两种构建下得出不同结论，门禁失去意义。

判定：**命令表必须 cfg-free，与 `feature_mounts.rs` 的 `MOUNTS` 同构。**这正是 `FEATURE-ZERO-COST-MOUNT-ANALYSIS.md` §4.2 已给出的硬约束：表要 cfg-free，就必须与开关无关，关闭态的差异只能落在特性边界文件内部。

## 6 不可自动化边界

以下四类**不是「以后能做」，而是「原则上不可自动化」或「需要专用基础设施」**。把它们计入「agent 代劳」的覆盖率，会得出虚高的数字。

| 类别 | 具体项 | 为什么不可自动化 | 处置 |
|---|---|---|---|
| **系统弹窗** | Windows Hello / 钥匙串授权 / UAC / 第三方 OAuth | 弹窗在应用信任边界之外，由操作系统或第三方渲染；自动化它等于绕过用户授权 | 必须 stub（`biometric` 注入假实现）；OAuth 用本地回调桩 |
| **观感** | 布局、DPI 缩放、动画帧、字体渲染、主题 | 判定标准是「人看着对不对」，无形式化判据 | 人工验收；最多做像素回归防退化 |
| **真实网络** | provider 流式响应、限流、断流、超时 | 结果不可重复，且涉及密钥与配额 | mock server 或录制回放；真实连通性另做冒烟 |
| **真实时序与系统事件** | 多窗口焦点、全屏切换、DPI 变更、睡眠唤醒、屏幕锁定 | 依赖真实桌面会话状态机 | 手动验收；或将事件注入为可编程源 |

判定：**「可代劳」的准确含义是「语义面与装配面可代劳」**，渲染面有限代劳（像素回归、selector 驱动），观感面与系统弹窗仍属人工。§0 命题 16 即此。

## 7 门禁与防回归

判据来源：`CODE-REVIEW-PRINCIPLE.md` D13（测试策略）、D14（构建与质量门禁）、D11（安全与隐私）。

| 门禁 | 内容 | 复用点 |
|---|---|---|
| **产物零残留** | release 产物中不得出现 `debug_` 前缀命令名与 `dev-hooks` 挂载条目 | A1 / A2 / B1 的既有范式 |
| **表 ↔ 注册对账** | 命令表条目与 `generate_handler!` 双向求差；表条目必须声明前置条件 | `assembly_contract.rs` 的 A4 / A6 / A7 |
| **前置条件覆盖** | 新增命令必须声明 `None` / `AnyState` / `Unlocked` 之一 | `command_gate.rs` 的 `PRECONDITIONS` |
| **harness 覆盖** | 每条命令至少被一个 harness 用例引用；未覆盖的进显式豁免清单 | 新增（当前无此约束） |
| **单一来源** | 三处文本解析不得各自维护规则；解析规则落后于源码形态时失败而非跳过 | `command_gate.rs` / `assembly_contract.rs` / `rustCommands.ts` |
| **取证可用性** | 失败必须产出 run 目录，且目录内含四类产物中的至少三类 | 新增 |

关键判定：**这些门禁不需要新判据体系，只需要把既有 17 条探针的形态复制到新对象上。**本仓库的装配契约已经证明「结构约束可以被机器守住」——这是「agent 可代劳」在本项目能成立的前提之一：agent 的产出（新增命令、新增挂载）会被门禁立刻检查，而不是靠人审。

## 8 需先定型的形状

六项形状一旦写错，第二个消费者（可能是人，也可能是另一个 harness）必然要求重构。以下为判定，非排期。

| # | 形状 | 判定 | 理由 |
|---|---|---|---|
| 1 | 构造入口的参数化形态 | **deps 结构体**（`init_with(deps)`），不用环境变量 | 环境变量在 10 个 `resolve()` 调用点不可靠：任何一处未读环境变量就回到真实目录；结构体是编译期可见的单点 |
| 2 | `AppDirs` 的持有形态 | **managed state** | 与 M7.10 的 `VaultRepo` 同型：唯一持有者 + 从 state 取用，消灭 10 处分散解析 |
| 3 | 命令表的真源位置 | **Rust 常量表**，前端与门禁从它派生 | 代码生成在 N=1 时负收益（`FEATURE-OPTIONAL-BINARY-ANALYSIS.md` 已判）；常量表可被 `include!` 与文本解析同时消费 |
| 4 | 静默信号的判定口径 | **状态推导**（turn + 审批 + 同步三计数），不用「无事件 N 秒」 | 后者在任何有负载的机器上不可判定，等价于 sleep（§5.2） |
| 5 | 测试面的隔离单位 | **feature（`dev-hooks`）**，不用 `debug_assertions` | 需要在 release 构建上验证「零残留」，而 debug 构建本身也可能被分发；feature 让两种构建都可生成、都可断言 |
| 6 | 取证产物落点 | **`local/logs/<run-id>/`** | 与既有日志、崩溃转储同根（`AppDirs::logs()`），不污染数据根，不进入漫游 |

补充判定（非形状，但需先定）：**`seq` / `correlation_id` 是否进入正式 wire 契约。**进入则需 `contract:gen` 与前端类型同步，且成为长期契约；不进入则只能在测试面可见，需要 cfg 隔离。两者的取舍应按「未来是否需要在生产中做事件溯源」决定，而不是按「测试方便」决定。

## 9 依赖次序的判定

以下为**依赖关系**，不是排期：

1. **R1（可构造）必须最先成立**，因为 R2 / R3 / R4 的验证都发生在 harness 内部，没有 harness 就无从验证。
2. **R2（可枚举）紧随其后**，因为 harness 的覆盖面由命令表决定；表不成立时，覆盖率的度量本身不成立。
3. **R3（静默信号）与 R2 并行推进**，两者无依赖，但都必须在用例规模化之前完成，否则早期用例会固化 `sleep` 习惯。
4. **R4（取证）在用例规模化之后立即需要**，因为 flaky 从规模化开始出现；过早建设则产物格式未定型。
5. **R5（隔离）必须与 R1 同时设计**，因为隔离是构造入口的属性（feature 开关决定挂载表是否包含测试项），事后补会要求重构挂载表。
6. **渲染面（进程外 driver + 截图）最后**，它依赖 selector 约定，而 selector 约定的成本主要落在组件改造上，与语义面无关。

一句话：**R1 与 R5 是一对，必须同时定型；R2 与 R3 是一对，共同构成「可判定」；R4 是规模化后的必然需求；渲染面独立且收益最窄。**
