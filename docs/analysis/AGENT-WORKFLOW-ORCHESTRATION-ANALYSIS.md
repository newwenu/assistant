## 0 结论速览

| # | 命题 | 判定 | 依据 |
|---|---|---|---|
| 1 | 「可编排 Agent」= 把 ComfyUI 的图编排照搬到现有 agent turn 上 | **不成立** | turn 内部的 12 个节点是内核实现细节（I55 §3.1），不是用户语义；把它暴露成可连线图，等于让内核结构成为 wire 契约（§1.1、§4.3） |
| 2 | 本项目已经有一张「图」 | **部分成立** | 只有一张**固定图**（12 节点 + 单条迭代回边），不可编辑；节点状态尚未上 wire（P15 未立项，§2 N1–N5） |
| 3 | 编排的最小可用单元是 turn | **成立** | turn 是当前唯一同时具备生命周期、取消、预算、观测、落库五件事的单元（§2 N2/N7/N9/N15） |
| 4 | 编排层可以直接复用 `TurnTasks` 做并发 | **不成立** | 其键是 `conversation_id`，语义为「单会话单 turn 互斥」；并行需要 run 级键与 run 级取消树，而 I55 §11.4 第 4 条已明示「键策略不动、不在观测面预留」（§2 N7、§4.6） |
| 5 | 编排层可以只在前端做 | **不成立（作为唯一方案）** | 前端无持久化、无调度权限、无审批资格；但画布本身只能是前端形态（§5） |
| 6 | 观测面已为编排预留了接入边界 | **成立** | I55 O10 + §11：独立控制端口、sink 恒只读、经既有命令入口发起 turn、编排失败不回灌（§2 N18） |
| 7 | 做编排必须改 I55 | **不成立** | I55 §11.5 明确「观测面一行不用改」（§4.5） |
| 8 | ComfyUI 的输出缓存可以直接照搬 | **不成立** | ComfyUI 的缓存以「节点是纯函数」为前提；agent 节点含模型采样（非确定）、工具副作用（不可重放）、人工审批（外部介入）（§3 R4、§4.2） |
| 9 | 拓扑排序可以直接照搬 | **部分成立** | 排序与就绪判定可用；但 ComfyUI 的无环假设 + `add_external_block` 只解决「等外部值」，不解决「人在环」与「重试环」（§4.3） |
| 10 | agent 图不需要环 | **不成立** | 重试、循环、条件回退都是环；本项目 turn 内部已有回边，图级环必须显式选择承载方式（§4.4、§7 D2） |
| 11 | 节点边界可以新造 | **不成立** | 只有三个既有语义单元可作节点：turn / 工具调用（Pipeline）/ 会话（conversation）；把「模型调用」「中间件」做成节点即把实现细节写进 wire（§4.3） |
| 12 | 编排状态可以不落库 | **不成立** | 图模板与 run 结果是业务事实；I55 的「V1 不落库」只针对观测事件，不覆盖编排（§4.7） |
| 13 | 审批可以因编排而简化 | **不成立** | 图级「一次批准整链」是**新增审批单元**，必须映射到既有 `ApprovalScope`；绕过 Gateway 即权限旁路（§4.8） |
| 14 | 预算可以只有一层 | **不成立** | turn 预算（迭代 / 工具 / 墙钟 + token）已存在，run 预算必须新增且可归因到节点，否则一次 run 的消耗无法分摊（§4.9） |
| 15 | 编排失败不得影响正在跑的 turn | **成立且必须** | O9 的扩展：编排层崩了，turn 仍应正常完成（§4.10） |
| 16 | 编排可以不等 P8.1 / P8.2 | **不成立** | 子代理与子会话是图里的天然节点类型；跳过 P8.1 会出现「图内子代理不受 `max_depth` 限制」（§4.11、§9） |
| 17 | 只串 turn 的编排也有独立价值 | **不成立** | 串 turn ≈ 多轮提示链，现有「会话 + 模式」可近似；不可替代的价值只在三件事：**并行分支**、**条件路由**、**人在环节点**（§4.12） |
| 18 | 技术上可行 | **成立** | 缺的是三件基础设施——run 级键与取消、run 落库、编排控制端口；不缺架构（§6） |

一句话：**本项目的「可编排 Agent」不是把 ComfyUI 的画布搬过来，而是新增一个位于内核之上的编排层：它把 turn 与工具调用当成节点，用一张可编辑的工作流图决定「何时发起哪个 turn、并行到哪、在哪个节点停下来等人」，而它读的是 I55 已经规格化的只读事件流、写的是自己的 run 台账、控制只经既有命令入口。可行，但不是增量特性——它要求先补齐 run 键、run 落库、控制端口三件基础设施，并且必须先通过 §4.12 的价值门槛，否则会得到一个「用画布串多轮提示」的空壳。**

## 1 边界

### 1.1 三层粒度：只有后两层可编排

「可编排」在本项目里同时指向三种完全不同的东西，混在一起谈必然得出错误结论：

| 层 | 单元 | 现状承载 | 可编排性 | 为什么 |
|---|---|---|---|---|
| **L1 turn 内** | 12 个节点（`admit` → `after-iteration`） | 内核固定图，单条迭代回边 | **不可编排，只可观测** | 节点是内核实现细节（中间件顺序、预算切分位置）；连线等于让实现结构成为用户契约，且与 I55 O4「模板静态」直接冲突 |
| **L2 turn 之间** | turn / 工具调用 / 子代理 | `TurnTasks` 单会话互斥（§2 N7） | **可编排** | 这是唯一有生命周期、取消、预算、落库的层级；ComfyUI 的「节点」在这里的对应物就是 turn |
| **L3 会话之上** | 会话 / Worker / Router | P8.2 / P8.3 候选（未立项） | **可编排** | 需要跨会话调度与持久运行；前置是 P8.2，且与 P9（continuity）相邻 |

**判定：编排层只能落在 L2 / L3。** 把 L1 变成可连线图是「把内核拆成积木」的诱惑，代价是每一次内核重构都变成 wire 破坏性变更；而 L1 的可视化需求已由 I55 覆盖（静态模板 + 7 值状态），两者目的不同，不能合并成一张图。

### 1.2 三个身份

编排语境里「谁说了算」混了三种权利，必须先拆开：

| 身份 | 能做什么 | 当前持有者 | 编排层能否取得 |
|---|---|---|---|
| **图作者** | 决定有哪些节点、边怎么连、参数是什么 | 目前无人持有（模板是编译期常量） | 能。但产物是**数据**（工作流模板），不是常量 |
| **调度者** | 决定此刻执行哪个节点、并行几个、何时停 | 目前是内核的固定循环 | 能，但必须**另设控制端口**，且不得改写观测 sink（I55 O10） |
| **执行者** | 真正跑 turn / 工具，产生事实 | 内核（`TurnRunner` + `RoundExecutor` + `ToolPipeline`） | **不能**。编排层只能请求，不能自己执行 |

越界的后果是具体的：

- 图作者越界成调度者 → 用户在画布上「拖一个节点」就等于改执行顺序，绕过审批与预算；
- 调度者越界成执行者 → 出现第二个 turn 发射者，违 I55 O1（每个 turn 恰好一个发射者）；
- 执行者越界成调度者 → 内核被迫认识「编排」概念，内核零 tauri 依赖与端口隔离（I36a）同时失效。

### 1.3 「可编排」不等于「更灵活的内核」

需要排除一个直觉：编排层**不新增执行语义**。它不并行节点（并行的是 turn / 工具调用）、不引入条件指令（条件由图的边表达）、不改迭代循环。I55 §1.3 已对观测面写过同一条，这里对编排层复述：**新增的是「谁决定下一步」这一层，不是「下一步怎么执行」**。

### 1.4 不属于本文的东西

- 画布渲染与交互（拖拽 / 缩放 / 小地图）：属前端 feature 的 UI 设计，只受 §5 的位置约束；
- DAG 编辑器的数据格式（节点参数表单、变量引用语法）：属工作流模板 schema，本文只给边界要求（§7 D5）；
- 模型选择 / 提示词模板：属既有 `TurnSpec` 与 `AgentMode` 的既有配置面，编排层只消费；
- 资源观测与存储配额：属 I54 / 存储监视器议题，与编排无因果关系。

| **N14** | 预算三维（迭代上限 / 工具调用上限 / turn 墙钟）；`token-budget` 钩子未配置时**不安装**、无默认值 | `src-tauri/crates/assistant-agent/src/kernel/limits.rs`、`agent/stop.rs` | turn 预算无法覆盖 run；且「未配置 ≠ 0」的显示口径必须沿用（I55 §4.4） |
| **N15** | 审批发生在工具流水线的 `Gateway` 阶段（`ApprovalScope` 求值）；`ask_user` 是一个**工具**，不是节点 | `src-tauri/crates/assistant-tools/src/runtime/pipeline.rs`、I38f | 人在环当前只有两种形态：调用级审批、工具级提问；**没有图级 HITL 形态** |
| **N16** | `spawn_agent` 规格：作为工具接入 Pipeline、`max_depth = 1` 硬上限、结果摘要回父、取消树向父会话传播（**暂缓接入**） | I38f | 图内子代理必须复用这条链路，不能新造「图内 spawn」 |
| **N17** | I55 §11 已定型编排器的四条接入约束：独立控制端口、经既有命令入口发起 turn、sink 恒只读、编排失败不回灌 | I55 §11.2 | 编排层的**边界已经写好了**，缺的是接口定义 |
| **N18** | I55 §11.4 第 4 条明确：`TurnTasks` 键策略不动，编排若需并行节点须由编排层自己解决 | I55 §11.4 | 与 N7 互相印证：并发键是编排层的**自担成本** |

**由事实得到的三个硬结论**：

1. **可观测性未就绪**：编排要「读事件决定下一步」，而节点级事件尚未上 wire（N1）。因此编排的阶段前置是 P15，而不是反过来。
2. **并发未就绪**：单会话单 turn 互斥（N7）与前端活跃会话过滤（N11）共同决定「并行编排当前无处落脚」。
3. **持久化未就绪**：无 run 台账（N10），而编排的图状态是业务事实（§4.7）。

| **R7** | Dify `api/core/workflow/` | 变量池 + `node_execution.py` / `node_runtime.py`；`nodes/agent_v2/` 把 **agent 做成工作流节点**（含 `session_store` / `tool_snapshot` / `output_adapter` / `validators`）；`nodes/human_input/` 把 **HITL 做成图节点**；`graph_topology.py` 提供上游判定（`is_upstream`）与保存期校验 | **这是与本项目最接近的形态**：agent 是节点、HITL 是节点 | **形态可移植**（agent 节点 + HITL 节点 + 保存期拓扑校验）；变量池**不采纳**（本项目节点间传递的是 turn 结果与工具结果，不是全局变量池） |
| **R8** | litegraph.js / ComfyUI_frontend | 前端画布：节点/端口/连线的数据模型与渲染 | 与「画布只是 UI」的定位一致 | 可选依赖；**不得**让画布模型成为 run 状态的来源 |

### 3.1 采纳 / 拒绝 / 自研

| 类别 | 条目 |
|---|---|
| **采纳（结构）** | 就绪集合 + 拓扑推进（R1/R3）；节点状态闭集（R2，已由 I55 定型）；`executionId` 键控与等待-恢复结构（R5）；checkpoint 式 run 台账（R6）；agent 作为节点 + HITL 作为节点 + 保存期拓扑校验（R7） |
| **拒绝** | 节点纯函数假设与输出缓存（R4）；八值 `ExecutionStatus`（R5，I55 已裁剪为 7 值）；全局变量池（R7）；superstep 语义（R6，与 turn 循环重叠）；`DynamicPrompt` 的运行时节点注入（R1，本项目图模板是静态数据，运行时不得注入节点） |

## 4 结构命题

### 4.1 命题一：编排的单元是 turn，不是节点

ComfyUI 的节点是「一次计算」，本项目的对应物**不是**内核的 12 个节点，而是**一次 turn**：它有独立的 `turn_id`、取消令牌、预算、落库结果与终态事件（N7 / N14 / N9）。工具调用是第二类节点（有 5 个阶段，N6），会话是第三类（L3）。

反过来把内核节点当编排单元，会遇到三个具体障碍：

1. `ladder` / `brake` / `after-tool` 是中间件与裁决，不是可独立执行的计算；把它们连成边没有语义。
2. 12 个节点共享一个 `TurnRunCtx`，拆开后端口无法切片（`TurnObserver` 只有一个，N3）。
3. I55 O4 要求模板静态；一旦允许连线，模板必须变成 wire 数据，首帧布局与向前兼容同时失效。

### 4.2 命题二：agent 节点不是纯函数，缓存不可照搬

ComfyUI 的 `cache_update` / `cache_link` 成立的前提是：节点输出只由输入决定（R4）。agent 节点三条全破：

| 破坏项 | 具体表现 | 后果 |
|---|---|---|
| **非确定性** | 模型采样、温度、工具返回的外部世界状态 | 同输入不同输出；按输入哈希缓存会给出「假命中」 |
| **副作用** | `write` / `edit` / `delete` / `shell` 改磁盘 | 跳过执行 ≠ 结果一致；重放会二次写入 |
| **人工介入** | 审批（Gateway）与 `ask_user` 的回答 | 输出取决于「谁在什么时候点了什么」，不属于输入 |

**因此可缓存的最小单位只能是「已完成且被显式标记为可重放」的节点结果**，且默认策略必须是「不缓存」。这条必须在 schema 层表达（例如 run 记录带 `replayable: bool`），而不是靠运行期判断。

### 4.3 命题三：拓扑排序可用，但无环假设不可用

ComfyUI 用 `add_external_block` / `release_external_block`（R1）解决「节点等待外部值」；n8n 用 `waitingExecution`（R5）解决同类问题。两者都假定**图本身无环**。

agent 图有天然的环：

- 重试环（节点失败后重跑）；
- 循环环（对一组输入逐项处理）；
- 条件回退环（结果不满足则回到前一个节点）。

本项目的特殊性在于：**turn 内部已经有一条回边**（迭代循环，N5）。如果图级再允许环，就会出现「图循环 × turn 循环」两层嵌套，状态机会从「12 × iteration」膨胀成「节点 × run × iteration」，任何一次重试都要重新定义「哪一层负责收敛」。

**判定：图级环必须显式选择承载方式**（§7 D2）：
- **方案 A（推荐）**：图保持 DAG，所有循环收敛到 turn 内部的迭代循环（即「一个循环节点 = 一次带循环的 turn」）；
- **方案 B**：允许图级环，但必须给出收敛判据（最大圈数、预算耗尽、显式终止边），且不得与 turn 回边叠加。

### 4.4 命题四：节点边界只能是既有语义单元

三个候选边界，全部来自既有代码：

| 边界 | 已有语义 | 可观测 | 可取消 | 可落库 |
|---|---|---|---|---|
| **turn** | `TurnSpec` + `TurnRunCtx` | 终态事件 | 按会话（N9） | assistant / tool 行 |
| **工具调用** | `ToolCall` + 5 阶段（N6） | `agent-tool-call` | 随 turn | 结果行 + `compact` |
| **会话** | `conversations` + `mode_id` | `session-state-changed` | 按会话 | 消息树 |

**不能**作为边界的：`model` 调用（内层重试属 provider 客户端，不是调度单元）、中间件（顺序是内核约定）、`persist-*`（副作用步骤，无独立语义）。

### 4.5 命题五：观测面是编排的输入，不是编排的通道

I55 已经把这条写成不变式（O10）与接入约束（§11.2），本文只需引用并强调两个推论：

1. **编排不需要改 I55**。它订阅 `agent-node-event`（只读），控制走自己的端口 + 既有命令入口（N17）。I55 §11.5 的结论对本文同样成立。
2. **编排不得把投影当输入**。I55 §2.3 已说明「投影为人服务，编排消费原始事件」；编排若读前端投影，就依赖了渲染层的裁剪结果，等于让 UI 决定调度。

### 4.6 命题六：并发键必须上移到 run

现状是 `conversation_id` 单 turn 互斥（N7）。编排要并行，会遇到四个连锁问题：

| 问题 | 现状 | 需要 |
|---|---|---|
| 任务键 | `conversation_id` | `run_id` + `node_id`（同一会话内多个并行节点） |
| 取消粒度 | 按会话取消（`cancel_agent`，N9） | 按 run / 按节点取消，且取消树幂等 |
| 事件路由 | 前端按活跃会话过滤（N11） | 按 `(runId, nodeId)` 键控投影，不依赖活跃会话 |
| 落库 | 无 run 表（N10） | run / node_run / edge 三张表 |

I55 §11.4 第 4 条已明确「`TurnTasks` 键策略不动，编排若要并行节点需新的键策略——那是编排层的事」。**这条把并发成本明确划给了编排层**，因此它必须是编排阶段的第一等交付，而不是后续优化。

### 4.7 命题七：编排必须自带持久化

I55 §7.1 定「V1 不落库」，理由是观测事件可丢、重载可由快照补齐。编排不适用：

| 对象 | 为什么必须落库 | 可否复用现有表 |
|---|---|---|
| **工作流模板** | 用户资产，跨重启存在 | **不能**。`messages` / `conversations` 语义不匹配 |
| **run 状态** | 业务事实：哪次运行、走到哪个节点、成功/失败 | **不能**（N10 无 run 级记录） |
| **节点结果引用** | 结果正文已在消息行 / 工具结果落盘，但「属于哪个节点」无处记 | **不能**。需要 `node_run → message_id` 的引用列 |
| **人工确认** | 谁在何时批准了什么（审计） | **部分**：审批已有审计（安全域），但「图级授权」无载体 |

因此编排阶段必须自带 schema 与迁移，且必须与既有 `messages` 表**只做外键引用、不做合并**。

### 4.8 命题八：审批不能因编排而降级

编排会自然产生一个新诉求：「整条链一次批准」。它必须被拆成两层：

- **图级授权**：声明「这个工作流可以执行哪些意图 / 哪些工具组」——这是**配置面**，与 P6 的 `alwaysApprove` 同族；
- **调用级审批**：每个工具调用仍走 `Gateway` 求值（N15）——这是**执行面**，不可跳过。

**禁止**的形态是「图级批准 → 跳过 Gateway」。理由是 P14 已把「沙箱不替代审批」写成阶段约束，编排层若提供整链豁免，会形成与 P14 直接冲突的第二条执行路径。

### 4.9 命题九：预算必须分层且可归因

现有预算是 turn 级三维 + token（N14）。run 预算不是「把 turn 预算放大 N 倍」，而是三个独立问题：

1. **run 总预算**（墙钟 / 总 token / 最大节点数）——防止图级死循环；
2. **节点配额**（每个节点分到多少）——否则先跑的节点吃光预算，后续节点静默失败；
3. **归因**（哪次 turn / 哪个工具消耗了多少）——否则账目无法分摊，`token_usage` 会失去节点维度。

I55 §4.4 的 `BudgetRemaining` 只覆盖 turn，**不覆盖 run**；编排阶段必须新增 run 层口径，且显示规则沿用「未配置 ≠ 0」（N14）。

### 4.10 命题十：编排失败不得回灌

I55 O9 已定「观测失败不影响 turn」。编排层是更强的外部依赖（可能崩、可能卡、可能被杀），因此必须扩展同一条：

- 编排层崩溃 → 正在跑的 turn 仍完成，终态照常落库；
- 编排层丢事件 → 只能降级为「该 run 停在最后一次已知节点」，不得让 turn 失败；
- 编排层被杀 → run 标记为 `orphaned`，由启动扫描收口（与 I38e tasklist（已归档）登记的「turn task panic 无终态事件」属同类问题，收口方式应一致）。

### 4.11 命题十一：子代理与子会话是图里的节点类型，不是编排的替代品

P8.1（`spawn_agent`）与 P8.2（Worker 会话）在编排语境下不是「另一条路线」，而是**节点类型**：

- 图里一个「委派节点」= 一次 `spawn_agent`（受 `max_depth = 1` 约束，N16）；
- 图里一个「子会话节点」= 一个 Worker 会话（受 P8.2 的 roster / steer 约束）。

**因此编排不得先于 P8.1 落地**：否则会出现「图里的子代理」这条绕过深度限制与取消树的第二条路径。

### 4.12 命题十二：价值门槛——只串 turn 不构成新阶段

如果编排的全部能力是「节点 A 的 turn 跑完，再跑节点 B 的 turn」，那它等价于多轮提示链，现有「会话 + `AgentMode`」已经能近似表达（P6 已落地模式与链路选路）。

**不可替代的价值只来自三件事**：

| 能力 | 为什么现有机制做不到 | 参考对应物 |
|---|---|---|
| **并行分支（fan-out）** | 单会话单 turn 互斥（N7）；`partition_tool_batches` 只在工具批内并行 | ComfyUI 多输出分支；n8n 多分支 |
| **条件路由** | 现有 turn 的分支只有「有无工具调用」一条判据（`branch` 节点） | Dify `graph_topology` + 条件边；n8n IF 节点 |
| **人在环节点** | 现有 HITL 只有调用级审批与 `ask_user` 工具（N15），没有「图停在这里等人」的形态 | Dify `human_input` 节点 |

**判定：三者缺一，编排不应立项。** 只有并行分支时，它是「批量跑 N 个 turn」；只有条件路由时，它是「模型决定下一轮提示」；只有 HITL 时，它是一张审批流程表。三者同时具备，才构成「可编排 Agent」。

## 5 三种形态取舍

| 形态 | 描述 | 优点 | 致命问题 | 判定 |
|---|---|---|---|---|
| **A 后端编排 crate** | 新增 `assistant-orchestrator`，依赖 `assistant-agent` 的端口与 `assistant-tools` 的 pipeline；自带 run 台账；控制经命令入口 | 有持久化、有取消、有审批资格；与内核端口隔离一致（I36a）；可被前端与未来其它入口共用 | 需要新 crate 与新 schema；需要 run 级键（N7 的键策略由编排层自担） | **推荐** |
| **B 前端编排** | 画布 + 前端调度器（webview 内决定下一节点，经 ipc 发命令） | 无需后端 crate；迭代快 | 无持久化、无跨窗口一致、应用关闭即丢 run；调度逻辑与 UI 同生共死；无法在后台推进 | **不采纳为唯一方案**；画布仍是必需的 UI 形态 |
| **C 编排即模式** | 把编排做成一种 `AgentMode`（新增 `kind`），一个 turn 内按图执行 | 复用既有模式配置面 | 与「单 turn 单发射者」冲突；图的多次执行必须产生多个 turn，塞进一个 turn 会让 `turn_index` / `iteration` 语义崩塌 | **不采纳** |

**结论：A 为骨架、B 为视图、C 明确排除。** 具体形态：

```
┌────────────── 前端 feature（画布 + run 视图）──────────────┐
│  工作流模板编辑（数据）· run 进度投影（只读）· 人工确认入口   │
└──────┬──────────────────────────────────▲──────────────────┘
   命令（保存模板 / 发起 run / 取消 / 确认）   事件（agent-node-event + run 事件）
       ▼                                    │
┌────────────── 编排层（assistant-orchestrator）──────────────┐
│  GraphScheduler（控制端口，自有状态机）· RunStore（run 台账）  │
└──────┬──────────────────────────────────▲──────────────────┘
   发起 turn / 取消（既有命令入口）          只读订阅（无回执）
       ▼                                    │
┌────────────── 内核层（现状，不改）──────────────────────────┐
│  TurnRunner → RoundExecutor → ToolPipeline → EventSink        │
└──────────────────────────────────────────────────────────────┘
```

四条与 I55 §11.2 完全一致的约束：编排器自有控制端口；只经既有命令入口发起 turn；观测 sink 恒只读；编排失败不回灌。

| **D6** | 并发键 | `run_id` / `(run_id, node_id)` / 复用 `conversation_id` | 决定 `TurnTasks` 是否新增一层、事件路由键 | **`(run_id, node_id)`**；`TurnTasks` 不动（I55 §11.4 第 4 条） |
| **D7** | 审批单元 | 保持调用级 / 新增图级授权 / 两者 | 决定审批卡片与审计字段 | **两者并存**：图级为配置面、调用级不可跳过（§4.8） |
| **D8** | 预算分层 | 只有 run 总预算 / run + 节点配额 + 归因 | 决定 `token_usage` 是否加 run 维度 | **run + 节点配额 + 归因**（§4.9） |
| **D9** | HITL 形态 | 复用 `ask_user` / 新增图级 HITL 节点 | 决定是否新增节点类型与事件 | **新增图级 HITL 节点**，但底层复用 `ask_user` 的问答 DTO（不新造 wire 家族） |
| **D10** | 与 P8.1 / P8.2 的先后 | 编排先立项 / P8.1 先行 / 并行推进 | 决定图内子代理是否出现第二套深度与取消规则 | **P8.1 先行**（或至少同批）：图内委派必须复用 `spawn_agent` 的 `max_depth` 与取消树（§4.11） |

## 8 门禁

未来编排规格（无论叫 P16 还是别的编号）的验收判据。每条都是可检查的，不是原则宣言。

| # | 门禁 | 检查方式 |
|---|---|---|
| **O1** | 编排层不得成为第二个 turn 发射者 | 全仓 turn 发起点仍只有命令层一处（`src-tauri/src/cmd/agent/mod.rs`） |
| **O2** | 编排层不得让 `EventSink::emit` 有返回值或产生回执 | 端口签名不变；编排侧只有订阅，无 `emit` 调用 |
| **O3** | 节点集合只能来自既有语义单元（turn / 工具调用 / 会话） | 节点类型枚举可逐项映射到 N5 / N6 / 会话；出现「模型调用」「中间件」类节点即不合格 |
| **O4** | 「turn 模板（常量）」与「工作流模板（数据）」在命名与数据结构上分离 | 两个独立类型、两张独立表；不得用同一 `Workflow` 类型承载两者 |
| **O5** | 所有节点执行必须经既有命令入口与 `ToolPipeline` | 编排层不得直连 provider / 不得自建工具执行路径 |
| **O6** | run 状态必须落库且可恢复（含幂等） | 重启后 run 可续跑或明确标记 `orphaned`；重复发起同一 run 不产生双执行 |
| **O7** | 取消必须是 run 级树传播且幂等 | 取消 run 时其所有节点与子代理收到取消；重复取消无副作用 |
| **O8** | 并行节点必须声明并发上限与冲突域 | 写同一工作区路径的节点不得并行（与工具批内并行的冲突判据同源） |
| **O9** | 预算必须分层且可归因 | 存在 run 总预算与节点配额；账目可按节点分摊；「未配置 ≠ 0」显示口径保持 |
| **O10** | 前端画布不得成为控制源 | 画布只发命令、只读投影；断开前端后 run 仍能推进 |
| **O11** | 未知节点类型不得渲染为默认态 | 沿用 I55 §4.8：降级为 `pending` + 原始参数可展开，并计入未知节点计数 |
| **O12** | 事件必须自带 `runId` / `nodeId` 路由键 | 前端投影按 `(runId, nodeId)` 键控；不得依赖「活跃会话」过滤（N11） |
| **O13** | 保存期必须校验图（环、悬空边、必填输入缺失、类型不符） | 保存即拒绝非法图；错误定位到节点与边（参考 R7 `graph_topology`） |
| **O14** | 已有 chat / agent 单轮链路零回归 | 既有契约测试与端到端用例全绿；编排代码路径在无 run 时不参与 |
| **O15** | 编排失败不得回灌内核 | 编排崩溃 / 丢事件 / 被杀三种情形下 turn 仍正常终态（§4.10） |
| **O16** | 图内委派受 `max_depth` 与取消树约束 | 与 I38f 同一常量、同一传播路径；不得出现编排层自建深度计数 |

## 11 收口

**可行，但门槛在价值而不在技术。**

技术上需要补的三件基础设施都在既有架构的自然延长线上：

1. **run 级键与取消树**——`TurnRunCtx` 已预留归属字段（N8），`TurnTasks` 的键策略被 I55 明确划给编排层（N18）；
2. **run 台账**——与消息表只做外键引用，不改既有 schema 语义（§4.7）；
3. **控制端口**——I55 §11.2 的四条约束已写好，只差接口定义（N17）。

真正的风险在形态：

- 若把 L1（turn 内 12 节点）做成可连线图，会得到一个「内核结构可视化器」，而它的每次内核重构都变成 wire 破坏性变更；
- 若只做「串 turn」，会得到一个「用画布画多轮提示链」的空壳，价值低于既有「会话 + 模式」；
- 若照搬 ComfyUI 的输出缓存，会在 agent 节点上产生假命中，后果是工具副作用被跳过、审批被静默绕过。

因此本分析的最终判定是三句话：

1. **单元定案**：编排的节点是 turn 与工具调用，不是内核节点（§4.1、§4.4）。
2. **边界定案**：编排层读 I55 的只读事件、写自己的 run 台账、控制只经既有命令入口，不改内核一行（§4.5、§5）。
3. **门槛定案**：并行分支、条件路由、人在环节点三者至少同时具备两项（推荐三项），否则不立项（§4.12）。
