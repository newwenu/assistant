## 0 命题核对

下表只核对「命题是否成立」，不回答「因此该做什么」。

| # | 命题 | 核对结果 | 依据 |
|---|---|---|---|
| 1 | 现有「画布」是一张图 | **不成立** | 它是 CSS 网格：位置来自模板行列号，**全图没有一条线**，只有「当前活动边」的高亮与一行文字（C1/C2） |
| 2 | 观测画布现在就能画出全图连线 | **不成立，但缺口只有边集** | 边可由模板顺序派生（C2 的 `templatePredecessor` 就是 `order - 1`），但视图模型里没有边数组（G1）；出口边须另立一类，不得建成第 13 个节点（P6） |
| 3 | 现有观测画布具备缩放 / 平移 | **不成立** | 无坐标系、无 wheel / scale 实现（C1/C4） |
| 4 | 两种画布能共用一套渲染设施 | **成立** | 节点 / 边 / 背景 / 视口四件设施与「只读 vs 可编辑」正交（P2） |
| 5 | 两种画布能共用同一个视图模型 | **不成立** | 「格子」（行列号，无端口无尺寸）与「盒子」（x/y/w/h + 端口 + z-order）是两种数据形状（P3、C16） |
| 6 | 画布可以是 run 的推进者 | **不成立** | 编排分析 O10：画布只发命令、只读投影；断开前端 run 仍推进（P1） |
| 7 | 引入画布库必然破坏既有约束 | **不成立** | 破坏与否取决于三条前提是否建立（映射层 / 策略单点 / 失效不退化），而非取决于是否引库（§5） |
| 8 | 几十节点规模下 DOM 节点够用 | **成立** | Dify（`reactflow`）与 n8n（`@vue-flow/core`）都是 DOM 节点 + 库负责视口/边（R10/R11）；ComfyUI 的 canvas 路线是为 100+ 节点与扩展生态（R1） |
| 9 | 混合渲染（canvas 背景 + DOM 节点）在本项目成本低 | **不成立** | ComfyUI 两次事故说明代价是「帧边界 + 策略单点」；这两件事我们都还没建（R6/R7、G5） |
| 10 | 现有 rAF 合并可作为画布失效的落点 | **成立** | `schedule.ts` 已是「唯一调度点 + 帧合并 + 引用相等抑制」，与 ComfyUI 分类失效同构（C5） |
| 11 | 画布交互缺失的根因是框架缺失 | **不成立** | 缺的是交互（C3 零交互），不是框架；需要的是「纯 reducer + 意图输出」（P8） |
| 12 | 画布状态必须进 wire | **不成立** | 项目规则：wire 不承载本地 UI 状态；画布可零新 DTO（P12） |
| 13 | 画布快捷键必须自建监听 | **不成立** | 仓库已有统一 keymap（`src/types/shortcutDefaults.generated.ts`），画布是新的注册方（P13） |
| 14 | 单一 `NodeCell` 能承载节点类型扩展 | **不成立** | 需要「注册表 + 能力声明」，否则闭集一扩就散架（P7、G6） |
| 15 | 观测画布的补边 / 选择 / 视口依赖编排层定案 | **不成立（即不依赖）** | 三者只消费编译期模板与本地视图模型，不读工作流模板 schema、不读 run 台账（§11） |
| 16 | 编排画布的连线编辑可脱离模板 schema 先行 | **不成立** | 连线编辑的对象是工作流模板数据，其 schema 由编排层定案（G11、编排分析 D5/G6） |
| 17 | 证据等级标注可随缩放省略 | **不成立** | 证据等级是 I55 §6.6 的语义，不是视觉装饰（P11） |

一句话：**本项目的画布问题不是「选哪个库」，而是「画布从来没有被当成一层」——现在它是一段网格布局代码。** 命题 4 / 5 / 10 / 12 / 13 合起来只导出三条结构性条件：格子与盒子分型、交互策略只有一个读取点、失效与视口各有一个纯数据边界。这三条与具体选型无关；是否采纳、以何种顺序落地，由规格定案。

## 1 边界

### 1.1 一张设施，两种画布

「画布」在本项目里同时指向两个东西，混谈必然得出错误结论：

| | 观测画布（已存在） | 编排画布（未立项） |
|---|---|---|
| **数据源** | 编译期模板 `AGENT_NODE_TEMPLATE` + `TurnObservation` 投影 | 工作流模板数据（运行期）+ run 投影 |
| **图的性质** | 固定图：12 节点、11 条前向边 + 1 条回边 | 用户可编辑图：节点 / 边 / 端口由模板决定 |
| **交互策略** | **只读**（点击查看，不可改图） | **可编辑**（拖拽 / 连线 / 删除 / 保存） |
| **事实来源** | 只读副本（I55 O6 / §6.5，C14） | 模板 = 命令产物；run 进度 = 只读投影 |
| **节点形状** | 格子：行列号 + 状态徽标 | 盒子：坐标 + 尺寸 + 端口 + z-order |
| **失效来源** | 事件流（帧合并，C5） | 事件流 + 用户输入 + 视口 |

分析结论：**两套视图模型、一套渲染设施、两份交互策略。** 可共用的是「节点渲染器 / 边渲染器 / 背景 / 视口 / 失效调度」五件设施；不可共用的是「节点数据形状」与「策略」。

**本文用词以词表为准**：画布 / 观测栅格 / 格子 / 单元格 / 盒子 / 卡片 / 端口 / 槽 / 交接端点 / 接线 / 连线 / 锚点 / 模板边 / 出口边 等术语的唯一出处是《编排分析概念清单与语义转移对照》§2.5（边与卡片词表），本文只引用不复述。三点直接影响本文的读法：

1. 本文旧称的「观测画布」在词表里是**观测栅格**（固定拓扑、只读、无视口），与「编排画布」不是同一类 UI；
2. 观测侧节点边缘的可视位置叫**锚点**，不叫端口——L1 无边可接（N3），端口是 L2 概念；
3. 「边」是数据形状、「接线」是语义实例、「连线」是渲染形态，本文 §4.6 与 §6 讨论的分别是这三层。

### 1.2 画布不是控制源，也不是事实源

编排分析 O10 已经把这条写死：画布只发命令、只读投影。本文把它翻译成三条可检查的约束：

1. 画布组件**不得** import 任何控制路径（`send` / `cancel` / 工具执行），只 import 投影读取与命令发射（K1）；
2. 画布**不得**写观测 store，观测 store 的任何字段都不得被画布侧改写（K2）；
3. 断开画布（路由切走 / 组件卸载）后，run 与 turn 的推进不受影响（K1 的行为版）。

### 1.3 与编排分析的分工

编排分析 §1.4 明确把「画布渲染与交互（拖拽 / 缩放 / 小地图）」划出本文范围，并只在 §5 给了位置约束：「A 为骨架、B 为视图」。本文是那一句的展开：**画布是视图，视图里的一切都不能反向决定调度**。反过来，编排层给画布的只有两件输入——工作流模板 schema（D5/G6）与 run 投影（O12 的 `runId`/`nodeId` 路由键）；本文不重新设计它们。

### 1.4 不属于本文的东西

- 节点参数表单与校验 UI（属工作流模板 schema 的编辑面，只受本文 §7 的缝约束）；
- 自动布局算法（分层 / 力导向 / 正交路由）：本文只要求「布局意图」与「渲染测量」分离（P4），不选算法；
- 后端调度、run 台账、取消树（编排分析 §4.6 / §4.7）；
- 排期与人力（本文只给依赖关系与可验证的出口，§11）。

1. **画布不存在，只有版面**：无坐标系、无视口、无选择、无手势（C1/C3/C4）。

3. **正确的骨架已有一半**：失效调度（C5）与只读纪律（C14）已经是画布需要的形态，缺的是几何与交互。

## 3 参考项目结构对照

| # | 参考 | 核心结构 | 与本项目的同构点 | 可移植性 |
|---|---|---|---|---|
| **R1** | ComfyUI 前端双渲染器 | 经典 canvas（litegraph）与 Vue DOM 节点**并存**，后者是 cloud/desktop 默认；两套指针路径（`CanvasPointer` vs `useNodePointerInteractions`） | 我们只有 DOM 一侧；「两套渲染器分叉」是混合渲染的现成反例 | **不可移植**（反例：两条指针路径与两套呈现边界） |
| **R2** | ADR-CANVAS-VIEWPORT-0009 | `CanvasViewport` 冻结快照 + `measureViewport`（纯）/ `applyViewport`（原子副作用）；双画布一次应用；DPR 归一化 ≥ 1；scheduler 管「何时」、viewport 管「是什么」 | 「视口是纯数据」与我们的投影纯函数同一口味；DPR 问题在 DOM 下不存在，但「快照 + 原子应用」的形式仍适用 | **形式可移植**（快照 + 单一应用点）；**内容不适用**（无 canvas 后备缓冲） |
| **R3** | ADR-CANVAS-GESTURE-0029 | 纯 reducer 手势状态机；`GestureState` 判别联合；输出意图不产生副作用；`InteractionPolicy` 作为单一策略值 | 我们零手势（C3），但一旦加拖拽/框选，就必须先有 reducer 与策略值 | **结构可移植**（P8） |
| **R4** | ADR-RENDERING-INVALIDATION-0021 | 按**原因**分类失效、帧级合并、动画显式生命周期 | `schedule.ts` 已是「帧合并」；缺「分类」与「动画生命周期」（P10、G9） | **可移植**（增量扩展现有调度点） |
| **R5** | ADR-RENDERING-ATOMICITY-0020 | 帧级快照、显式依赖、禁止传递读（transitive read） | 与我们的「投影纯函数 + 引用相等」同构 | **已有雏形**（C5），无需重造 |
| **R6** | ADR-CANVAS-0052（Accepted） | 共享几何**不等于**同步：canvas 帧是两种渲染器的呈现边界；DOM 位置更新服从画布帧 | 混合渲染的代价被写成了规则 | **原则可移植**（P11 的「帧边界」），仅在走混合渲染时适用 |
| **R7** | ADR-CANVAS-INTERACTION-0035（**Proposed**） | 「拾取中」一个模式被抄进约二十个面（节点标题折叠与重命名、缩放手柄、右键菜单、alt-clone、widget 网格、slot 连线、事件处理器、DOM widget 层、媒体预览…），每个新面都要自己知道该读哪个 capability；中间修订改为 pin `read_only` 后又让点击选择失效；两次所有权修复仍未收敛。结论：**一个权威事实 + 一个读取器注入到派发点**（`CanvasInteractionModeReader.isSelectOnly()`），不复制到任何地方 | 这正是「策略拷进组件」的完整事故记录 | **反例**：策略必须在派发点读一次（P2、K8），复制到任何位置都会复现该事故 |
| **R8** | ADR-CRDT-LAYOUT-0003 | 位置**意图**集中到 layout store，渲染**测量**留本地投影；命令模式 + 观测者；为换渲染器留路 | 我们的「位置」目前是模板行列号（意图的最小形态）；测量尚不存在 | **分离原则可移植**（P4）；CRDT 与命令模式**无对应需求** |

## 4 结构命题

本节是从 §2 事实与 §3 参考导出的结构性命题，每条给出可检查形式；它们不指定选型。后文引用的 `P1`–`P13` 即本节命题一至十三。

### 4.1 命题一：画布是视图 + 命令发射器，不是控制源

O10 的画布版。可检查的形式是依赖方向：画布组件只 import 投影读取与命令发射，不 import 控制路径（K1）。反例很具体——若画布能直接 `send`，那么「在画布上点一个节点」就等于「发起一次 turn」，审批与预算全部旁路（编排分析 §4.8）。

### 4.2 命题二：一套设施、两套策略、策略只有一处事实

设施（节点渲染器 / 边渲染器 / 背景 / 视口 / 失效）与「只读 vs 可编辑」正交；但**策略必须在派发点读一次**，不得作为 prop 或 store 字段拷进每个节点组件。R7 是这条命题的完整事故记录：一个「拾取中」被抄进二十个面，每个新面都要自己知道该读哪个 capability，两次所有权修复仍未收敛。

**可检查形式**：全仓只有一处 `isEditable`（或同义策略值）的读取点，且位于手势派发入口（K8）。R7 给出的实现形态是「一个权威事实 + 一个单方法读取器（`isSelectOnly()`）注入到派发点」，而不是把策略值塞进节点 `data` 或组件 prop。

### 4.3 命题三：格子与盒子是两种数据形状，不得合并

`GraphNodeView` 是格子：行列号 + 状态 + 证据等级，无端口、无尺寸、无 z-order（C16）。编排画布的节点是盒子：坐标、尺寸、端口、层级。把格子「升级」成盒子会立刻带来两个后果：

1. 观测画布被迫承担编辑语义（端口存在即暗示可连线），与 I55 O4「模板静态」冲突；
2. 编排分析 O4 要求「turn 模板（常量）」与「工作流模板（数据）」在类型上分离——格子/盒子分家是这条 O4 在前端的对应物。

### 4.4 命题四：位置是意图（数据），尺寸与锚点是测量（渲染）

R8 的分离原则。观测画布现在只有「意图」的最小形态（行列号，C1）；编排画布会有真正的意图（x/y/w/h，来自模板数据）与真正的测量（端口像素位置、文本实际高度、连线端点）。

**测量不得进 store**：进 store 的测量值会让每次 resize / 字体加载都变成一次状态写入，进而触发一次帧重算——与 C5 的引用相等抑制正好打架。

### 4.5 命题五：视口是纯快照，缩放平移只改视口不改节点坐标

R2 的形式：`viewport = { x, y, scale }` 冻结快照，单一应用点（DOM 侧是一次 `transform: translate(x,y) scale(s)`）。三条推论：

- 缩放不得写回节点坐标（否则每次缩放都是一次全图位置写入）；
- 视口变化只触发「背景 + 边」的失效，不触发节点内容重渲染（K6）；
- 适配全图（fit）是视口的派生计算，不是布局的重新求解。

### 4.6 命题六：边是独立子系统，且「活动边」是派生量

观测画布的边集是常量（11 前向 + 1 回边，C15），可以纯派生；但**活动边是投影算出来的**（`activeEdgeOf` 取「最靠后的进行中格子」，再按 `order - 1` 与 `admit + iteration > 1` 两条规则定边），画布不得自己从状态推断「哪条边在动」，否则同一事实会有两个算法。

更硬的一条：补全图边集时，**全图边集与活动边必须同源**。现有 `activeEdgeOf` 里的两条规则（前向 = `order - 1`、回边 = `admit` 且 `iteration > 1`）如果只在投影里存在，而画布另写一份 `edges` 常量，就会出现「高亮的边不在画出来的边集里」——这种不一致没有任何测试能拦住。能满足同源要求的形态是把两条规则收成一份 `templateEdges` 常量，投影与画布都读它，并用判据锁死（K14）。

另有一类边不属于节点图：**出口边**（③/⑩/⑫ 的 `stopped`、④ 的 `failed`/`cancelled`、⑦ 的 `completed`/`wrap_up`、⑨ 的 `cancelled`）指向的是汇点徽标而非节点（I55 §3.2）。画布必须把「出口边」与「节点边」分成两类数据，否则出口会被迫建成第 13 个节点，与 O4「模板静态、12 节点」冲突。

编排画布的边是数据（用户连线），必须有独立的边渲染器：路径计算、标签、命中区、活动/选中态。把边当节点渲染的副产物，会在「边上挂加号（插入节点）」这种需求出现时立刻返工（R10 的边即入口）。

### 4.7 命题七：节点渲染走注册表 + 能力声明，key 来自闭集

一个 `NodeCell` 组件硬编码了 12 个节点的语义（顺序徽标、迭代徽标、证据徽标、状态文案）。节点类型一旦扩展（编排分析的 L2 节点：turn / 工具调用 / 会话），这套硬编码就会变成 if/else 分支树。

C13 已给了现成形态：注册表 + `index.ts` 自注册 + 能力声明。**能力声明**是画布侧真正需要的那部分——「该节点是否可编辑」「是否带端口」「是否有详情面板」；它决定交互策略在派发点如何取值（P2）。

### 4.8 命题八：手势是纯 reducer，输出意图而非副作用

R3。手势状态是判别联合（idle / panning / dragging-node / marquee / connecting），`reduce(state, event) → state` 纯函数；意图（`pan` / `select` / `move` / `connect`）由 dispatcher 翻译成命令或本地状态变更。三条收益直接对应我们的缺口：

- 拖拽 / 框选 / 平移不会各自 `if`（G7）；
- 只读策略在 reducer 入口读一次（P2）；
- 手势可单测，不需要 DOM fixture。

### 4.9 命题九：选择是有序集合，且只有一个所有者

R13。ComfyUI 为此写了两份 ADR：0028 记的是「选中事实同时存在于 `item.selected` / `canvas.selectedItems` / `selected_nodes` / store 镜像，15 处调用手工同步」；0031 记的是「用不可变集合每次增删都复制既有成员，选 200 个节点要重建 19,900 个键」。

对本项目的含义：

1. **单一所有者**：选中态只能有一份，不得同时存在于组件 prop、store 字段与 inspector 入参；多选是**有序集合**运算，不是「层级最高者」；
2. **本地 UI 状态**：选中只影响描边与 inspector 联动，不进 wire、不进持久化（P12）；
3. **增量增删**：选择命令只增删成员，不重建整个集合（避免 0031 的二次方写入）。

### 4.10 命题十：失效按原因分类，动画有显式生命周期

C5 已经做了「帧合并 + 引用相等」，缺的是分类与动画（R4）。分类的最小集合：`viewport` / `node-state` / `selection` / `edges` / `layout-measure`。分类的价值不在命名，而在**可判定**：视口变化不得重算节点投影（K6），选中变化不得重算边路径。

动画的三种口径各有代价：无限 CSS 动画在「turn 收尾」时无人停（`running` 脉冲会一直闪）；JS 循环与 C5 的帧合并冲突；「CSS 动画 + 由状态变化驱动启停」两处都避开，但要求状态变化与动画起停严格配对。口径属 §9 的 D9。

### 4.11 命题十一：证据等级在任何视觉编码下保真

`observed` / `derived` / `assumed` 是语义（I55 §6.6），不是装饰。三条硬约束：

1. 缩放不得隐藏证据徽标（小尺寸下可折叠为色点，但不得消失）；
2. 边与节点着色都不得覆盖证据编码（例如用虚线画 `derived` 的格子，用同一种虚线画「未连接」的边就会混淆）；
3. 未知 `node` / `state` 取值走「不显示」，不得渲染成默认态（C7、O11）。

### 4.12 命题十二：画布零 wire 变更

画布状态（视口、选择、悬停、拖拽中的临时坐标、展开的详情）全部是本地 UI 状态。项目规则已定：wire 不承载本地 UI 状态，本地扩展用交叉类型。因此画布的任何增强都不得产生新 DTO、不得要求 `npm run contract:gen`（K3）。

### 4.13 命题十三：画布快捷键接入统一 keymap，不自建监听

仓库已有生成式快捷键默认表（`src/types/shortcutDefaults.generated.ts`）与冲突校验。R14 的经验是：焦点决定所有权、冲突在激活前解决、canvas 编辑器必须暴露一个可聚焦 owner。落到本项目的三条要求：

- 画布是一个可聚焦容器（`tabIndex=0` + `role`），键盘事件只在该容器内生效（G10）；
- 画布快捷键注册进同一张表，冲突由既有机制在注册期拒绝（K9）；
- 焦点在输入框 / 弹层内时，画布快捷键必须失效（不得自建 `document` 监听）。

## 5 渲染形态的方案分析

三种形态不是互斥的二选一，而是对应不同的规模与交互复杂度区间。本节只分析各方案的前提、代价与失效模式，不给选型结论。

| 形态 | 描述 | 成立条件 | 主要代价 | 条件不满足时的失效形态 |
|---|---|---|---|---|
| **A DOM + CSS** | 网格布局 + 横向滚动；边用固定锚点折线 | 节点数固定且小（约 ≤ 30）；只读；无缩放 / 平移需求；无小地图与协作 | 无视口能力；节点一多只能靠滚动；跨行边与回边要按行列轨道特判 | 节点增长后必须补视口，而补视口会连带引入「锚点改测量」，与 P4 冲突 |
| **B 引入 `@xyflow/react`** | 库负责视口 / 边 / 端口 / 框选 / 小地图 / 键盘；我们用映射层喂视图模型 | React 栈；需要视口、框选、端口、小地图中的多项；规模在几十到数百节点 | 新增依赖；库的受控 `nodes` / `edges` 数组与既有帧合并之间需要桥接 | 缺映射层 → 库数组变成事实源（违 P1）；策略写进节点 `data` → R7 事故重演；每帧重建数组 → C5 的引用相等抑制失效 |
| **C 自研 canvas2D + DOM 覆盖层** | ComfyUI 形态：背景与边画在 canvas，节点是 DOM | 100+ 节点；需要统一 canvas 帧边界；需要扩展生态（widget / 第三方节点） | 富文本节点 + i18n + antd 主题需自绘或镜像；DPR、帧边界、策略单点三件基建都得自建 | 三件基建缺一 → 两套指针路径与两套呈现边界（R1/R6）；策略被抄进各层（R7） |
| **D 自研 DOM + SVG 边** | 自己实现 `transform` 视口、SVG 贝塞尔边、矩形框选 | 规模 ≤ 30；无小地图 / 协作；连线只允许端口到端口 | 视口数学、边路径、框选、键盘导航全部自建；每一处都是「策略泄漏」的新风险点 | 交互项一增加（小地图 / 边即入口 / 多选快捷键），自建件的维护成本按项累加 |

**方案与需求的对应关系**（用于判断落在哪个区间，不构成选型）：

| 需求特征 | 落在哪个区间 |
|---|---|
| 节点固定 12、只读、无缩放 | A 的成立条件全部满足；B/C/D 的能力全部闲置 |
| 节点几十、需要视口与框选、无小地图 | B 与 D 的成本接近，交叉点取决于是否已有 React 图库依赖 |
| 节点上百、需要小地图 / 协作 / 第三方扩展 | C 的能力才被用到，但三件基建必须先存在 |
| 只读画布与可编辑画布共存 | 与形态无关：A/B/C/D 都要求「策略单点」与「视图模型分型」（P2/P3） |

**B 的三条必要条件**（不是建议，而是「选了 B 就必须同时成立」的条件；缺任一条，B 的实际行为退化为 D 的代价并额外背上依赖）：

1. **映射层**：库的 `nodes` / `edges` 是**派生产物**，每次从视图模型映射（R11 的 `useCanvasMapping`），库状态不得被任何控制路径读取（K1）；
2. **策略单点**：只读 / 可编辑在派发点读一次，不写进库的节点 `data` 里再逐组件判（K8）；
3. **失效不退化**：库的受控数组更新必须经过既有帧合并，不得让每次事件都重建整个 `nodes` 数组（K7）。

**规模边界尚未定案**：B 与 D 的成本交叉点取决于编排画布的节点规模上限、是否需要小地图、连线是否只允许端口到端口（Q1）。该信息属编排层，本文不给阈值。

## 6 分层与缝

### 6.1 六层

| 层 | 内容 | 输入 | 输出 | 禁止 |
|---|---|---|---|---|
| **L0 图数据** | 编译期模板（观测）/ 工作流模板数据（编排） | 无 / 命令产物 | 节点 + 边 | 画布不得写 L0 |
| **L1 视图模型** | 格子视图（现状）/ 盒子视图（待建） | L0 + 投影 | 纯数据（含证据等级） | 视图模型不得含测量值 |
| **L2 视口** | `{ x, y, scale }` 冻结快照 | 用户手势 / fit 计算 | 变换 | 视口不得写回 L1 |
| **L3 几何** | 位置意图（L1）+ 测量（本地） | L1 / L2 | 像素矩形、锚点 | 测量不进 store |
| **L4 渲染器** | 节点注册表 / 边 / 背景 / 覆盖层 | L1 + L3 | DOM | 渲染器不得读策略、不得发命令 |
| **L5 交互** | 策略 → 手势 reducer → 意图 → dispatcher | DOM 事件 | 意图 / 命令 | reducer 不得有副作用 |

失效是横切关注点：L1 变化、L2 变化、L5 产生的本地状态变化都经同一个调度点（C5）按原因分类合并。

### 6.3 格子模型补边时的几何问题

观测画布不引入视口，但补边仍然需要一次「格子 → 锚点」的几何换算，这是 L3 在格子模型下唯一要建的部件。三种边各有不同的锚点规则：

| 边类型 | 例 | 锚点规则 | 注意 |
|---|---|---|---|
| **同行前向** | ①→② … ⑪→⑫（同 row） | 从左侧格子右边框中点，到右侧格子左边框中点 | 纯 CSS 网格下可用「行轨道 + 列轨道」直接算出，不需要测量 |
| **跨行前向** | ⑦ `branch` → ⑧ `budget-split`（同列不同行） | 从上一行格子下边框中点，到下一行格子上边框中点 | 折线或短竖线；不能用水平锚点，否则线会穿过格子 |
| **回边** | ⑫ `after-iteration`（row 1, col 10）→ ① `admit`（row 0, col 0） | 从 ⑫ 上边框出、沿两行之间的空隙回到 ① 下边框 | 必须与所有前向边**视觉可分**（不同线型或不同层级），否则「回路」读不出来 |

由此得到两条约束：

1. **锚点由模板行列号推导，不测量**：格子的像素位置来自网格轨道，`row` / `column` 已知即可算锚点；一旦改成「读取 DOM 实际尺寸」，就会把测量拉进 store（违反 P4/K5），也会让 resize 触发一次全图重算；
2. **回边与证据编码不得共用同一种线型**：P11 要求 `derived` 用某种视觉区分，回边也要区分——两种语义不能都靠虚线表达（否则 `derived` 的节点与「回路」会被读成同一件事）。可用「回边固定走行间空隙 + 端点箭头 + 独立 z 层」而非线型。

编排画布不存在这个问题：锚点是节点盒子上的端口（G2），位置与尺寸都来自数据（D11），几何换算由库承担。

## 13 分析结论

三条，均为事实判断，不含选型：

1. **现状是版面，不是画布**——网格、行列号、零交互、零边线。它把「图」这件事降级成了一行文字（活动边）与几个徽标（C1/C2/C3/C4）。
2. **画布必须先被当成一层才谈得上形态选择**——六层（数据 / 视图模型 / 视口 / 几何 / 渲染器 / 交互）+ 七条缝（投影 / 视口 / 注册表 / 手势 / 命令 / 失效 / 主题）。其中投影与失效两条已有正确骨架（`projections/` 与 `schedule.ts`），另外五条是空白（§6）。
3. **两个工作块的依赖不对称**——W1（补边与选择）不依赖任何未定项；W3（编排画布）依赖模板 schema 定案（G11、编排分析 D5）。这一不对称是依赖事实，如何据此安排落地属规格。

另有一条条件性判断：**若在缺少映射层、策略单点、失效约束时引入图库，得到的是「把库的 `nodes` 数组当事实源、把只读与可编辑抄进每个节点组件」的画布**——这正是 R7 记录的事故形态。这是「条件不满足时的后果」，不是对某种形态的结论。
