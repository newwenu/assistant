# I9 密码箱设计（v1.5）

> 状态：活跃设计文档（2026-11-12）

## 1. 要解决什么问题

v1 把「口令」和「数据密钥」焊在一起：主密钥 = Argon2id(口令)。这一个选择带来四个连锁后果。

| 后果 | 表现 |
|---|---|
| 改密 = 换密钥 | 每条条目都要重加密，本机库要 `PRAGMA rekey`，成本 O(n)，中途失败要回滚 |
| 恢复码被口令绑架 | 恢复封装包的是主密钥，所以改密必须作废恢复码并重新生成 |
| 仓库被迫承载恢复结构 | 为了「只凭仓库 + 恢复码」能恢复，`.vault-meta` 里存 salt 与加密后的主密钥 |
| 跨用户预计算 | 引导 salt 是硬编码常量，所有人都能共用同一份彩虹表 |

根因只有一个：**口令直接参与数据密钥的生成**。v1.5 的全部设计都是把这两件事拆开。

## 2. 加密模型

一句话：**数据由一个随机密钥保护，口令只负责把这个密钥包起来。**

```
口令 ──Argon2id(salt, m=64MiB, t=3, p=4)──▶ kek (32B)
                                              │  AES-256-GCM 包封（48B）
                                              ▼
                                    dek (20B, 随机生成)
                                              │  HKDF-SHA256 + 域标签
        ┌─────────────────────────────────────┼──────────────────────────────┐
        ▼                                     ▼                              ▼
   dbKey (32B)                           metaKey (32B)                 entryKey (32B)
  本机库页加密                          meta 完整性签名                单条目字段加密
```

四条性质，整个方案都建立在它们上：

1. **`dek` 是唯一随机源。** `kek` 是它的包裹工具，`dbKey` / `metaKey` / `entryKey` 是它的派生。除此之外没有任何独立随机密钥。
2. **口令只出现在一条路径上**：`口令 → kek → 解开 dek`。它不参与条目加密、不参与完整性校验、不参与本机库钥匙。
3. **`dek` 从不以明文落盘。** 仓库里只有 48 字节的包裹结果（`nonce(12) ‖ 密文(20) ‖ tag(16)`）；`dek` 的另一个文本形态只存在于用户手上那张纸。
4. **域标签冻结。** `i9:v1:` 是 HKDF 的派生域，不是文件版本号。它的作用是让同一个 `dek` 在不同用途下派生出互不相关的密钥；改名会让所有既有数据解不开。

这套模型把「可用性」和「保密性」分开记账：口令泄露影响的是 `kek` 那条边，换掉它只需重包 20 字节；`dek` 泄露才是灾难，所以它只在两个地方出现——用户手里的纸，和运行时的内存。

## 3. 五个关键取舍

### 3.1 本机库钥匙从 `dek` 派生，不从 `kek` 派生

早期设计是 `dbKey = HKDF(kek)`，看起来更自然：口令变 → 库钥匙变 → 改密连带换库钥匙，听着更「彻底」。

代价是「彻底」的另一面：改密就要动 N 台设备上各自的本机库。于是冒出两个新麻烦——跨设备改密必须逐台成功，中间态要靠一套钥匙失配检测与重建流程兜底。而它保护的只是本机缓存（索引、审计表、回滚基线），丢了能重建，属于可丢数据。

改成 `HKDF(dek)` 后，改密完全不碰本机库，真正的 O(1)。代价是「拿到纸面的人可以自己算出 `dbKey`」——但纸面本来就持有 `dek`、能解开全部条目，多一个 `dbKey` 不增加任何实际能力。**用一个不成立的威胁，换掉了真实的运维复杂度。**

只有 `rotate_dek`（真换 `dek`）才需要重换本机库钥匙，而它本来就是 O(n) 全量重加密，多一步无所谓。

### 3.2 纸面恢复码就是 `dek` 本身

另一种常见做法是「仓库里放一个 recovery slot」：用恢复码包封一份 `dek` 副本，恢复时读仓库里的 slot 解开。好处是换纸只需重包一次（O(1)），`dek` 还能用 256 bit。

没选它，理由是**恢复路径的可达性**：恢复场景恰恰是「仓库结构可能已经出问题」的场景。如果恢复码要靠仓库里的封装才能用，那么 `.vault-meta` 损坏、被篡改、被替换成旧版本时，恢复也跟着失效——把唯一的救命通道和它要救的东西绑在了一起。

纸面直接是 `dek`，恢复时只需读条目文件本身，不需要 `.vault-meta` 里的任何密钥字段。代价明确记在账上：换纸 = 换 `dek` = O(n) 重加密，纸面泄露 = 全部条目泄露，纸面无法单独撤销。这三条见 §7。

### 3.3 纸面不存 `SHA256(dek)` 做校验

很自然的想法：纸上印一段哈希，抄完对一下就知道抄没抄错。否决理由两条：

- 这个哈希一旦进仓库（为了跨设备校验就得进），等于公开一个 160 bit 的靶，攻击者每猜一次只需一次 SHA-256；
- 它解决的是「可验证」，而纸面真正需要的是「可抄对」。

所以改用**能定位错误的结构**：40 字符 Crockford base32 内嵌 CRC32C。抄错时不只告诉你「错了」，而是告诉你「第 3 组第 5 个字符错了，可能是 X 或 Y」。成本是一次 CRC，收益是用户不必重抄整张纸。

### 3.4 只有一个 password slot

`slots` 设计成数组、当前恒为 1 个，不预留第二口令。理由：多口令是功能，不是安全属性；而每多一个 slot 就多一份「旧封装必须被吊销」的义务——仓库一旦进 git 历史，这个义务根本无法履行。结构上留了扩展位，需要时再加。

### 3.5 不做 v1 → v2 迁移

旧库一律拒绝（明确报「版本不支持」并给重置入口），不写迁移器。理由：没有存量用户；迁移器会永久维护两套密钥语义，是长期负债；而「迁移」在密码学上等于「同时持有新旧两套秘密」，本身就是风险面。

## 4. 数据放在哪

| 位置 | 内容 | 进 git |
|---|---|---|
| 仓库 `security/vault/` | `.vault-meta`、`entries/*.enc` | 是 |
| 本机库 `security/security.db` | 条目索引、字段密文、审计表、回滚基线 | 否 |
| 用户手上 | 纸面恢复码 | — |
| OS keystore | 生物识别 payload（52B） | 否 |

仓库根目录是**白名单**：只允许 `.vault-meta`、`.gitignore`、`.git/`、`entries/*.enc`。出现 `security.db`、`*.bak`、`*.jsonl`、`*.tmp` 一律报错，只提示、不自动删除——「自动清理用户仓库」比「多一个文件」更危险。

**单一写入者**：`.vault-meta` 只由生命周期编排层写，同步引擎只能读。这不是洁癖：meta 里同时有清单和完整性签名，两个写入口必然导致其中一个失真。

`.vault-meta` 只存非秘密的密钥元数据：仓库身份、`dekVersion`、包裹后的 `dek`、条目清单、完整性签名、可选的「已备份」标记。**不含任何可直接还原 `dek` 的东西。**

条目文件把 `category`、`revision` 留在密文外，因为同步合并在不持有密钥时也要比较版本；但它们进入 AAD，被篡改会导致解密失败。这是「可比较」与「可认证」的折中，不是遗漏。

## 5. 完整性：三层，且只能检测

| 层 | 机制 | 防什么 | 存在哪 |
|---|---|---|---|
| L1 | `HMAC-SHA256(metaKey)` 覆盖整个 meta 的规范化字节 | 改 slot、改清单、改标记 | 仓库 |
| L2 | 每条目文件的 sha256 + `dekVersion` | 删条目、改条目、整块旧 meta 重放 | 仓库 |
| L3 | meta 整文件 hash + `dekVersion` + 单调 `revision` | 本机被回滚到旧状态 | 本机库 |

三个实现细节值得记：

- L1 用**专用结构体**固定字段顺序做规范化，不依赖 JSON 键序。JSON 的键序不是密码学承诺，靠通用值类型排序在嵌套与浮点上不可靠。
- L2 的 hash 覆盖**完整文件字节**，包括缩进与换行。所以外部工具「格式化一下 JSON」也会被判为篡改——这是有意的，宁可误报。
- L3 的基线只在本机有效。重建本机库会重置基线一次，必须在日志与 UI 里写明，否则用户会把「被回滚」当成 bug。

三层都是**检测**，不是**阻止**。能阻止篡改的只有签名或中心化授权，本地优先的密码箱没有这个前提。

## 6. 改密和吊销是两个动作

这是全文最容易被误解的一点，单列一节。

| | 换 `dek` | 重加密条目 | 旧口令 | 旧纸面 | 生物识别 |
|---|---|---|---|---|---|
| **改密** | 否 | 否 | 仍能解出当前 `dek` | 仍有效 | 仍有效 |
| **`rotate_dek`** | 是 | 是（O(n)） | 失效 | 失效 | 强制重注册 |

原因是一个绕不开的约束：**`.vault-meta` 一旦进过 git 历史，旧封装就永远在历史里。** 你可以删掉当前分支上的旧 slot，但 clone 过的人手里还有。所以：

- 「改密」只承诺换口令，**不承诺吊销旧口令**。旧口令 + 历史里的旧 meta 仍能解出当前 `dek`。
- 真吊销必须走 `rotate_dek`：换 `dek` → 条目全部重加密 → 历史里的旧封装解出来的只是旧 `dek`，对当前条目无效。

`rotate_dek` 的步骤顺序有硬约束：

1. 会话必须由口令建立（生物识别会话没有 `kek`，无法重包，直接拒绝）；
2. **先吊销生物识别**，失败即中止——否则旧 `dek` 还能被指纹解出来，轮换等于没做；
3. 重加密条目 → 换本机库钥匙 → 用新 `dekVersion` 重包 → 写 meta；
4. **写 meta 是唯一提交点**；
5. 提交后本机库换钥失败**不致命**：本机库是可重建缓存，下次解锁会因钥匙不匹配自动重建。

第 4 步的语义后果要记住：提交点之前的崩溃留下「新旧混杂的密文」，但 meta 仍指向旧版本，清单校验会拦住它；提交点之后的崩溃只留下本机库钥匙失配，一条重建命令就能恢复。

## 7. 边界：明确不承诺什么

这一段是产品文案的来源，不许含糊。

1. **仓库仍是口令的离线爆破靶。** salt 和包裹后的 `dek` 都在 git 里，攻击者可以离线穷举口令。v1.5 只能抬高单次猜测代价（Argon2id 64 MiB），不能消除这个靶。
2. **纸面泄露 = 全部条目泄露。** 纸面就是 `dek`，不需要口令。
3. **纸面无法单独撤销。** 换纸必然换 `dek`，即 O(n) 重加密。
4. **改密不吊销旧口令**（§6）。
5. **纸面能推出本机库钥匙。** `dbKey = HKDF(dek)`，API 层不提供 `dbKey` 出口只是最小权限，不是密码学隔离。禁止宣称「纸面在密码学上不可能开库」。
6. **生物识别是口令的等价替代，不是第二因素。** 开启后保险箱强度 = min(主密码强度, OS 登录强度)；Windows Hello 在多数设备上退化为 4–6 位 PIN。这是产品承诺问题，不是密码学问题。
7. **API key 的本机包裹不是保密。** 用 `SHA-256(machine_uid)` 作 AES 密钥，同机任意进程都能算出同一把钥匙——它防的是「误把配置文件当密钥文件分享」，不是防本机读取。UI 与文案禁止宣称「已加密保护」。
8. **恢复通道只带回条目，带不回本机基础设施**（审计日志、生物识别注册、回滚基线）。这些都可重建，符合预期。

## 8. 运行时会话

状态机只有一条：`Locked → Unlocked → Locked`，解锁失败不改变状态。

会话是独占结构：连接 + 四个密钥 + 版本号 + 代数 `epoch`，整体放在一个 `Mutex<Option<...>>` 里。**单锁的理由**：避免出现「有连接但没有密钥」或「有密钥但连接已关」的半状态，这类半状态是竞态 bug 的温床。

`epoch` 是给在途业务用的：每次锁定 `epoch += 1`，在途操作发现代数变了就失败返回，而不是拿着已经清零的密钥继续读。

所有锁定都分两层，顺序不可调换：

1. **先锁库**：`epoch += 1` → 取走会话 → 写审计 → 关连接 → 清零密钥。`epoch` 必须最先，否则在途业务会在密钥已清零之后继续用。
2. **再清外部残留**：强制清剪贴板 → 移除 SSH agent 注入 → 清揭示守卫 → 广播锁定事件（前端据此清可见状态）。

顺序理由：先锁库再清外部，任何一步失败都不会留下「库还开着但剪贴板已清」或「密钥没清零但已广播锁定」的中间态。

`auto_lock_minutes = 0` 表示「永不自动锁」，必须显式支持——把 0 当作「默认 15 分钟」是经典的安全与可用性冲突，这里选择尊重用户设置。

## 9. 明文出口

每个出口先定档，再实现。

| 档 | 含义 |
|---|---|
| **E1 允许** | 用户显式请求、单条目、有 TTL 或审计 |
| **E2 有条件** | 批量 / 落文件 / 出网络，需要二次确认 + 审计 + 路径约束 + 用后清理 |
| **E3 禁止** | 无用户请求、静默发生、不可控 |

具体分档：复制、揭示、单条 TOTP 码是 E1（TTL 默认 30 秒，揭示限速 3 次/60 秒，`expiresAt` 由后端下发而非前端自算）；导出、HIBP 检查、SSH 注入、纸面展示、provider API key 是 E2；日志、错误消息、崩溃报告是 E3——密钥、口令、条目明文一律不得出现。

剪贴板是特殊项：写入用 `Zeroizing` 守卫，到期强制清除，锁定与退出时也强制清除，而不是「尽力而为」。

## 10. 能力通道

### 10.1 生物识别

定位是**口令的等价替代凭据**（理由见 §7.6），实现要点只有三条：

- 交给 OS keystore 的是 52 字节：`dek(20) ‖ dbKey(32)`，由 OS 在生物识别通过后才释放。不做「认证返回 true 然后自己去解密」——那种写法任何进程都能绕过。
- 另存一份指纹 = `SHA-256(明文 payload)`，用来判断 payload 是否还对应当前 `dek`。必须对明文算、不能对密文算：非 Windows 路径每次注册都会换随机包裹密钥，密文必然变化。
- Windows 用签名派生包裹密钥（签名可复现，天然能发现凭据变更）；其他平台没有这个信号，只能依赖平台 ACL。能力缺失返回明确错误码，禁止静默降级。

`rotate_dek` 强制重注册；重置仓库必须清空 keystore。

### 10.2 纸面恢复

| 项 | 值 |
|---|---|
| 长度 | 40 字符 = 5 组 × 8（200 bit） |
| 布局 | 版本字节 `0x02` + `dek(20)` + CRC32C(4) = 25 字节 |
| 编码 | Crockford base32（去掉 I/L/O/U 等易混字母） |
| 归一化 | 全角→半角、大写、去分隔符、`O→0`、`I/L→1`、`U→V` |
| 纠错 | 逐位枚举其余 31 个字符，恰好一个候选通过 CRC 才报位置 |

展示通道的约束是产品级硬要求：**生成后只展示一次**；不自动写剪贴板、不提供一键复制、不生成二维码、不提供分享；只提供打印通道（隐藏 iframe，用完即清，内容做 HTML 转义），文案明确「请手抄或打印保存，不要截图、生成二维码或分享」。

理由：这串字符就是整个保险箱。剪贴板会被同步、截图会进相册、二维码会被扫，任何「方便」的通道都会把它扩散到用户控制不了的地方。

## 11. 性能

同一台 Windows 开发机、release 构建，实测：

| 环节 | v1 | v1.5 |
|---|---|---|
| Argon2id | 3 次，261–283 ms | 1 次，85–95 ms |
| HKDF 派生 | — | 13–25 µs |
| SQLCipher 开库 | 13.1–15.2 ms | 12.9–15.0 ms |
| **解锁总计** | **274–298 ms** | **98–108 ms** |

提速来自**删掉两次 Argon2id**（约 2.7 倍），不是 `kdf_iter = 1`。raw key 路径下 `kdf_iter` 只差 0.2 ms，它的意义只是「不在已经由 Argon2id 派生的全熵密钥上重复做 PBKDF2」。

## 12. 关键决策一览

| 决策 | 理由 |
|---|---|
| `dek` 随机 160 bit | 对随机密钥无条件安全；40 字符纸面可手抄 |
| `dbKey = HKDF(dek)` | 改密真 O(1)，消除跨设备修库与中间态 |
| 单 password slot | 仓库最小化；结构已兼容扩展 |
| 纸面即 `dek`，仓库无恢复封装 | 恢复路径不依赖它要救的仓库 |
| 纸面 40 字符 + CRC32C，不存哈希 | 「可抄对」优于「可验证」，避免公开哈希靶 |
| 口令校验用 GCM tag | 省一次 Argon2id 与一个仓库字段 |
| `kdf_iter = 1` | raw key 已全熵，PBKDF2 重复无收益 |
| `integrity` 用专用结构 + HMAC | 规避 JSON 键序不确定性 |
| 回滚基线三行 KV，不改 DDL | 缩进敏感的整文件 hash，外部重排也能发现 |
| `.vault-meta` 单一写入者 | 双写会让清单与签名失真 |
| 改密与吊销分离 | git 历史使「删除旧封装」不可能真正吊销 |
| 生物识别 = 口令等价替代 | OS 端点攻破不在威胁模型内 |
| 恢复通道只读副本、只打印 | 权限最小化 + 防扩散 |
| 三个版本号不混用 | 混用会误报版本错误或静默降级 |
| `i9:v1:` 域标签冻结 | 它是派生域，不是文件版本 |
| 不做 v1 迁移 | 无存量用户；迁移器是长期负债 |

## 13. 与 v1 的差异

| 维度 | v1 | v1.5 |
|---|---|---|
| 条目密钥根 | Argon2id(口令) | 随机 `dek` |
| 仓库密钥材料 | 主密钥 salt + 校验 salt + 恢复封装 | 一个 password slot |
| 改密成本 | O(n) + 本机库换钥 | O(1)，不动本机库 |
| 改密对恢复码 | 作废 | 不作废 |
| 恢复码能否开库 | 能（解出主密钥） | 不能（`dbKey` 不在纸面） |
| 口令校验 | 独立 salt + 第三次 Argon2id | GCM tag |
| 跨用户预计算 | 可（硬编码 salt） | 不可（每库随机 salt） |
| `kdf_iter` | 256000 | 1 |
| 抄错检测 | 无 | 分组 + CRC32C + 位置定位 |
| 恢复通道 | 布尔返回值 + 全局连接 | 只读副本，编译期无库连接 |
| 恢复码长度 | 32 字符 | 40 字符 |
| 生物识别 payload | 64B | 52B |
| 额外随身文件 | 恢复包 | 零 |
| 审计 | 仅本机表 | 本机表 + JSONL 双写 |
