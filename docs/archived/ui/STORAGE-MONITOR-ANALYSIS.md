## 0 命题核对

| # | 命题 | 判定 | 依据 |
|---|---|---|---|
| 1 | 存储监视器应把「所有应用相关目录」都纳入 | **不成立** | 归属表内的都要能看见，归属表外的一律不碰；`config` 是登记过的例外，工作区根属工具侧边界（§1.4） |
| 2 | 观测与回收可以合成一个组件 | **不成立** | 回收由 owner 执行，否则引用完整性两套语义（§1.1、§6） |
| 3 | 监视器可以自己拼路径、自己遍历目录 | **不成立** | 会绕过 I44 的「字面量单点、拼串单点」门禁，等于造第二个所有者（§1.1、§6） |
| 4 | 附件已有完整范式可复用 | **成立** | `get_storage_breakdown` 已做「磁盘集合 × 引用集合 → 孤儿集合」，`delete_attachments` 已做全量校验（§2、§3） |
| 5 | `tool-results` 可沿用附件范式 | **不成立** | 无引用表，引用写进消息正文的 `<persisted-output path>`，且跨进程重放依赖文件存在（§5.1） |
| 6 | `tool-results` 可自动清理 | **不成立（未定案）** | 清理会破坏重放；是否允许删「仍被历史消息引用」的文件尚未定案（§5.1、§9） |
| 7 | 「本应用存储占用」有唯一自然口径 | **不成立** | 文件长度 / 磁盘占用 / 含不含子布局与伴生文件，三者数量级不同（§4） |
| 8 | 总占用 = 各目录大小相加 | **不成立** | 存在嵌套与重复计数（`derived/` 位于 `attachments/` 内、`backups/` 与 `security.db` 同域），只有分层才不重复计数（§4.4） |
| 9 | 目录体量都可由文件系统遍历得出 | **部分成立** | 受管目录可以；数据库内部表级占用不行，需 SQL；`vault/` 的 Git 历史体积也不是普通文件求和能解释的（§5.5、§5.6） |
| 10 | 监视器应新建 crate | **不成立** | 它依赖 `AppDirs` 与各 owner 的 stats API，放进 `crates/` 会形成反向依赖与「无法注入」（§6） |
| 11 | 监视器应自持一份目录清单 | **不成立** | 那就是第二套字面量；只能调 owner 的 getter（§6） |
| 12 | 采样可无状态全量扫描 | **部分成立** | 规模线性增长，需要缓存；缓存需要显式失效判据（§7.3） |
| 13 | 观测只需快照，不需事件 | **部分成立** | 冷启动对齐只能靠快照；阈值跨越需要事件，但事件不能替代快照（§7.1） |
| 14 | `logs` / `crashes` 应纳入配额治理 | **不成立** | 轮转在插件层（`KeepSome(3)` + 10 MiB），再叠加一套治理会互相打架；只展示数字（§5.4） |
| 15 | 监视器需要处理自指 | **成立且必要** | 它自己会写日志，日志就在被观测目录里（§8） |
| 16 | 单实例假设成立 | **成立** | `tauri-plugin-single-instance` 已在插件装配中启用，缓存可视为单写者；但 `vault/` 会被外部 git 进程改动（§7.3） |

核对结果：与既有门禁相容的形态是「一张观测表 + 一个聚合器」——表里每行由 owner 提供 stats，聚合器只做求和与投影，回收回落到 owner 的既有方法。仓库已把这套形状在附件上完整跑过一遍；真正缺的是 `tool-results` 与安全域的统计入口，以及三个尚未定案的口径。

## 1 观测的边界

### 1.1 三个身份

「纳入管理」在存储语境下混了三种完全不同的权利。需要先拆开，否则监视器会自然滑向所有者：

| 身份 | 能做什么 | 当前持有者 | 监视器能否取得 |
|---|---|---|---|
| **所有者** | 决定目录名、拼基根、建目录 | `app_dirs`（无条件）、`cmd/vault`（可选能力）、各库（库内子布局） | **不能**。只能调用 getter |
| **观测者** | 读字节、条数、时间 | 各 owner 自己提供的只读方法 | 能，且只走方法 |
| **回收者** | 删除、轮转、清空 | owner 的既有方法 | 只能**请求**，不能自己 `remove_*` |

这条分工不是洁癖，它直接对应 I44 的两条门禁：目录字面量只允许命中 `app_dirs::dir_name` 与 `cmd/vault`；`dirs::` 只允许出现在 `app_dirs` 与 `assistant-config`。监视器一旦自己 `read_dir` + `join`，这两条门禁同时失效，而监视器恰恰是最容易长成「到处遍历」的组件。

### 1.2 四类对象

| 对象 | 例子 | 观测手段 | 是否进观测表 |
|---|---|---|---|
| **受管目录** | `attachments/`、`tool-results/`、`mascot-assets/`、`security/` | owner 的 stats | **是** |
| **受管文件** | `assistant.db`、`security.db` | SQL + 文件长度 | **是** |
| **诊断产物** | `logs/`、`crashes/`、`security/audit/` | 目录体量（只读） | **是，但只展示，不参与治理** |
| **非受管路径** | 工作区根、外部导入源、WebView 缓存、系统 temp | — | **否** |

### 1.3 为什么观测不能并入管理

`TASK-RESOURCE-MANAGER-ANALYSIS.md` §1.4 已定过判据：观测回答「占了多少」，管理回答「能不能、该不该、什么时候」。两者合并会产生一个具体后果——回收决策与删除执行同处一个组件，而删除必须尊重引用完整性（附件有 `attachment_refs`，工具结果有消息正文），引用知识只存在于 owner。观测者不掌握引用，就不具备删除资格。

### 1.4 不进观测表的东西

- `config.json` / `orb-config.json` / `mascot-config.json` / `vault-config.json`：`assistant-config` 的 5 个计算点是登记过的既有例外，`app_dirs` 刻意不提供 `config()`；监视器再开第 6 个入口就是漂移。
- 工作区根：属 `assistant-tools` 的路径边界与 I38h 的会话级解析，不是应用自有目录。
- 外部导入源：只经 `resolve_external_input` 进入受管目录，本身无常驻身份。
- WebView 缓存与系统 temp：无 owner、无稳定路径；纳入等于自造第 5 套基根。

## 2 仓库已有的观测范式

| 范式 | 位置 | 形状 | 复用性 |
|---|---|---|---|
| 目录归属 | `src-tauri/src/app_dirs/roots.rs` | `AppDirs` 提供基根与第一层 getter | **直接用**，监视器只拿根 |
| 附件清点 | `crates/assistant-storage/src/attachment_store.rs` `list_all` | 只扫第一层文件，返回 `id/bytes/created_at` | **直接用** |
| 孤儿判定 | `src-tauri/src/cmd/storage.rs` `get_storage_breakdown` | 磁盘集合 − 引用集合（`attachment_refs`） | **可扩展为通用判定** |
| 内容寻址 | 同上 `save_attachment` | `id = sha256.ext`，重复导入不增长 | 去掉重复计数，但不同内容仍线性增长 |
| 回收委托 | 同上 `delete_attachments` | 全量先校验，任一非法整体失败；文件与引用同批处理 | 沿用既有实现 |
| 临时清理 | 同上 `clean_tmp` | 只删 `attachments/` 第一层的 `*.tmp` | 可复用，但**不覆盖 `derived/`** |
| 备份轮转 | `crates/assistant-vault/src/security_db/mod.rs` `prune_backups` | `MAX_BACKUPS = 5`，按时间保留 | 已有回收，缺对外数字 |
| 日志轮转 | `src-tauri/src/plugins.rs` | `KeepSome(3)` + `10 MiB` + `Rotate` | 只可读，不可再治理 |
| 审计轮转 | `crates/assistant-vault/src/audit/jsonl.rs` | 按日 + 超 8 MiB 顺延序号 | 有轮转**无保留策略**（§5.2） |

这套范式说明一件事：**仓库的存储观测是「按 owner 逐个长出来的」，从来没有一张统一账。** 监视器的增量价值正是这张账，而不是又一套遍历逻辑。

| `crashes/` | `assistant-crash` | **无** | 无 | 只读展示 |

### 3.2 现状结论

- **能直接出账的只有附件一条**：`get_storage_breakdown` 已经覆盖「总量 + 孤儿 + 按会话分组」，前端 `src/settings/pages/StorageSettings.tsx` 已是它的消费方，监视器的 UI 落点不必新建页面。
- **其余全部只有「写」没有「读」**：`tool-results`、安全域五项、素材、日志、崩溃，都是只能写、不能查。
- **`security/audit/` 是归属表之外的真实存在**：I44（已归档）§6.1 的归属表列了 `security.db`、`vault/`、`recovery/`、`backups/`，但没有 `audit/`；代码里它由安全库路径的父目录推出（`parent().join("audit")`），且回退值是相对路径 `audit`。这是归属表与代码的一处漂移，应先补表再谈观测。

## 4 三个待定案的口径

口径不选，等于选了最差的那个（判据见 `TASK-RESOURCE-MANAGER-ANALYSIS.md` §8.2）。存储侧有三个：

### 4.1 字节口径

| 可选值 | 特征 | 适用面 |
|---|---|---|
| 文件长度之和 | 便宜、稳定、可解释 | 唯一适合直接展示给用户的数字，文案写「文件大小」 |
| 磁盘占用（簇对齐） | 小文件会系统性放大 | 只适合内部判断，不适合展示 |
| 目录 `metadata` 的 `len()` | Windows 上对目录恒为 0 | 不能当作目录体积（恒为 0，与「空目录」无法区分） |

### 4.2 包含范围

以下四类需要在规格里逐条写明，不能「看情况」：

1. **子布局**：`attachments/` 是否含 `derived/`；`security/` 是否含 `backups/`、`audit/`、`recovery/`；
2. **伴生文件**：主库是否含 `-journal`（当前未显式设置 `journal_mode`，走 SQLite 默认回滚日志，写入期会短暂出现）与将来可能的 `-wal` / `-shm`；素材目录是否含 `atomic_write` 留下的 `custom.tmp`（`uninstall` 只按允许扩展名清理，不删 `.tmp`）；
3. **旧位置残留**：`crashes` 迁移前落在 data 根的旧目录（I44 §6.1 明确不迁移，只在启动后记一条日志）；
4. **自身产物**：监视器自己写的日志就落在 `logs/`，属于自指（§8）。

### 4.3 时间口径

- 附件时间取文件 `modified()`（`list_all` 现状），与 `AttachmentSummary.created_at` 一致；
- 安全域审计时间取 JSONL 记录内的 `at`，不取文件 mtime（一个文件跨多事件）；
- 回收排序与展示排序不同源时，「显示最旧」与「删除最旧」会错位。

### 4.4 总量口径

扁平求和不成立：`derived/` 物理上位于 `attachments/` 内，`backups/` 与 `security.db` 同属安全域。可行形态是**分层**：

```
应用总占用
├─ data 根
│  ├─ 业务数据（assistant.db）
│  ├─ 附件（attachments/，含或不含 derived/ 显式标注）
│  ├─ 工具结果（tool-results/）
│  ├─ 素材（mascot-assets/）
│  └─ 安全域（security/，子项另列）
└─ local 根
   ├─ 日志（logs/）
   └─ 崩溃（crashes/）
```

每一层只对自己的直接子项求和，**不跨层累加**，嵌套项在父层标为「已计入」或「另计」。

## 5 六个真缺口

### 5.1 `tool-results/`：无观测、无回收，且有重放语义冲突

- `FileToolResultStorage` 只有 `persist` 与 `root()`，没有列表、没有总量、没有清理；
- 文件名由 `tool_call_id` 清洗而来（`result_file_name`），**同一 id 重复落盘会覆盖**，所以增长只由「不同 id 的数量」驱动，且永不回收；
- 落盘路径写进消息正文的 `<persisted-output path="…">`，`tool_setup.rs` 的注释明确要求「稳定路径、跨进程重放依赖它」；
- 因此自动清理需要先回答：**允许删除仍被历史消息引用的文件吗？** 目前没有引用表，判定只能靠扫描消息正文，成本与正确性都不轻。

**核对**：观测（`stats`）不依赖重放语义，可以先独立成立；回收依赖重放语义，而当前没有引用表，「超过 N 天删除」这一条无法判定是否破坏重放。

### 5.2 `security/audit/`：有轮转、无保留，且不在归属表

- 按日生成 `audit-YYYYMMDD.jsonl`，超 8 MiB 顺延序号，**没有最大文件数、没有最大总字节**，只有「当天不被撑爆」这一条约束；
- 目录由安全库路径父目录推出，父目录缺失时回退 `PathBuf::from("audit")`（相对路径），与 I44 §11 的失败策略不一致；
- I44（已归档）归属表未登记此目录。

**判定**：这是唯一「既会无限增长、又不在归属表、又没有任何回收入口」的目录。它比 `tool-results` 更需要先补归属与保留策略。

### 5.3 `security/backups/`：有回收、无观测

`prune_backups` 已经按 `MAX_BACKUPS = 5` 保留，但对外没有「当前几份、共多少字节、上限是多少」。用户看不到，监视器也就无法解释「为什么清理没效果」。

### 5.4 `logs/` / `crashes/`：有轮转、无数字

轮转在 `tauri-plugin-log` 内部完成（`KeepSome(3)` + 10 MiB），应用层拿不到当前占用。若要展示，只能由应用层读目录——这又回到 §1.1：由某个 owner 提供，而不是让监视器自己扫。

**核对**：只展示、不治理。再加一套清理会与插件轮转互相打架。

### 5.5 数据库内部占用：文件系统给不出

`assistant.db` 的文件长度包含空闲页与未 `VACUUM` 的空间，表级占用只能靠 SQL（如页数 × 页大小、`dbstat` 虚拟表）。若要「按会话/按表」展示，需先定：是文件长度，还是有效页数，还是 `VACUUM` 后的大小。

### 5.6 `security/vault/`：Git 历史体积不是文件求和

它是 Git 工作区，体积由历史对象决定；`git gc` 前的工作对象、packfile、索引各有语义。同步期间外部 git 进程会持续改动它，任何「读一次算总账」都会很快过期。

## 6 与既有门禁冲突的做法

下表列出与 I44 归属表、owner 边界直接冲突的做法，以及冲突后果与既有替代入口：

| 做法 | 冲突后果 | 既有入口 |
|---|---|---|
| 自己 `read_dir` 遍历受管目录求和 | 绕过 owner，绕过 `is_plain_file_name` 与库内子布局约定 | 调 owner 的 stats |
| 自己 `remove_file` / `remove_dir_all` | 引用与文件两套语义分叉 | 调 owner 的回收方法 |
| 自己拼基根或目录名 | 第二套字面量，I44 门禁失效 | 调 `AppDirs` 的 getter |
| 新建 crate 承载监视逻辑 | 反向依赖，无法注入 `AppDirs` | 放应用层，依赖 `AppDirs` 与 owner |
| 引入第二套日志轮转 | 与插件轮转冲突 | 只读展示 |
| 把 `config` 目录纳入 | 破坏「既有例外」 | 明确排除 |
| 把工作区/导入源纳入 | 造第 5 套基根 | 明确排除 |
| 用 `to_string_lossy` 拼比较键 | 非 UTF-8 被改写，统计与去重失真 | 非 UTF-8 显式报错（I44 §10.3） |

## 7 观测通道与契约

### 7.1 快照与事件的关系

- **快照**：一次聚合返回全量账，供冷启动对齐与手动刷新；可独立成立，不依赖事件流补历史。
- **事件**：仅在「跨越阈值」时下发（如某目录超上限），属提示，不承载账本；事件丢失不影响账本正确性。

两条事实：只做事件会让前端冷启动无账可显示；只做快照则阈值提示需要轮询，可接受。

### 7.2 DTO 契约

- 新增字段按项目规则走 `npm run contract:gen`，禁止手改生成类型；
- 输出侧 `Option` 不加 `skip_serializing_if`（键恒在、值 `null`），前端声明 `T | null`；
- 聚合结果按「层 + 项」组织，而不是扁平 `Record<string, number>`，才能对应 §4.4 的分层口径；
- 口径字段进 DTO（例如 `includesDerived`、`includesJournal`、`byteBasis`），文案才可解释；只写在文档里的口径会随文档过期。

### 7.3 采样成本与缓存失效

- `attachments/` 与 `tool-results/` 的条数与会话/工具调用次数同阶，全量遍历是 O(n) 系统调用，放在主线程会直接卡 UI；
- 缓存失效判据需要显式：目录 mtime 在 Windows 上对「子项增删」可靠、对「子项内容改写」不可靠；`security/vault/` 被外部 git 改动时 mtime 不足以判定；
- 单实例插件已启用，可假设单写者，但 `vault/` 并非单进程独占（外部 git 会改动它）。

## 8 失败模式与自指

| 失败模式 | 表现 | 对应语义 |
|---|---|---|
| 目录不存在 | 首次运行、崩溃目录迁移后 | 计 0，不报错；不创建目录（观测不得产生副作用） |
| 目录不可读 | 权限、加密未解锁（`security/`） | 单项标「不可用」，整账仍返回；不得整体失败 |
| 安全库未解锁 | `security.db` 与 `vault/` 不可读 | 标「锁定」而非「0 字节」，两者语义不同 |
| 文件在遍历中被删除 | 并发回收 | 单项跳过，不计入错误 |
| 非 UTF-8 文件名 | 少见但可能 | 跳过并计数，禁止 `to_string_lossy` 混入展示键 |
| 自指 | 监视器写日志到 `logs/`，又统计 `logs/` | 统计时标注「含本应用日志」，不做递归扣除 |
| 采样阻塞 UI | 大目录遍历 | 异步执行，前端有 loading 与上次快照 |

**自指是显式项而非回避项**：`logs/` 的字节里必然包含监视器自己的运行痕迹；若口径声称「本应用占用不含日志」，就需要写明排除项，而不是让数字自己解释自己。

## 9 待定案项

| # | 待定 | 为什么会影响下游 | 影响面 |
|---|---|---|---|
| 1 | `tool-results` 是否允许回收 | 直接决定 `<persisted-output>` 跨进程重放是否仍成立 | 回收入口、文案、历史消息可用性 |
| 2 | `security/audit/` 的保留策略 | 当前无上限，是唯一确定会无限增长的受管目录 | 归属表、回收入口、合规口径 |
| 3 | 字节口径选「文件长度」还是「磁盘占用」 | 决定所有展示数字与阈值 | DTO 字段、文案 |
| 4 | 是否把 `derived/` 计入附件总量 | 影响孤儿判定与用户对「删了没释放」的感知 | 聚合口径、清理提示 |
| 5 | 数据库是否展示表级占用 | 决定是否需要 SQL 统计与 `VACUUM` 语义 | 主库口径、性能 |
| 6 | `vault/` 是否展示 Git 体积 | 决定是否引入 git 调用或接受「目录求和」的粗糙口径 | 安全域展示 |
| 7 | 阈值告警是否需要 | 决定事件通道是否落地 | 通道形态、契约 |

其中 1 与 2 属「不做会持续恶化」类：`tool-results` 只增不减、`security/audit/` 无保留上限。3 与 4 属「一旦写进 DTO 就难改」类。

## 10 受既有门禁约束的事实

1. **监视逻辑落在应用层**：目录布局只能由应用层持有，库无法注入基根（I44 §5.2），因此监视逻辑依赖 `AppDirs` 与 owner 的 stats，而不是独立 crate。
2. **观测表以 owner 为行**：路径只从 getter 来；以路径为行会形成第二套目录清单。
3. **不存在第二套治理**：`logs` / `crashes` 只展示；`backups` 沿用 `prune_backups`；附件沿用 `delete_attachments`。
4. **观测不产生副作用**：统计不创建目录、不修复缺失目录、不触发迁移。
5. **归属表先于观测**：`security/audit/` 未入表，观测表若以「代码事实」覆盖「规格事实」，漂移会被固化。
6. **口径进 DTO 而不是只进文档**：文档会过期，字段不会。

事实收束：监视器的价值在于把「各 owner 已有的数字」聚成一张可解释的账，并把「谁能删」留在 owner 手里；它一旦自己找目录、自己算、自己删，就从观测者变成了第二个所有者，而这正是 I44 用一整份规格去防止的事。
